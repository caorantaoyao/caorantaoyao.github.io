进程、线程与协程：一个后端服务怎样同时处理多个请求

一个后端服务会同时收到查询商品、创建订单、调用模型等请求。如果只能处理完一个请求再处理下一个，任何慢请求都会让后续用户排队。后端并发的核心问题是：当一个请求正在等待网络、数据库或磁盘时，服务器怎样利用等待时间处理其他请求？常见答案是组合使用进程、线程和协程。

1. 并发与并行

并发表示多个任务在同一段时间内交替推进，即使只有一个CPU核心也能做到。并行表示多个任务在同一时刻由多个CPU核心或计算设备真正执行。

并发：同时应对多个任务
并行：同时执行多个任务

协程特别擅长I/O并发，多进程适合利用多核并行。

2. 为什么后端请求适合并发

一次请求通常不是持续占用CPU，而是反复在计算和等待之间切换：

解析参数
→ 查询Redis并等待
→ 查询数据库并等待
→ 调用其他服务或模型并等待
→ 生成响应

等待期间CPU可以处理其他请求。如果一个请求等待时整个服务也停下来，就会浪费计算资源。

3. 单线程串行模型的问题

while True:
    connection = accept()
    handle_request(connection)

这种模型处理完请求A才接收请求B。若A等待数据库5秒，即使B只需要10毫秒，也必须排队。这是慢请求造成的队头阻塞，生产后端通常不会只依赖这种串行模型。

4. 进程是什么

进程是一个正在运行的程序实例，以及操作系统为它管理的资源集合。进程通常拥有独立虚拟地址空间、堆与栈、文件描述符、Socket、环境变量、权限信息和进程ID。

运行 python app.py 会创建一个Python进程；启动多个副本，就得到多个可独立处理请求的Worker进程。

5. 多进程怎样处理请求

客户端请求
→ 监听端口或负载均衡
├── Worker进程1
├── Worker进程2
├── Worker进程3
└── Worker进程4

多个Worker可以分别处理请求，在多核机器上还可以真正并行执行。多进程能够利用多核、提供较强故障隔离并绕开CPython GIL对单进程线程并行的限制，但会占用更多内存，进程间共享数据也需要IPC或外部存储。

6. 多进程中的共享状态

不同Worker拥有相互隔离的普通Python内存。若每个进程都定义 tasks = {}，第一次请求写入Worker 1，第二次查询进入Worker 2时可能找不到任务。

关键共享状态通常放在Redis、数据库、消息队列、对象存储或专门的状态服务中，而不是只放进某个Worker的全局变量。

7. 线程是什么

线程是进程内部的一条执行路径。同一进程中的线程通常共享堆、全局变量、代码、文件描述符和连接池；每个线程独立拥有调用栈、寄存器状态和程序计数器。

8. 多线程怎样处理请求

线程1等待数据库时，操作系统可以调度线程2继续运行。因此多线程适合大量使用同步阻塞库的I/O场景。

线程1：等待数据库
线程2：处理请求B
线程3：等待网络
线程4：处理请求D

线程共享内存方便，但共享数据可能产生竞争，需要锁、信号量等同步机制。线程过多还会增加栈内存和上下文切换成本。

9. 数据竞争与锁

balance -= 100 可能经历读取、计算、写回三个步骤。两个线程同时读取1000并各自写回900时，正确结果本应为800，却得到900，这叫数据竞争。

with lock:
    balance -= 100

锁可以保护临界区，但也会带来等待、性能开销和死锁风险。工程上还可以使用数据库事务、原子操作、并发队列和减少共享状态等方法。

10. Python GIL

在常见CPython解释器中，GIL使同一个Python进程内通常只有一个线程能在同一时刻执行Python字节码。因此，纯Python CPU密集任务难以仅靠多线程充分利用多核；但线程等待数据库、网络或文件I/O时通常会释放执行机会，所以多线程仍适合很多I/O密集型任务。

任务

常见选择

同步HTTP、数据库、文件等待

线程池可以有效

纯Python大量计算

多进程或独立计算服务

NumPy、PyTorch等原生计算

取决于原生库是否释放GIL及计算设备

大量异步网络连接

协程通常更合适

11. 协程是什么

协程是可以在等待时主动暂停，并在条件满足后恢复的轻量级任务。

async def get_user():
    user = await query_database()
    return user

执行到 await 时，当前协程把控制权交还给事件循环，事件循环可以运行其他请求；数据库结果到达后再恢复原协程。

12. 事件循环

事件循环管理协程、非阻塞Socket、定时器和Future等对象。它反复执行已经就绪的任务，遇到未完成的异步I/O时暂停当前任务并切换到其他任务。

运行协程A
→ A等待数据库并暂停
→ 运行协程B
→ B等待模型API并暂停
→ 运行协程C
→ 数据库结果到达
→ 恢复协程A

Python通常通过 asyncio 提供事件循环，底层会结合操作系统的I/O多路复用能力。

13. 协程的优势与限制

协程创建和切换通常比线程轻，一个线程可以管理大量I/O并发，适合数据库、Redis、RPC、模型API和WebSocket。但它要求调用链使用异步库；阻塞操作和CPU密集计算都会卡住事件循环。

协程并不是多个任务在一个CPU核心上同时执行，而是在明确的让出点高效交替推进。

补充：等待时间为什么不只用线程

等待I/O当然可以使用线程。阻塞线程在等待数据库或网络时不会持续占用CPU，操作系统会将它挂起并调度其他线程。因此，线程和协程都能利用I/O等待时间，区别在于等待期间保留的资源，以及能够经济地支撑多大并发。

线程怎样利用等待时间。请求A所在的线程等待数据库时，操作系统挂起线程A，转而运行线程B。线程A不继续消耗CPU，但仍占用线程栈、内核调度对象和线程池中的一个位置。如果只有几十或几百个并发请求，这种模型往往足够简单有效。

协程怎样利用等待时间。协程执行到异步I/O的 await 时，把控制权交还事件循环。它不需要为每个等待请求保留一条独立的阻塞线程，少量事件循环线程就能管理大量正在等待网络结果的任务。

线程模型：
请求A等待I/O → 线程A被挂起，但线程A仍然存在

协程模型：
请求A等待I/O → 协程A保存状态并暂停
              → 事件循环继续运行B、C、D

为什么不全部使用协程。协程要求调用链真正支持非阻塞异步操作。同步数据库驱动、requests 或只有同步接口的第三方SDK不会因为外层使用 async def 自动变成异步。这类代码直接放进事件循环会阻塞其他协程，放入线程池反而更合适。

为什么不全部使用线程。每个等待请求都占用一条线程时，高并发会增加内存和内核调度成本，线程池耗尽后新请求仍会排队。大量WebSocket、SSE、模型API和Agent工具调用通常长时间处于等待状态，协程的资源效率更高。

Python生产后端通常不是二选一，而是组合使用：多个Worker进程利用多核，每个进程通过协程处理大量异步I/O，少量线程池兼容阻塞SDK，CPU密集和重要长任务交给任务队列或独立计算服务。

线程等待时不占用CPU，但仍占用一条线程；协程等待时主要保存任务状态，让少量线程管理大量等待中的请求。

14. async 与 await

async def 声明协程函数；调用后通常先得到协程对象。await 等待异步对象，同时将控制权交还事件循环。

当前协程执行到await
→ 当前任务暂停
→ 事件循环处理其他任务
→ 等待对象完成
→ 原协程恢复

前提是被调用操作真正支持异步。仅在函数前添加 async 不会让阻塞库自动变成异步。

15. 阻塞操作为什么危险

import time

async def handler():
    time.sleep(10)
    return {"ok": True}

time.sleep() 不会让出事件循环，因此一个请求可能让其他协程也停顿。异步等待应使用 await asyncio.sleep()；网络访问和数据库访问也应使用真正的异步客户端。

16. 用线程池兼容阻塞代码

必须使用同步阻塞库时，可以将工作交给线程池：

import asyncio

result = await asyncio.to_thread(
    blocking_function,
    argument,
)

当前协程暂停，事件循环继续处理其他请求，工作线程完成后再恢复协程。但线程池容量有限，大量慢任务仍会造成排队。

17. FastAPI、ASGI 与 Uvicorn

客户端
→ Nginx或负载均衡器
→ Uvicorn
→ ASGI
→ FastAPI
→ 路由函数

Uvicorn使用事件循环和非阻塞Socket处理并发连接。异步路由适合异步数据库、Redis、HTTP和模型调用；普通同步路由通常会由FastAPI或Starlette放入线程池，避免直接阻塞事件循环。

@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await async_database.get(user_id)
    return user

18. FastAPI中的常见错误

在异步路由中调用同步 requests.get() 会阻塞事件循环，应使用异步HTTP客户端或把同步调用放入线程池。生产中还应复用客户端和连接池，而不是每次请求重新创建。

import httpx

@app.get("/model")
async def call_model():
    async with httpx.AsyncClient() as client:
        response = await client.get(MODEL_URL)
    return response.json()

在异步路由中直接执行大量纯Python计算同样会阻塞事件循环，应考虑进程池、任务队列、独立计算服务或GPU推理服务。

19. 生产环境通常组合使用

负载均衡器
├── Worker进程1
│   └── 事件循环
│       ├── 协程A
│       ├── 协程B
│       └── 协程C
└── Worker进程2
    └── 事件循环
        ├── 协程D
        ├── 协程E
        └── 协程F

多进程利用多核并提供故障隔离，协程处理大量I/O并发，线程池兼容同步阻塞库，任务队列处理长任务，独立计算服务处理重计算或模型推理。

20. Gunicorn 与 Uvicorn

一种常见部署方式是由Gunicorn管理多个Worker进程，每个Worker运行Uvicorn事件循环，再由FastAPI协程处理请求。也可以直接使用Uvicorn多Worker，或由Kubernetes启动多个单Worker容器。

关键是理解：Worker数量决定进程级并行和隔离，每个Worker内部的协程决定I/O并发能力；二者都受CPU、内存、连接池和下游容量限制。

22. Agent长任务怎样设计

让一个HTTP请求保持十分钟，可能遇到网关超时、客户端断开、Worker重启和重试重复执行。更合理的结构是：

客户端提交任务
→ API生成task_id
→ 任务写入持久化队列
→ Agent Worker异步执行
→ 状态保存到数据库或Redis
→ 客户端通过轮询、SSE或WebSocket获取进度

API进程快速接收请求，Worker负责长任务，外部存储保存状态，队列负责调度、重试和削峰。

23. 并发不是无限的

即使协程很轻，也受到数据库连接池、Redis连接池、文件描述符、内存、CPU、线程池、下游容量、模型配额和GPU显存限制。

服务需要设置并发上限、连接池、超时、限流、队列、信号量、熔断和背压。超过系统容量后继续提高并发，只会增加排队、超时和失败。

24. 超时、取消与幂等

result = await asyncio.wait_for(
    call_remote_service(),
    timeout=5,
)

异步调用应设置超时。请求被取消时，还需要考虑是否取消下游任务、数据库事务是否回滚、资源是否清理以及重试是否安全。创建订单、执行Agent工具等操作还要通过幂等键或业务约束避免重复执行。

25. 协程也会发生并发问题

协程通常运行在同一个线程，但会在 await 处切换。如果两个协程先后读取相同余额，再分别写回，就可能发生丢失更新。因此仍需使用数据库事务、乐观锁、唯一约束、分布式锁或 asyncio.Lock 等机制。

26. 一个异步请求怎样执行

@app.get("/orders/{order_id}")
async def get_order(order_id: int):
    cached = await redis.get(f"order:{order_id}")
    if cached:
        return cached

    order = await database.fetch_order(order_id)
    await redis.set(f"order:{order_id}", order, ex=60)
    return order

请求A等待Redis时，事件循环处理请求B；B等待数据库时处理请求C；A的Redis结果到达后再恢复A。同一事件循环线程通过多个等待点交替推进请求。

27. 完整生产执行链路

客户端请求
→ 负载均衡器
→ 容器或服务器实例
→ Worker进程
→ 事件循环
→ 请求协程
→ Redis、数据库、RPC或模型API
→ 恢复协程
→ 生成HTTP响应

同步阻塞代码可交给线程池，CPU密集或重要长任务交给进程池、任务队列或独立服务。

28. 常见误区

  • 多线程等于并行：错误，CPython GIL会限制纯Python字节码的多线程并行。
  • 用了async def就不会阻塞：错误，内部阻塞函数仍会卡住事件循环。
  • 协程能提高CPU计算速度：错误，协程主要利用I/O等待时间。
  • 协程完全不需要锁：错误，协程也会在await处交错访问共享状态。
  • Worker越多越好：错误，过多Worker会增加内存、连接池和调度压力。
  • 并发越高吞吐越高：错误，超过系统或下游容量后只会增加排队和超时。
  • 全局变量可以保存任务状态：多进程和多实例环境中不可靠。
  • 进程内后台任务天然可靠：错误，Worker重启时任务可能丢失。

29. 面试回答

后端服务可以通过多进程、多线程和协程同时处理请求。多进程拥有相对独立的地址空间，可以利用多核并提供故障隔离，适合CPU密集型任务；线程共享进程内存，适合阻塞式I/O，但需要处理锁、数据竞争和CPython GIL；协程由事件循环调度，在遇到异步I/O时主动让出执行权，一个线程就能管理大量并发连接，适合数据库、Redis、RPC和模型API等I/O密集型场景。Python生产服务通常采用多Worker进程加事件循环协程的组合，同步阻塞库放入线程池，CPU密集型或长时间任务交给任务队列或独立计算服务。同时还必须限制并发，并处理连接池、超时、取消、幂等和共享状态。

30. 一句话总结

进程负责资源隔离和多核并行，线程适配阻塞式I/O，协程利用等待时间处理更多请求；生产后端通常组合使用三者。
