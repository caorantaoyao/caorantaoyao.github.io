四层与七层负载均衡：从连接转发到应用路由

一句话理解：四层负载均衡根据 IP、端口和 TCP/UDP 连接选择后端；七层负载均衡能够理解 HTTP、HTTPS 或 gRPC 请求，并根据域名、路径、Header、Cookie 等应用信息路由。

“四层”和“七层”来自 OSI 网络模型。它们不是产品等级，也不代表七层一定优于四层，而是描述负载均衡器在转发请求时能够理解到哪一层信息。

1. 先回顾 OSI 层次

第七层：应用层——HTTP、HTTPS、gRPC、WebSocket
第四层：传输层——TCP、UDP
第三层：网络层——IP

四层负载均衡主要处理连接；七层负载均衡能够解析具体的应用请求。

2. 用同一个 HTTP 请求理解差异

POST /api/agent/run HTTP/1.1
Host: platform.example.com
Authorization: Bearer ***
X-Tenant-ID: tenant-a
X-Model: deepseek
Content-Type: application/json

四层负载均衡主要看到：源 IP、源端口、目标 IP、目标端口、TCP/UDP 协议和连接状态。

七层负载均衡还可以看到：域名、URL 路径、HTTP 方法、Header、Cookie、Content-Type 等应用层信息。

如果只需要回答“这个连接交给哪台机器”，四层往往足够；如果需要回答“这个请求是什么业务，再交给哪个服务”，通常需要七层。

4. 四层负载均衡如何工作

假设用户连接统一入口 10.0.0.10:443，后端有三个实例。负载均衡器在建立 TCP 连接时选择实例 B，后续这个连接中的数据通常继续转发给 B。

客户端 203.0.113.10:52100
            │ TCP 连接
            ▼
四层负载均衡 10.0.0.10:443
            │ 选择实例 B
            ▼
后端实例 B 10.0.1.12:8000

常见选择依据包括轮询、加权轮询、最少连接、源 IP 哈希和网络五元组哈希。

网络五元组：源 IP、源端口、目标 IP、目标端口、传输层协议。

5. 七层负载均衡如何工作

七层负载均衡器接收并解析 HTTP 请求，即使多个请求访问相同 IP 和 443 端口，也能按照业务内容分发。

客户端 HTTPS 请求
        │
        ▼
七层网关 / 负载均衡器
        ├── /api/users/*  → 用户服务
        ├── /api/orders/* → 订单服务
        └── /api/agent/*  → Agent 编排服务

它还能根据 Header 路由：

X-Model: qwen      → Qwen 模型实例池
X-Model: deepseek  → DeepSeek 模型实例池
X-Model: embedding → 向量模型实例池

6. 为什么 HTTPS 会涉及 TLS 终止

HTTPS 会加密路径、Header、Cookie 和请求正文。如果负载均衡器只透传加密数据，就无法根据这些内容做七层路由。要读取 HTTP 内容，通常需要在负载均衡器处终止 TLS。

6.1 TLS 透传

客户端 ==加密==> 四层负载均衡器 ==加密==> 后端

负载均衡器不解密请求，证书通常部署在后端，适合四层转发。

6.2 TLS 终止

客户端 ==HTTPS==> 七层负载均衡器 ——HTTP——> 后端

证书部署在负载均衡器上，内部链路可能使用明文 HTTP。

6.3 TLS 再加密

客户端 ==HTTPS==> 七层负载均衡器 ==HTTPS==> 后端

负载均衡器解密、检查和路由后，再与后端建立新的 TLS 连接。安全要求较高的系统还会使用内部 mTLS。

7. 七层负载均衡能提供哪些能力

  • 按域名路由：api.example.com 与 admin.example.com 进入不同服务。
  • 按路径路由：/api/users、/api/orders、/api/agent 分别转发。
  • 按 Header 或 Cookie 路由：区分租户、版本、模型和用户组。
  • 灰度发布：把少量请求或测试用户导向新版本。
  • 请求处理：添加请求 ID、重写路径、压缩响应、修改 Header。
  • 入口治理：认证、接口级限流、跨域配置和访问日志。

8. 为什么四层通常性能更高

四层转发通常不需要完成 TLS 解密、HTTP 解析、URL 匹配、Header 检查、Cookie 解析和内容修改，因此延迟更低、吞吐量更高、CPU 开销更小，也更容易支持任意 TCP/UDP 协议。

但不能简单回答“七层很慢”。现代 Nginx、Envoy 和云负载均衡器能够提供很高性能。在普通 Web 系统中，应先根据路由和治理需求选择层次，再通过压测验证性能。

9. 连接级和请求级负载均衡

四层通常按连接选择实例：TCP 连接建立时选中 A，该连接里的后续流量通常继续发给 A。

TCP 连接 1 → 实例 A
TCP 连接 2 → 实例 B

七层可以按请求选择实例：理解 HTTP 后，可以对不同请求分别选择后端。

HTTP 请求 1 → 实例 A
HTTP 请求 2 → 实例 B
HTTP 请求 3 → 实例 C

对于 HTTP/2、gRPC、WebSocket 等长连接，仅仅做到“连接数均衡”不一定代表“请求量或计算量均衡”。一个连接可能承载大量并发流或长时间任务。

10. 分别适合什么场景

10.1 更适合四层的场景

  • MySQL、PostgreSQL 等数据库连接；
  • Redis 和其他自定义 TCP 服务；
  • DNS 的 TCP/UDP 流量；
  • 游戏服务器；
  • TLS 透传；
  • 不需要理解应用内容、追求高吞吐的网络入口。

10.2 更适合七层的场景

  • 网站和 REST API；
  • 微服务 API 网关；
  • Kubernetes Ingress；
  • gRPC 服务路由；
  • 灰度发布和 A/B 测试；
  • 需要鉴权、限流、Header 修改的入口；
  • 根据租户、模型或任务类型路由的 AI Agent 平台。

11. 真实系统经常组合使用

用户
  │
  ▼
云负载均衡器（四层）
  │ 分配 TCP 连接
  ▼
Nginx / Envoy 网关集群（七层）
  ├── 用户服务
  ├── Agent 编排服务
  ├── 文件服务
  └── 模型网关

四层入口负责高吞吐连接转发，并把流量分配给多个网关实例；七层网关负责域名和路径路由、身份认证、API 限流、灰度发布与请求追踪。

13. 常见误区

13.1 “Nginx 就是七层负载均衡器”

不完整。Nginx 的 HTTP 模块可以做七层负载均衡，stream 模块也可以做四层 TCP/UDP 负载均衡。

13.2 “四层是硬件，七层是软件”

错误。四层和七层描述处理信息的层次，与硬件或软件没有必然关系。云服务、硬件设备和软件代理都可能同时支持两者。

13.3 “七层更高级，所以全部使用七层”

错误。七层功能丰富但解析开销更高，并且不能天然处理所有自定义协议。是否需要理解应用层内容才是选择依据。

13.4 “负载均衡等于高可用”

错误。还需要健康检查、多负载均衡实例、超时、熔断、限流和后端无状态化。单个负载均衡器自己也可能成为单点。

14. 选型检查清单

☐ 是否需要根据域名、路径、Header 或 Cookie 路由？

☐ 目标协议是 HTTP/gRPC，还是普通 TCP/UDP？

☐ 是否需要 TLS 透传、TLS 终止或再次加密？

☐ 路由单位应当是连接还是每个请求？

☐ 是否需要认证、灰度发布、接口级限流和请求改写？

☐ 长连接数量能否真实反映后端计算负载？

☐ 负载均衡器自身是否做了高可用？

☐ 健康检查是否区分存活与就绪？

15. 面试回答模板

四层负载均衡工作在传输层，主要根据源目标 IP、端口和 TCP/UDP 连接选择后端，通常按连接转发，性能高且协议通用，但无法根据 URL 和 Header 路由。七层负载均衡工作在应用层，能够解析 HTTP、HTTPS 或 gRPC，根据域名、路径、Header、Cookie 等进行请求级路由，还能实现鉴权、限流和灰度发布，但解析和 TLS 终止会产生更多开销。真实系统中经常用四层负载均衡承接入口连接，再用七层网关完成业务路由。

16. 一句话总结

四层看连接：把这个 TCP/UDP 连接交给哪台机器；七层看请求：先判断这个应用请求是什么，再决定交给哪个服务。
