单服务器上的 AI Agent 多租户与容器隔离

核心结论：一台服务器完全可以运行多个容器。镜像只保存一份，容器按照每次 Agent Run 临时创建；服务器达到并发上限后，新任务进入队列，而不是无限创建容器。

一、问题背景

在 AI Agent 运行平台中，用户提交的任务可能执行 Python 代码、调用浏览器、读写临时文件或访问外部工具。如果所有用户和所有任务共享同一个运行环境，前一个任务留下的文件、环境变量、后台进程或访问令牌，就可能被后一个任务读取。

因此，多租户隔离不能只考虑数据库，还要同时处理身份、数据、运行环境、网络、凭证与资源配额。

二、容器为什么能在一台服务器上运行很多个

容器不是完整虚拟机。多个容器共享宿主机的 Linux 内核，只隔离进程、文件系统、网络和资源视图。它们不需要分别启动一套操作系统，因此启动更快、额外开销通常也更小。

高频创建的 Agent 任务沙箱

镜像与容器不是一回事：镜像是只读模板，可以只有一份；容器是由镜像启动出的运行实例。十个任务可以共用同一份镜像，但拥有十个相互隔离的容器实例。

三、推荐架构：常驻控制面 + 临时运行沙箱

单服务器上的服务分为两类：

  • 长期运行：API 服务、PostgreSQL、Redis、任务调度器、Sandbox Manager。
  • 按需运行：每次 Agent Run 创建的临时沙箱容器，任务结束后销毁。

持久化状态必须放在容器之外，例如 PostgreSQL、对象存储或受控工作区。临时容器本身不应成为数据长期保存的位置。

四、为什么按 Run 创建容器，而不是每个用户永久一个容器

“每个用户一个永久容器”看起来直观，但同一用户也可能并发运行多个 Agent。若多个 Run 共享同一容器，它们仍可能相互读取文件、覆盖依赖、争抢端口或继承后台进程。

更合理的三层模型是：

  1. 租户层：隔离数据库、对象存储目录、密钥命名空间、预算与配额。
  2. 用户层：负责登录身份、角色和操作权限。
  3. Run 层：每次执行创建独立临时容器，隔离文件、进程、网络与短期凭证。

因此，推荐原则是：数据按租户长期隔离，执行按 Run 临时隔离。

六、Agent Run 的完整生命周期

  1. 验证用户身份、租户状态和 Agent 权限。
  2. 检查租户预算、并发额度和剩余资源。
  3. 任务进入 Redis 队列。
  4. 调度器获得并发槽位后创建干净容器。
  5. 只挂载本次 Run 必需的输入和临时目录。
  6. 通过 Tool Gateway 提供最小权限、短生命周期凭证。
  7. 执行 Agent，并持续采集日志、资源使用量和审计事件。
  8. 将结果与制品写入容器外的持久化存储。
  9. 撤销临时凭证并销毁容器，释放并发槽位。

七、容器资源与安全限制

docker run --rm \
  --user 10001:10001 \
  --read-only \
  --memory 1g \
  --cpus 1 \
  --pids-limit 128 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --tmpfs /tmp:rw,noexec,nosuid,size=256m \
  --network none \
  agent-python:2026.07
  • CPU 与内存：避免单个 Run 抢占整台服务器。
  • 进程数：防止 fork bomb 等进程耗尽攻击。
  • 只读根文件系统：只允许写入指定 tmpfs 或工作目录。
  • 非 root 用户：降低容器逃逸后的影响范围。
  • 删除 Linux capabilities：不给任务不需要的内核能力。
  • 运行超时：超时后终止任务并强制回收容器。

绝不能把宿主机的 Docker Socket 挂载到 Agent 容器中，否则容器内代码可能直接控制宿主机上的所有容器，等同于获得极高权限。

八、网络和外部工具隔离

默认使用 --network none 最安全。如果 Agent 必须访问互联网，不应直接开放任意网络，而应通过统一的 Egress Proxy 或 Tool Gateway：

  • 按工具和域名设置 allowlist。
  • 阻断 localhost、内网网段和云元数据地址，例如 169.254.169.254。
  • 限制请求频率、响应大小和总流量。
  • 记录租户、用户、Run、工具和目标地址，便于审计。

GitHub、飞书、云厂商等长期密钥不应直接注入容器。更好的方式是容器调用 Tool Gateway，由网关持有真实密钥并签发短期、最小权限的调用结果。

九、数据库多租户隔离

容器解决的是运行时隔离，数据库仍需独立设计。初期可以采用共享数据库、共享表，并要求所有业务表包含 tenant_id；查询时必须绑定当前租户上下文。高敏感租户可以升级到独立 Schema 或独立数据库。

十、容量规划示例

以 4 核 8 GB 单服务器为例，可以先采用保守配置：

  • API、Redis、PostgreSQL 与调度服务预留约 3～4 GB。
  • 每个 Agent 容器限制为 1 CPU、1 GB 内存。
  • 全局最大并发设置为 2，其余任务排队。
  • 每个租户再设置独立并发上限，防止单个租户占满全部槽位。
  • 持续监控内存、CPU、磁盘、容器启动时延和队列等待时间，再调整并发。

这里的数字只是起步值，最终容量取决于 Agent 是否运行浏览器、模型推理、代码编译以及任务平均执行时间。

十一、从单机到多机如何演进

  1. MVP：单机 Docker + PostgreSQL + Redis，限制并发为 1～2。
  2. 增长期：数据库或对象存储外置，增加多台 Worker，队列统一调度。
  3. 规模化：使用 Kubernetes、Nomad 或专门沙箱编排系统，按节点池隔离不同风险等级。
  4. 高风险代码：根据威胁模型升级到 rootless 容器、gVisor、Kata Containers 或 Firecracker 等更强隔离方案。

如果从一开始就把“控制面、队列、持久化状态、临时沙箱”分开，后续从一台服务器扩展到多台服务器时，业务模型不需要推倒重来。

十二、常见误区

  • 误区 1：一个用户一个镜像。正确做法通常是一组版本化公共镜像，按 Run 创建容器。
  • 误区 2：任务结束后清理目录就能安全复用容器。清理很难覆盖后台进程、内存状态、挂载和凭证，跨租户最好直接销毁。
  • 误区 3：数据库隔离就等于多租户隔离。Agent 平台还必须隔离运行环境、网络、密钥、缓存、日志和配额。
  • 误区 4：容器数量越多吞吐量越高。超过机器资源后只会导致抖动、OOM 和整体失败，应通过队列施加背压。
  • 误区 5：容器天然安全。容器只是基础边界，仍需要非 root、cgroup、capability、网络策略和凭证治理。

十三、面试回答模板

我的 AI Agent 平台即使初期只有一台服务器，也不会让所有任务共用一个运行环境。我会把 API、数据库、Redis 和调度器作为常驻控制面，把每次 Agent 执行放进临时容器。镜像只保留少量版本化模板，容器按 Run 创建，任务结束后销毁；并发超过服务器容量时进入队列。数据按租户隔离，执行按 Run 隔离，同时限制 CPU、内存、进程数、运行时间和网络访问。这样既能在单机上控制成本，也为后续增加 Worker 节点预留了扩展路径。

十四、最终设计原则

租户数据库隔离 + Agent Run 沙箱隔离 + 队列并发控制 + 短期工具凭证。

一台服务器不是不能运行多个容器，而是必须明确资源上限：并发运行少量容器，其余任务排队；任务结束后立即销毁，不保留跨 Run 状态。
