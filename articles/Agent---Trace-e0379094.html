Agent 评测：从 Trace 数据到质量闭环

Agent Trace 让我们看见一次任务经历了什么，评测则判断这次任务完成得好不好。二者结合后，系统才能从线上失败中提取样本，在离线环境回归验证，再把改进版本安全地发布回线上。

核心结论：Trace 提供证据，Evaluation 根据标准解释证据。没有 Trace，评测难以定位失败环节；没有评测，Trace 只是大量运行记录，无法证明新版本是否更好。

1. Trace 与评测分别回答什么

能力

核心问题

典型产物

Trace

这一次任务发生了什么，为什么成功或失败？

模型、检索、Tool、状态变化、错误、耗时和成本组成的执行链

Evaluation

一个版本在一组任务上的质量如何？

数据集、评分标准、逐样本结果、聚合指标和回归报告

Monitoring

生产系统是否正在恶化？

成功率、延迟、成本、错误率和安全告警看板

Trace 通常关注单次 Run，评测通常关注一批样本或两个版本的比较，监控则持续观察生产流量。三个视角可以使用同一批遥测数据，但目的不同。

2. 一套评测系统的四个基本对象

Eval Case。一个测试样本，至少包含输入、测试环境、期望结果或必须满足的约束，以及评分方法。例如“创建文档后必须位于指定父节点，且不得出现同名重复页面”。

Eval Dataset。多个 Eval Case 组成的数据集。它不应只包含顺利案例，还要覆盖边界条件、历史故障、攻击样本和高风险操作。

Grader。负责评分的程序或人，可以是精确匹配、规则代码、模型裁判或人工评审。

Eval Run。某个确定版本的 Agent 在一个确定数据集上的完整运行。结果需要绑定模型、Prompt、Skill、Tool、代码、配置、数据集和 Grader 版本，才能复现和比较。

3. 为什么不能只看最终回答

Agent 的最终文本正确，不代表整个过程正确。例如 Agent 可能先访问了错误租户的数据，最后又碰巧生成了正确答案；也可能重复创建两份文档，只把其中一份链接返回给用户。只评分最后一句话，会漏掉这些过程问题。

因此 Agent 评测至少要同时覆盖三层：

  • Outcome Evaluation：用户目标是否真正完成。
  • Trajectory Evaluation：执行路径是否满足必要约束，Tool 选择、参数、顺序和重试是否合理。
  • Component Evaluation：检索、模型、Tool、Memory、规划和安全组件分别表现如何。

4. 最终结果评测：任务是否完成

最终结果评测应尽量检查真实世界状态，而不只检查 Agent 自己的口头声明。创建文档后重新查询文档，修改数据库后重新读取数据，发送消息后核对收件人和消息内容，这些都属于独立验收。

常见指标包括任务成功率、字段准确率、答案正确性、引用正确性、约束满足率和人工接管率。对于有明确标准答案的任务，可以使用精确匹配或程序校验；对于开放式任务，则需要 Rubric、模型裁判或人工评审。

5. 轨迹评测：Agent 是怎样完成任务的

轨迹评测使用 Trace 中的 Span、Tool Call 和状态变化检查执行过程。常见检查项包括：

  • 是否选择了允许且合适的 Tool。
  • 参数 Schema、租户标识和目标资源是否正确。
  • 是否执行了必须的权限检查、幂等检查和写后回读。
  • 是否产生无意义的重复调用、循环或高成本模型调用。
  • 失败后是否正确重试、改道、请求审批或停止。
  • 是否违反 Tool 白名单、数据边界和风险策略。

轨迹评测不应把某一条固定路径当成唯一正确答案。很多任务存在多条同样合理的执行路线，更稳妥的做法是定义必须发生的步骤、禁止发生的步骤和资源预算，而不是要求每个 Span 顺序完全一致。

组件评测能回答“为什么总分下降”。如果结果正确率变差，但检索 Recall@K 没有变化，而 Tool 参数错误率明显升高，那么问题更可能出在 Tool Calling 或参数生成，而不是知识库。

7. 工程与效率指标

一个正确但极慢、极贵或经常超时的 Agent 仍然不能投入生产。评测报告应同时包含质量和工程指标：

  • 任务成功率、错误率、超时率和重试成功率。
  • P50、P95、P99 端到端延迟，以及各 Span 的耗时占比。
  • 平均 Agent Loop 次数、模型调用次数和 Tool 调用次数。
  • 输入 Token、输出 Token、缓存命中和单任务成本。
  • 人工确认率、人工接管率和恢复成功率。

不要只用加权总分掩盖硬约束。安全违规、跨租户泄漏和未授权写入通常应该直接判定失败，即使回答质量和延迟得分很高。

8. 离线评测：发布前的回归测试

离线评测是在固定环境中，让候选版本运行一组可复现样本，然后与基线版本比较。它适合验证 Prompt、模型、Skill、Tool 或工作流改动是否引入回归。

版本化评测集
    ↓
运行基线 Agent 与候选 Agent
    ↓
收集最终结果与完整 Trace
    ↓
规则 Grader、模型 Grader、人工抽检
    ↓
比较质量、安全、延迟与成本
    ↓
通过发布门禁或阻止上线

离线环境需要尽量固定外部依赖。数据库、搜索结果、时间和第三方 API 如果每次都变化，就难以判断差异究竟来自 Agent 版本还是测试环境。常见做法是使用测试租户、Mock Tool、固定快照或可重复 Fixture。

9. 在线评测：真实流量中的质量验证

离线测试无法覆盖所有真实输入，因此通过回归门禁后还需要灰度发布、A/B Test 或影子流量。在线阶段重点观察任务完成率、用户反馈、人工接管、错误率、延迟、成本和安全告警。

点赞、停留时间和重复提问等行为只是代理信号，并不天然等于正确性。例如用户没有投诉，可能是因为已经放弃使用。因此线上信号应该与抽样人工评审、真实状态校验和失败 Trace 分析结合。

10. 如何从 Trace 构建评测数据集

线上 Agent 运行
      ↓
采集正常、失败和高风险 Trace
      ↓
脱敏、去重、聚类并标注失败原因
      ↓
转化为回归、边界和对抗样本
      ↓
修改 Prompt、Skill、模型或 Tool
      ↓
离线评测与灰度发布
      ↓
继续收集新的线上 Trace

数据集应至少包含四类样本：代表正常业务分布的核心集、来自历史故障的回归集、长尾与边界条件集、越权和 Prompt Injection 等安全对抗集。容易出现的数据不一定最重要，高风险低频任务也应保留足够覆盖。

生产 Trace 进入数据集前必须进行敏感信息脱敏、租户隔离和访问控制。正常请求可以按策略采样，但失败、越权、超时和高成本请求通常应提高保留优先级。

11. Grader：谁来给 Agent 打分

确定性 Grader。使用字符串、JSON Schema、数据库状态、单元测试或业务规则评分。可复现、便宜，适合有明确答案和硬约束的任务。

模型 Grader。由另一个模型按照 Rubric 判断正确性、完整性、相关性或风格。适合开放式文本，但结果具有不确定性。

人工评审。适合高风险、主观标准或用于校准模型裁判的样本。成本最高，但不能完全被自动化替代。

生产系统通常组合三者：程序规则先检查硬约束，模型裁判处理语义质量，人工抽检校准模型裁判并处理争议样本。

12. LLM-as-a-Judge 的使用边界

LLM-as-a-Judge 适合没有唯一标准答案的任务，但它不是绝对真值。模型可能偏爱更长的答案、偏爱特定措辞、对自己生成的内容更宽松，也可能被待评测文本中的指令干扰。

使用模型裁判时应：

  • 给出清晰、可分解的 Rubric，而不是只问“答案好不好”。
  • 固定 Judge 模型、Prompt、温度和版本。
  • 优先采用成对比较，必要时随机交换候选答案顺序。
  • 用人工标注集校准一致率、误判率和阈值。
  • 把评分理由和引用证据一并保存，便于审查。
  • 安全、权限和真实状态等硬约束优先使用确定性检查。

13. 非确定性：为什么同一案例要运行多次

模型采样、检索排序、外部 Tool 和并发执行都可能让同一输入产生不同轨迹。只运行一次无法代表真实稳定性。重要案例应重复运行，报告成功率、均值、分位数和波动范围，并记录随机种子、温度和外部依赖快照。

如果产品允许多次尝试，可以报告多次尝试至少成功一次的指标；如果用户要求一次调用就可靠，则应重点看单次成功率。指标必须符合真实产品交互，不能用大量重试掩盖首轮失败。

14. 安全评测

Agent 能够调用外部系统，因此安全评测必须覆盖“模型输出安全”和“实际动作安全”两个层面。建议重点测试：

  • 网页、文档、邮件和 MCP 返回内容中的 Prompt Injection。
  • Tool 白名单、参数范围和资源 ACL 是否能够阻止越权。
  • 是否会访问其他用户或其他租户的数据。
  • 删除、发送、支付等高风险写操作是否要求确认或审批。
  • Trace、日志和评测集是否泄露 Token、Cookie、PII 或商业数据。
  • 失败或超时后是否发生重复写入和不可控重试。

安全失败通常应设置为发布阻断项，而不是与普通质量分数平均。

关键关联键包括 trace_id、span_id、eval_case_id、eval_run_id 和各类版本号。这样既能从低分样本跳转到对应 Trace，也能从异常 Span 找到它属于哪次评测和哪个版本。

16. 实例：评测“落地成飞书文档”

任务输入是“把当前知识落地成飞书文档”。最终结果评测可以检查页面是否真实存在、标题和父节点是否正确、正文是否包含指定知识点，以及返回链接是否可访问。

轨迹评测可以检查：

  1. 是否先验证个人飞书账号和用户身份。
  2. 是否查询父节点并检查同名页面。
  3. 是否选择语义正确的知识库位置。
  4. 是否只创建一次 Wiki 节点。
  5. 是否在写入后回读层级、目录和区分性关键词。
  6. 是否没有访问企业飞书或其他租户资源。

工程指标还可以统计端到端耗时、飞书 API 调用次数、失败重试次数和单任务成本。这样评测的对象就不只是“文章写得像不像”，而是 Agent 是否正确、安全、稳定地完成了真实任务。

17. 常见错误

  • 只评最终回答：无法发现越权访问、重复写入和错误 Tool 路径。
  • 只看一个总分：安全失败可能被语言质量和速度分数抵消。
  • 评测集全是简单正常样本：线上长尾、故障和攻击输入没有覆盖。
  • 模型裁判没有人工校准：评分漂移后仍被当成真实质量。
  • 不固定版本和环境：无法判断回归来自代码、模型还是外部依赖。
  • 把生产 Trace 原样加入数据集：可能造成隐私泄漏和跨租户数据污染。
  • 过度约束唯一轨迹：把另一条同样正确的执行路线错误判失败。

18. 面试回答模板

Agent Trace 记录一次任务中模型、检索、Tool、状态变化、错误、耗时和成本组成的完整执行链；评测则用数据集和 Grader 判断一个版本的任务成功率、执行轨迹、组件质量、安全性与工程效率。生产中的失败 Trace 可以经过脱敏和标注后沉淀为回归样本，新版本在固定数据集上进行离线评测，通过发布门禁后再灰度上线，并继续从线上 Trace 中发现新问题。这样就形成 Trace、评测、发布和监控的持续质量闭环。

21. 面试八股强化：先把核心术语说清楚

Agent 评测不是只给模型最后一句话打分，而是在可重复的任务、环境和工具条件下，多次运行“模型 + Agent Harness + Context + Tool + State”，再检查最终结果、执行轨迹、关键组件和线上产品效果。面试时先建立这套对象模型，再谈指标，会比直接罗列准确率更完整。

术语

含义

面试中要强调的点

Task

一条待完成的用户任务，包含输入、初始环境、可用工具和业务约束。

不是只有一段 Prompt，还包括任务发生时的真实环境。

Trial

Agent 针对一个 Task 的一次完整运行。

Agent 有随机性，同一 Task 需要重复多个 Trial。

Trace / Trajectory

一次运行中的模型决策、工具调用、参数、Observation、状态变化、耗时和错误。

用于解释为什么成功或失败，但不能替代最终结果检查。

Outcome

运行结束时数据库、文件、订单或外部系统的真实最终状态。

Agent 自称“成功”不等于任务真的成功。

Grader

对结果、轨迹或组件进行判分的规则、程序、LLM 或人工专家。

客观事实优先用确定性 Grader，开放质量再用 Judge。

Eval Suite

版本化的任务集、环境、Rubric、Grader、运行配置和报告切片。

它应可复现、可回归，而不是临时手测几个 Demo。

Agent Harness

包围模型的运行时，包括 Agent Loop、Context 组装、Tool 执行、权限、State、Checkpoint 和错误恢复。

被测对象是模型与 Harness 共同构成的系统。

Evaluation Harness

负责装载数据集、重置环境、批量运行 Trial、执行 Grader、聚合指标和生成报告的评测基础设施。

不要把它与 Agent Harness 混为一谈。

一句话判断：Outcome 回答“事情有没有真正办成”，Trace 回答“Agent 是怎样办的”，组件评测回答“具体坏在哪一层”，线上指标回答“真实用户是否因此获益”。

22. 四层评测如何组合，而不是互相替代

层级

典型问题

适合的指标或 Grader

局限

组件级

记忆是否写对、RAG 是否召回、Tool 是否选对、参数是否合法？

Precision、Recall、F1、Recall@k、Schema 校验、参数准确率。

组件分数提高，不保证端到端任务更好。

轨迹级

调用顺序、依赖、权限、重试与错误恢复是否合理？

必要步骤覆盖率、越权率、循环率、恢复率、Trajectory Judge。

开放任务可能有多条正确路径，不能盲目精确匹配唯一轨迹。

端到端 Outcome

数据库、文件、订单或最终答案是否达到目标状态？

Task Success、目标状态匹配、规则遵循率、回答正确性与完整性。

最接近用户价值，但单独使用时难以定位失败原因。

产品与线上

真实用户是否完成任务、继续使用、减少人工接管？

任务完成率、满意度、留存、人工接管、延迟、成本和安全事件。

受真实流量和外部因素影响，通常还需 A/B 和 Trace 归因。

正确做法是把四层连起来：先用端到端指标判断版本是否真正变好，再用 Trace 和组件指标解释变化来自哪里，最后通过灰度与 A/B 验证真实产品价值。对于权限、隐私、不可逆工具操作等高风险条件，应设置硬门禁，而不是用平均分抵消。

23. pass@1、pass@k 与 pass^k：能力和稳定性不能混为一谈

pass@1 是一次运行成功的比例，最贴近用户只得到一次回答的常见场景。pass@k 表示运行 k 次后至少成功一次的概率，适合允许搜索、采样多个候选或重试的任务；它回答“这个系统有没有能力做到”。pass^k 表示连续 k 次全部成功的概率，用来衡量生产 Agent 的一致性和可靠性；它回答“这个系统能不能每次都做到”。

若每次 Trial 的成功概率近似为 p 且相互独立，则：

pass@k ≈ 1 − (1 − p)^k

pass^k ≈ p^k

例如单次成功率为 80%，运行 5 次后至少一次成功的 pass@5 约为 99.97%，看起来很高；但连续 5 次全部成功的 pass^5 只有约 32.77%。因此，不能用很高的 pass@k 掩盖较差的单次体验或稳定性。面向真实用户的 Agent 通常至少要同时报告 pass@1、重复 Trial 的分布和 pass^k。

24. 数据集、回归与 A/B：如何证明新版本真的更好

一条可复现的 Agent 评测样本不仅包含用户输入，还应包含初始环境状态、可用工具与权限、业务规则、期望 Outcome、必要里程碑、禁止行为、评分 Rubric、场景标签和难度。样本来源应同时覆盖产品需求、领域专家题、历史 Trace、用户投诉、Bug、边界场景和对抗场景。

环节

关键做法

要避免的问题

数据集

覆盖典型、边界、对抗与真实失败；按任务类型、难度和用户群切片；保留未参与调优的 Holdout。

只挑容易成功的 Demo，或不断针对测试题刷分。

公平对照

Baseline 与 Candidate 使用相同任务、环境、模型、Prompt、Tool、温度、Judge 和运行次数，尽量只替换一个主要变量。

同时改模型、Prompt、Memory 和检索器后，无法归因。

回归门禁

正确性、安全、延迟和成本分别设阈值；重要 Slice 不能被总平均分掩盖。

总分上升就直接发布，忽视租户泄漏等严重退化。

线上 A/B

按用户稳定随机分桶，预先定义主指标与护栏指标，再观察真实任务完成、体验、成本和安全。

只看短期点击或满意度，忽视学习结果、错误和人工接管。

质量闭环

线上失败经脱敏、去重和人工确认后回流离线集，修复后进入 Regression Suite。

评测集长期不更新，与真实失败分布脱节。

Capability Eval 回答“系统现在能做到什么”，可以包含尚未稳定解决的难题；Regression Eval 回答“过去会的能力有没有退化”，应接近全通过并作为发布门禁。已经稳定解决的能力题可以逐步进入回归集。

25. 你的记忆系统升级应该怎样评测

记忆系统升级非常适合讲成“组件级 + 端到端 + 工程护栏”的完整评测案例。最关键的实验设计是保留旧版 Agent 作为 Baseline，在相同模型、Prompt、Tool、任务集、环境、Judge 和 Trial 次数下，只替换 Memory 模块。这样才能把效果变化归因到记忆系统，而不是其他变量。

25.1 组件级：记忆本身是否工作正确

25.2 端到端：记忆是否真的改善了 Agent

LongMemEval 将长期交互记忆拆成五类核心能力：Information Extraction、Multi-session Reasoning、Knowledge Updates、Temporal Reasoning 和 Abstention。你的评测集可以据此设计跨会话事实回忆、多会话信息组合、偏好更新、时间先后判断，以及“历史中没有信息时不编造”的样本。

最终要比较的是跨会话回答正确率、一致性、个性化准确性、错误记忆干扰率、Token、延迟和成本。仅证明 Recall@k 提高还不够：如果召回更多内容却引入过期事实、噪声、跨用户泄漏或更高延迟，端到端 Agent 可能反而变差。

25.3 适合你的项目叙述

我对记忆系统做升级时，没有只看召回率，而是建立了旧版 Baseline 和新版 Candidate。在相同模型、Prompt、Tool、任务集和运行配置下，只替换 Memory 模块。组件层评测抽取、去重、更新、召回和上下文注入；端到端评测跨会话回忆、多会话推理、知识更新、时间推理和无记忆时的拒答；同时观察 Token、延迟、稳定性和错误记忆干扰。真实失败样本会沉淀进回归集，避免后续版本再次出现同类问题。

26. 教育 Agent 的评测：会做题不等于会教学

教育 Agent 不能只看答案准确率。一个直接给出正确答案的系统可能让用户短期满意，却没有帮助学生理解，更可能诱导代做。评测应至少覆盖学科正确性、教学质量、真实学习结果和安全公平四条轴。

维度

关键指标

学科与多模态正确性

OCR/公式识别、题目区域切分、知识点识别、最终答案、解题步骤、教材或检索证据忠实度。

教学质量

能否识别并定位学生错误，是否提供循序渐进的提示，指导是否可执行，是否适配年级和已有水平，是否避免无条件泄露答案。

真实学习结果

前测/后测提升、同类题迁移、延迟保持率、重复错误减少、学习完成率。

产品体验

真实任务完成率、满意度、继续互动、人工接管、延迟和成本。

安全与公平

未成年人隐私、图片数据保护、年龄适配、有害内容、作弊诱导，以及不同年级、语言和群体的切片表现。

面试豆包爱学这类岗位时，可以明确说：回答正确性只是能力层，是否帮助学生形成理解才是产品层；安全、隐私和年龄适配属于硬门禁，不能用其他维度的高分抵消。

27. LLM-as-a-Judge 的偏差与治理

LLM Judge 适合开放答案、教学质量和轨迹合理性等难以写死规则的维度，但它是可扩展的近似标注器，不是真值来源。常见偏差包括位置偏差、冗长偏差、同模型家族偏好、Judge 自身推理错误，以及更换 Prompt、Rubric 或模型造成的标尺漂移。

工程上应将客观事实交给 Code Grader；Judge 使用单一维度、明确分档和示例化 Rubric；Pairwise 比较时隐藏模型名称并交换 A/B 顺序；有标准答案时提供 Reference；允许证据不足时输出 Unknown；固定并版本化 Judge 模型、Prompt、温度和 Rubric；再用专家标注小集校准，并对争议、高风险和随机样本进行人工复核。

28. 高频面试陷阱

错误说法

正确回答

只看最终答案就够了。

Outcome 决定是否完成，Trace 和组件评测负责定位原因；也不能只看漂亮 Trace 而忽略真实最终状态。

Agent 有随机性，所以评测没意义。

正因为非确定，才要固定环境、重复 Trial，并区分 pass@1、pass@k 和 pass^k。

LLM Judge 可以替代人工。

Judge 负责规模化，人工负责定义 Gold Standard、校准标尺和复核高风险案例。

唯一标准轨迹越精确越好。

只有法规、权限和业务强制步骤应设硬约束；开放任务可能有多条正确路径。

平均分提升就能上线。

还要看重要 Slice、失败严重度、稳定性、延迟、成本、安全门禁和线上 A/B。

召回率提高就证明记忆系统更好。

还必须证明端到端回答和任务完成改善，并排除噪声、过期事实、泄漏、Token 和延迟代价。

29. 可直接背诵的两分钟回答

我会把 Agent 评测拆成四层。第一层是组件评测，例如检索召回、记忆抽取、Tool 选择和参数是否正确；第二层是 Trace 评测，检查 Agent 的决策、工具调用、规则遵循和错误恢复；第三层是端到端 Outcome，直接检查数据库、文件或最终答案，确认任务真正完成；第四层是上线后的产品指标，例如真实任务完成率、满意度、人工接管、延迟和成本。

Grader 我不会只用一种。客观事实优先使用确定性程序，例如 Schema、单元测试和数据库最终状态；开放质量使用带明确 Rubric 的 LLM-as-a-Judge；再用专家人工标注集校准 Judge，并通过盲评、交换答案顺序和抽样复核控制位置、长度等偏差。

数据集会来自产品需求、专家样本、历史 Trace 和真实失败，覆盖正常、边界和对抗场景，并按能力切片。因为 Agent 有随机性，同一任务会运行多次，同时看 pass@1 和连续稳定性，而不是只展示一次成功 Demo。

在我的记忆系统升级中，我保留旧版作为 Baseline，在相同模型、Prompt、Tool 和评测集下只替换 Memory 模块。组件层比较抽取、去重、更新和召回；端到端比较跨会话正确性、知识更新、时间推理和不知道时能否拒答；同时观察 Token、延迟和错误记忆干扰。修复后的真实失败样本会进入回归集，最后再通过灰度或 A/B 验证真实用户效果。
