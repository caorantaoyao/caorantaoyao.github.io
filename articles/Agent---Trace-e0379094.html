Agent 评测：从 Trace 数据到质量闭环

Agent Trace 让我们看见一次任务经历了什么，评测则判断这次任务完成得好不好。二者结合后，系统才能从线上失败中提取样本，在离线环境回归验证，再把改进版本安全地发布回线上。

核心结论：Trace 提供证据，Evaluation 根据标准解释证据。没有 Trace，评测难以定位失败环节；没有评测，Trace 只是大量运行记录，无法证明新版本是否更好。

1. Trace 与评测分别回答什么

能力

核心问题

典型产物

Trace

这一次任务发生了什么，为什么成功或失败？

模型、检索、Tool、状态变化、错误、耗时和成本组成的执行链

Evaluation

一个版本在一组任务上的质量如何？

数据集、评分标准、逐样本结果、聚合指标和回归报告

Monitoring

生产系统是否正在恶化？

成功率、延迟、成本、错误率和安全告警看板

Trace 通常关注单次 Run，评测通常关注一批样本或两个版本的比较，监控则持续观察生产流量。三个视角可以使用同一批遥测数据，但目的不同。

2. 一套评测系统的四个基本对象

Eval Case。一个测试样本，至少包含输入、测试环境、期望结果或必须满足的约束，以及评分方法。例如“创建文档后必须位于指定父节点，且不得出现同名重复页面”。

Eval Dataset。多个 Eval Case 组成的数据集。它不应只包含顺利案例，还要覆盖边界条件、历史故障、攻击样本和高风险操作。

Grader。负责评分的程序或人，可以是精确匹配、规则代码、模型裁判或人工评审。

Eval Run。某个确定版本的 Agent 在一个确定数据集上的完整运行。结果需要绑定模型、Prompt、Skill、Tool、代码、配置、数据集和 Grader 版本，才能复现和比较。

3. 为什么不能只看最终回答

Agent 的最终文本正确，不代表整个过程正确。例如 Agent 可能先访问了错误租户的数据，最后又碰巧生成了正确答案；也可能重复创建两份文档，只把其中一份链接返回给用户。只评分最后一句话，会漏掉这些过程问题。

因此 Agent 评测至少要同时覆盖三层：

  • Outcome Evaluation：用户目标是否真正完成。
  • Trajectory Evaluation：执行路径是否满足必要约束，Tool 选择、参数、顺序和重试是否合理。
  • Component Evaluation：检索、模型、Tool、Memory、规划和安全组件分别表现如何。

4. 最终结果评测：任务是否完成

最终结果评测应尽量检查真实世界状态，而不只检查 Agent 自己的口头声明。创建文档后重新查询文档，修改数据库后重新读取数据，发送消息后核对收件人和消息内容，这些都属于独立验收。

常见指标包括任务成功率、字段准确率、答案正确性、引用正确性、约束满足率和人工接管率。对于有明确标准答案的任务，可以使用精确匹配或程序校验；对于开放式任务，则需要 Rubric、模型裁判或人工评审。

5. 轨迹评测：Agent 是怎样完成任务的

轨迹评测使用 Trace 中的 Span、Tool Call 和状态变化检查执行过程。常见检查项包括：

  • 是否选择了允许且合适的 Tool。
  • 参数 Schema、租户标识和目标资源是否正确。
  • 是否执行了必须的权限检查、幂等检查和写后回读。
  • 是否产生无意义的重复调用、循环或高成本模型调用。
  • 失败后是否正确重试、改道、请求审批或停止。
  • 是否违反 Tool 白名单、数据边界和风险策略。

轨迹评测不应把某一条固定路径当成唯一正确答案。很多任务存在多条同样合理的执行路线，更稳妥的做法是定义必须发生的步骤、禁止发生的步骤和资源预算，而不是要求每个 Span 顺序完全一致。

6. 组件评测：定位具体是哪一层变差

组件

常见评测问题

示例指标

RAG

正确文档是否被召回并排在前面？

Recall@K、MRR、Context Precision、引用命中率

是否选择正确 Tool，参数是否有效？

正确率、事实一致性、引用准确率

组件评测能回答“为什么总分下降”。如果结果正确率变差，但检索 Recall@K 没有变化，而 Tool 参数错误率明显升高，那么问题更可能出在 Tool Calling 或参数生成，而不是知识库。

7. 工程与效率指标

一个正确但极慢、极贵或经常超时的 Agent 仍然不能投入生产。评测报告应同时包含质量和工程指标：

  • 任务成功率、错误率、超时率和重试成功率。
  • P50、P95、P99 端到端延迟，以及各 Span 的耗时占比。
  • 平均 Agent Loop 次数、模型调用次数和 Tool 调用次数。
  • 输入 Token、输出 Token、缓存命中和单任务成本。
  • 人工确认率、人工接管率和恢复成功率。

不要只用加权总分掩盖硬约束。安全违规、跨租户泄漏和未授权写入通常应该直接判定失败，即使回答质量和延迟得分很高。

8. 离线评测：发布前的回归测试

离线评测是在固定环境中，让候选版本运行一组可复现样本，然后与基线版本比较。它适合验证 Prompt、模型、Skill、Tool 或工作流改动是否引入回归。

版本化评测集
    ↓
运行基线 Agent 与候选 Agent
    ↓
收集最终结果与完整 Trace
    ↓
规则 Grader、模型 Grader、人工抽检
    ↓
比较质量、安全、延迟与成本
    ↓
通过发布门禁或阻止上线

离线环境需要尽量固定外部依赖。数据库、搜索结果、时间和第三方 API 如果每次都变化，就难以判断差异究竟来自 Agent 版本还是测试环境。常见做法是使用测试租户、Mock Tool、固定快照或可重复 Fixture。

9. 在线评测：真实流量中的质量验证

离线测试无法覆盖所有真实输入，因此通过回归门禁后还需要灰度发布、A/B Test 或影子流量。在线阶段重点观察任务完成率、用户反馈、人工接管、错误率、延迟、成本和安全告警。

点赞、停留时间和重复提问等行为只是代理信号，并不天然等于正确性。例如用户没有投诉，可能是因为已经放弃使用。因此线上信号应该与抽样人工评审、真实状态校验和失败 Trace 分析结合。

10. 如何从 Trace 构建评测数据集

线上 Agent 运行
      ↓
采集正常、失败和高风险 Trace
      ↓
脱敏、去重、聚类并标注失败原因
      ↓
转化为回归、边界和对抗样本
      ↓
修改 Prompt、Skill、模型或 Tool
      ↓
离线评测与灰度发布
      ↓
继续收集新的线上 Trace

数据集应至少包含四类样本：代表正常业务分布的核心集、来自历史故障的回归集、长尾与边界条件集、越权和 Prompt Injection 等安全对抗集。容易出现的数据不一定最重要，高风险低频任务也应保留足够覆盖。

生产 Trace 进入数据集前必须进行敏感信息脱敏、租户隔离和访问控制。正常请求可以按策略采样，但失败、越权、超时和高成本请求通常应提高保留优先级。

11. Grader：谁来给 Agent 打分

确定性 Grader。使用字符串、JSON Schema、数据库状态、单元测试或业务规则评分。可复现、便宜，适合有明确答案和硬约束的任务。

模型 Grader。由另一个模型按照 Rubric 判断正确性、完整性、相关性或风格。适合开放式文本，但结果具有不确定性。

人工评审。适合高风险、主观标准或用于校准模型裁判的样本。成本最高，但不能完全被自动化替代。

生产系统通常组合三者：程序规则先检查硬约束，模型裁判处理语义质量，人工抽检校准模型裁判并处理争议样本。

12. LLM-as-a-Judge 的使用边界

LLM-as-a-Judge 适合没有唯一标准答案的任务，但它不是绝对真值。模型可能偏爱更长的答案、偏爱特定措辞、对自己生成的内容更宽松，也可能被待评测文本中的指令干扰。

使用模型裁判时应：

  • 给出清晰、可分解的 Rubric，而不是只问“答案好不好”。
  • 固定 Judge 模型、Prompt、温度和版本。
  • 优先采用成对比较，必要时随机交换候选答案顺序。
  • 用人工标注集校准一致率、误判率和阈值。
  • 把评分理由和引用证据一并保存，便于审查。
  • 安全、权限和真实状态等硬约束优先使用确定性检查。

13. 非确定性：为什么同一案例要运行多次

模型采样、检索排序、外部 Tool 和并发执行都可能让同一输入产生不同轨迹。只运行一次无法代表真实稳定性。重要案例应重复运行，报告成功率、均值、分位数和波动范围，并记录随机种子、温度和外部依赖快照。

如果产品允许多次尝试，可以报告多次尝试至少成功一次的指标；如果用户要求一次调用就可靠，则应重点看单次成功率。指标必须符合真实产品交互，不能用大量重试掩盖首轮失败。

14. 安全评测

Agent 能够调用外部系统，因此安全评测必须覆盖“模型输出安全”和“实际动作安全”两个层面。建议重点测试：

  • 网页、文档、邮件和 MCP 返回内容中的 Prompt Injection。
  • Tool 白名单、参数范围和资源 ACL 是否能够阻止越权。
  • 是否会访问其他用户或其他租户的数据。
  • 删除、发送、支付等高风险写操作是否要求确认或审批。
  • Trace、日志和评测集是否泄露 Token、Cookie、PII 或商业数据。
  • 失败或超时后是否发生重复写入和不可控重试。

安全失败通常应设置为发布阻断项，而不是与普通质量分数平均。

15. Agent 平台中的评测架构

Agent Runtime
  ├── 模型、RAG、Tool、Memory Span
  └── 最终任务结果
          ↓
Trace Collector → Trace Store
          ↓              ↓
   线上监控与告警     Dataset Builder
                          ↓
                      Eval Runner
                          ↓
            规则 Grader / 模型 Grader / 人工评审
                          ↓
                   报告、对比与发布门禁

关键关联键包括 trace_id、span_id、eval_case_id、eval_run_id 和各类版本号。这样既能从低分样本跳转到对应 Trace，也能从异常 Span 找到它属于哪次评测和哪个版本。

16. 实例：评测“落地成飞书文档”

任务输入是“把当前知识落地成飞书文档”。最终结果评测可以检查页面是否真实存在、标题和父节点是否正确、正文是否包含指定知识点，以及返回链接是否可访问。

轨迹评测可以检查：

  1. 是否先验证个人飞书账号和用户身份。
  2. 是否查询父节点并检查同名页面。
  3. 是否选择语义正确的知识库位置。
  4. 是否只创建一次 Wiki 节点。
  5. 是否在写入后回读层级、目录和区分性关键词。
  6. 是否没有访问企业飞书或其他租户资源。

工程指标还可以统计端到端耗时、飞书 API 调用次数、失败重试次数和单任务成本。这样评测的对象就不只是“文章写得像不像”，而是 Agent 是否正确、安全、稳定地完成了真实任务。

17. 常见错误

  • 只评最终回答：无法发现越权访问、重复写入和错误 Tool 路径。
  • 只看一个总分：安全失败可能被语言质量和速度分数抵消。
  • 评测集全是简单正常样本：线上长尾、故障和攻击输入没有覆盖。
  • 模型裁判没有人工校准：评分漂移后仍被当成真实质量。
  • 不固定版本和环境：无法判断回归来自代码、模型还是外部依赖。
  • 把生产 Trace 原样加入数据集：可能造成隐私泄漏和跨租户数据污染。
  • 过度约束唯一轨迹：把另一条同样正确的执行路线错误判失败。

18. 面试回答模板

Agent Trace 记录一次任务中模型、检索、Tool、状态变化、错误、耗时和成本组成的完整执行链；评测则用数据集和 Grader 判断一个版本的任务成功率、执行轨迹、组件质量、安全性与工程效率。生产中的失败 Trace 可以经过脱敏和标注后沉淀为回归样本，新版本在固定数据集上进行离线评测，通过发布门禁后再灰度上线，并继续从线上 Trace 中发现新问题。这样就形成 Trace、评测、发布和监控的持续质量闭环。
