消息队列：从异步解耦到 Agent 任务调度

一句话结论：消息队列是服务之间传递消息的中间件。生产者把消息发送给 Broker，消费者按照自己的处理能力异步消费，从而实现异步处理、流量削峰、服务解耦和失败重试。

一、从现实中的排队理解消息队列

消息队列类似银行取号：顾客不需要一直占着柜台等待，先取号进入队列；柜台空闲后再处理下一个号码。

顾客取号 → 号码进入等待队列 → 柜台空闲 → 叫下一个号码

在 AI Agent 平台中：

用户提交 Agent 任务
        ↓
     消息队列
        ↓
空闲 Worker 获取任务
        ↓
创建临时容器执行 Agent

二、为什么不能让 API 直接执行 Agent

如果 FastAPI 收到请求后立即创建容器，并一直等待 Agent 执行完成，长任务会占用连接并面临超时。大量任务突然到达时，还可能同时抢占 CPU 和内存。

  • HTTP 请求可能保持数分钟甚至数十分钟。
  • API 连接和进程资源长期占用。
  • 并发任务可能直接压垮单服务器。
  • 失败任务不方便统一重试。
  • API 服务重启可能导致任务状态丢失。

加入消息队列后，FastAPI 只负责创建任务和发布消息，然后立即返回 run_id：

{
  "run_id": "run-1001",
  "status": "queued"
}

Agent 在后台执行，客户端通过轮询、SSE 或 WebSocket 获取进度。

四、消息队列解决的四个核心问题

1. 异步处理

任务提交和任务执行解耦。用户快速获得任务编号，耗时工作在后台运行。

2. 流量削峰

如果服务器最多同时运行两个 Agent，而瞬间收到一百个任务，只启动两个，其余九十八个排队。队列不会提高单个任务速度，但能把突发流量摊平。

3. 服务解耦

FastAPI 不需要知道哪台 Worker 执行任务，也不需要了解 Worker 使用 Docker、gVisor 还是其他沙箱。

4. 失败重试

网络抖动、模型限流或临时资源不足时，可以延迟重试；确定性的参数错误和权限错误则不应重试。

五、消息中应该保存什么

消息应尽量只保存任务标识和少量路由信息：

{
  "message_id": "msg-9001",
  "run_id": "run-1001",
  "tenant_id": "tenant-8",
  "agent_id": "agent-3"
}

完整提示词、文件和长期密钥不应直接进入队列：

  • PostgreSQL 保存任务元数据和权威状态。
  • 对象存储保存大文件和运行制品。
  • 密钥服务或 Tool Gateway 管理敏感凭证。
  • 消息队列只负责传递任务标识和事件。

六、消息从生产到 ACK 的生命周期

ACK 是消费者对 Broker 的确认：消息已经处理成功，可以删除或推进消费位置。通常应先完成业务和结果保存，再发送 ACK。

七、为什么消息可能重复

如果 Worker 完成任务并保存结果后，在发送 ACK 前崩溃，Broker 不知道业务已经成功，便可能重新投递同一条消息。

业务执行成功 → 结果已保存 → ACK 前宕机 → 消息重新投递

因此，“消费者收到同一消息多次”是正常工程场景，不能假设 Broker 永远只投递一次。

八、三种消息投递语义

工程中最常见的目标是：消息至少投递一次，业务效果通过幂等保证只有一次。

九、消费者如何保证幂等

幂等表示同一个操作执行多次，最终结果与执行一次相同。常用方法包括：

  • 为消息设置全局唯一 message_id。
  • 建立消费去重表，并添加唯一约束。
  • 使用业务唯一键，例如订单号或 run_id。
  • 通过数据库状态机阻止重复状态转换。
  • 支付、库存等关键操作使用数据库事务和唯一约束兜底。
UPDATE agent_runs
SET status = 'running'
WHERE id = :run_id
  AND status = 'queued';

如果影响行数为零，说明任务已经被其他 Worker 领取、取消或执行，不应再次运行。

十、消息重试和指数退避

适合重试的错误：

  • 网络超时；
  • 下游服务暂时不可用；
  • 模型 API 限流；
  • 数据库短暂连接失败；
  • 容器节点暂时没有资源。

不适合重试的错误：

  • 参数格式错误；
  • 用户权限不足；
  • Agent 配置不存在；
  • 余额或配额不足；
  • 确定性的业务规则拒绝。
第 1 次失败：5 秒后重试
第 2 次失败：30 秒后重试
第 3 次失败：2 分钟后重试
第 4 次失败：10 分钟后重试

应加入随机抖动，避免大量失败任务在同一时间重新请求下游服务，形成重试风暴。

十一、死信队列

消息超过最大重试次数后，应进入死信队列，而不是无限重试：

正常队列 → 多次失败 → 死信队列 → 人工排查或重新投递

死信记录至少应包含任务 ID、重试次数、最后错误、失败时间和原始消息摘要。

十二、消息顺序

消息队列通常不能保证全局顺序。严格顺序往往需要牺牲并行度。

  • 同一业务实体使用相同 Partition 或 Routing Key。
  • 同一 Key 只由一个有序消费者处理。
  • 通过业务版本号拒绝旧事件。
  • 使用数据库状态机阻止非法转换。

Kafka 只能天然保证同一个 Partition 内有序，不能保证所有 Partition 的全局顺序。

十三、消息积压

如果生产速度大于消费速度，队列长度会不断增加。例如每秒生产 1000 条、只能消费 500 条，每秒将积压 500 条。

常见原因：

  • Worker 数量不足；
  • 单个任务耗时过长；
  • 下游模型或数据库变慢；
  • 大量消息重复重试；
  • 分区数量不足或负载不均；
  • 消费者发生阻塞或故障。

处理方式包括限制生产流量、扩容 Worker、增加分区、优化慢任务、隔离异常消息，以及显示预计等待时间。

十六、Python 中的 Celery + Redis 示例

from celery import Celery

app = Celery(
    "agent_tasks",
    broker="redis://localhost:6379/0",
    backend="redis://localhost:6379/1",
)

@app.task(
    bind=True,
    autoretry_for=(TimeoutError,),
    retry_backoff=True,
    max_retries=3,
)
def run_agent(self, run_id: str):
    execute_agent_run(run_id)
@api.post("/agent-runs")
async def create_agent_run():
    run_id = await save_run_to_database(status="queued")
    run_agent.delay(run_id)
    return {"run_id": run_id, "status": "queued"}

Celery Worker 独立运行，从 Redis 获取任务并调用 run_agent。

十七、数据库与消息发送的一致性

以下流程存在失败窗口：

1. 数据库创建任务成功
2. 向队列发送消息失败
结果：数据库中永久存在 queued 任务，但 Worker 永远收不到

常用解决方案是 Transactional Outbox：

  1. 在同一个数据库事务中写入 agent_runs 和 outbox_events。
  2. 独立发布器扫描未发布的 Outbox 事件。
  3. 将事件发送到消息队列。
  4. 发布成功后标记事件已发布。

发布器崩溃后可以继续扫描。事件可能重复发布，因此消费者仍需幂等。

十八、Agent Run 状态机

created
   ↓
queued
   ↓
running
   ├── succeeded
   ├── failed
   ├── cancelled
   └── timed_out

推荐字段：

  • id、tenant_id、user_id、agent_id；
  • status、priority、retry_count；
  • queued_at、started_at、finished_at；
  • heartbeat_at、error_code、result_location。

还需要全局和租户并发上限、任务超时、心跳、Worker 失联回收、最大重试次数、死信处理、用户取消和审计日志。

十九、面试回答模板

消息队列是一种异步通信中间件，由生产者、Broker 和消费者组成，主要用于异步处理、服务解耦、流量削峰和失败重试。使用消息队列时需要重点考虑消息丢失、重复消费、幂等、顺序性、消息积压、重试和死信队列。工程中通常采用至少一次投递，并通过数据库唯一约束、状态机或去重表保证业务幂等。数据库写入与消息发送的一致性可以使用 Transactional Outbox 解决。

二十、针对当前 Agent 平台的结论

MVP：FastAPI + PostgreSQL + Redis + Celery/Dramatiq + 临时 Agent 容器。

可靠性底线：任务状态持久化、幂等领取、成功后 ACK、有限重试、死信队列、心跳回收和租户并发配额。

演进路径：任务可靠路由需求提高时引入 RabbitMQ；大规模执行事件流和多消费者分析时引入 Kafka。
