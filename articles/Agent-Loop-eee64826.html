Agent Loop：智能体如何持续决策并完成任务

核心结论：Agent Loop 是智能体的执行主干。运行时把目标和当前状态交给模型，模型决定调用工具、请求人工介入、移交其他 Agent 或生成最终答案；工具结果随后回到上下文中，驱动下一轮决策。

1. Agent Loop 是什么

普通聊天模型通常完成一次“输入—生成—结束”。Agent 面对复杂目标时，往往无法一次得到最终答案，需要根据真实执行结果持续调整下一步行动。这个反复进行“决策—执行—观察—更新状态”的过程，就是 Agent Loop。

用户目标
  ↓
读取上下文与当前状态
  ↓
模型判断下一步行动
  ├─ 生成最终答案 → 结束
  ├─ 请求用户输入 → 暂停
  ├─ 请求人工审批 → 暂停
  ├─ 移交其他 Agent → 切换执行者
  └─ 调用工具 → 执行工具 → 观察结果 → 更新状态 → 下一轮

因此，Agent 并不只是一个更强的语言模型。一个完整 Agent 系统通常由模型、工具、上下文、状态、循环控制器、安全策略和可观测性共同组成。

2. 一个完整例子：天气与日历提醒

假设用户提出：“查询北京明天的天气，如果下雨，就在日历中创建一个带伞提醒。”这不是单次文本生成任务，因为模型必须先知道天气，才能决定是否创建日程。

第一轮：模型识别出缺少天气信息，产生 get_weather(city="北京", date="明天") 工具调用。

执行与观察：运行时校验参数、执行天气工具，获得“北京明天有小雨”。工具结果被追加到当前运行上下文。

第二轮：模型根据“小雨”判断条件成立，产生 create_calendar_event(title="出门记得带伞", time="明天 08:00")。

再次执行与观察：日历工具返回创建成功及事件 ID。运行时把结果交回模型。

第三轮：模型确认用户目标已经完成，输出最终答复：“北京明天有小雨，我已经创建了明早 8 点的带伞提醒。”

同一次用户请求触发了多次模型调用和多次状态更新，但它们共同属于一次逻辑上的 Agent Run。

3. Agent Loop 的六个核心部分

3.1 Goal：目标

目标描述最终要达到的结果，例如“分析订单服务最近变慢的原因并生成报告”。它通常不是一个固定函数能直接解决的问题，因此模型需要决定查询哪些指标、是否查看日志和 Trace、何时信息已经足够，以及最终输出应采用什么形式。

3.2 Context：上下文

上下文是模型在当前一轮能够看到的信息，一般包括系统指令、用户目标、对话历史、已经完成的步骤、工具调用与返回结果、当前任务状态、可用工具、权限、预算和安全约束。上下文不等于数据库中的全部信息，而是运行时为本轮模型调用选择并组装的输入。

上下文过少会造成决策缺乏依据；上下文过多则会增加成本、延迟和干扰。因此生产系统还需要裁剪、摘要、检索和优先级控制。

3.2.1 State 与 Memory 的边界

State（运行状态）回答“这一次任务进行到哪里了”，例如 run_id、当前步骤、已调用工具、观察结果、待审批动作、剩余预算和任务状态。它属于当前 Agent Run，任务完成后可以归档。

Memory（记忆）回答“过去有哪些信息值得在未来再次使用”，例如用户偏好、稳定事实、历史任务经验和可复用结论。它可以跨会话、跨任务存在，但不应把所有历史内容无差别塞进每轮提示词。

二者的关系是：State 负责保存当前进度，Memory 为当前决策提供经过检索的历史信息。生产系统通常用数据库或状态存储持久化 State，用向量检索、结构化数据库或摘要存储管理 Memory，再由 Context Builder 选择本轮真正需要的内容。

3.2.2 上下文增长与压缩

Agent 每执行一轮，模型消息、工具参数和 Observation 都会增加。如果把全部历史永久保留，上下文会越来越长，带来更高延迟、Token 成本和注意力干扰。

  • 保留：系统约束、当前目标、最近决策、未解决问题、关键证据和待执行动作。
  • 压缩：把较早的过程总结成结构化摘要，同时保留原始 Trace 的引用。
  • 检索：只按当前步骤召回相关 Memory、文档片段和工具结果。
  • 丢弃：重复内容、无关日志、已被新结果取代的中间信息和敏感原文。

因此，Context 不是 State 与 Memory 的简单拼接，而是运行时为“下一次模型调用”制作的一份受预算约束的工作集。

3.3 Decision：决策

每一轮模型通常需要在几种行为中选择：调用工具、生成最终答案、请求用户补充信息、请求人工审批、移交其他 Agent，或者因安全与权限原因停止。模型只产生结构化的行动请求，并不直接操作数据库、云服务器或日历。

{
  "name": "query_database",
  "arguments": {
    "sql": "SELECT status, COUNT(*) FROM orders GROUP BY status"
  }
}

3.4 Action：执行

Agent Runtime 根据工具名称找到对应 Python 函数，并在真正执行之前完成参数校验、身份鉴别、权限判断、租户隔离、限流、超时控制和必要的人工审批。模型提出调用不代表系统必须无条件执行。

3.5 Observation：观察

工具返回值就是 Observation。它应使用稳定、结构化、可区分成功与失败的格式。模型根据观察结果判断任务是否完成、是否需要继续查询、是否需要换一种方法或者是否应向用户说明失败。

{
  "success": true,
  "data": {
    "pending_orders": 428,
    "failed_orders": 17
  },
  "error": null
}

3.6 Termination：结束

循环必须具备明确结束条件。正常结束是模型生成了满足输出约束的最终答案；异常结束则可能来自最大轮数、整体超时、费用上限、连续工具失败、安全规则、用户取消或需要人工介入。没有这些边界，Agent 可能陷入重复查询或无限重试。

4. Python：实现一个最小 Agent Loop

下面的代码省略了具体模型 SDK，但保留了最重要的控制逻辑。关键点是：工具结果必须以对应的 tool_call_id 重新加入消息上下文，再进入下一轮模型调用。

MAX_TURNS = 8


def run_agent(user_input: str) -> str:
    messages = [
        {
            "role": "system",
            "content": "你是一个可以使用受控工具完成任务的助手。",
        },
        {"role": "user", "content": user_input},
    ]

    for turn in range(MAX_TURNS):
        response = call_llm(
            messages=messages,
            tools=TOOL_SCHEMAS,
        )

        messages.append(response.message)

        if response.final_answer is not None:
            return response.final_answer

        for tool_call in response.tool_calls:
            try:
                arguments = validate_arguments(
                    tool_call.name,
                    tool_call.arguments,
                )
                authorize_tool_call(
                    tool_name=tool_call.name,
                    arguments=arguments,
                )
                result = execute_tool(
                    name=tool_call.name,
                    arguments=arguments,
                )
                tool_output = {
                    "success": True,
                    "data": result,
                }
            except Exception as error:
                tool_output = {
                    "success": False,
                    "error": classify_error(error),
                }

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": serialize(tool_output),
            })

    raise RuntimeError("Agent 超过最大执行轮数")

只有 Function Calling 而没有后续循环时，模型只是提出了一次函数调用。运行时执行工具、把结果反馈给模型并继续决策之后，才形成完整 Agent Loop。

5. Agent Loop 是一个状态机

代码上它经常表现为 for 或 while，但更准确的理解是有限状态机。每次事件都会推动任务从一个状态迁移到另一个状态。

当前状态

事件

下一状态

说明

RUNNING

产生工具调用

RUNNING

执行工具并继续循环

RUNNING

产生最终输出

COMPLETED

任务正常完成

RUNNING

需要审批

PAUSED

保存状态并等待审批

RUNNING

缺少用户信息

WAITING

向用户提问并暂停

RUNNING

可恢复错误

RUNNING

按策略重试或更换方案

RUNNING

不可恢复错误

FAILED

记录原因并停止

RUNNING

超过限制

FAILED

防止无限循环和成本失控

状态至少应包含运行 ID、用户和租户、消息历史、轮数、工具错误次数、任务状态、最终输出、预算以及待审批动作。长任务还需要将状态持久化，使进程重启后能够恢复。

5.1 Checkpoint、崩溃恢复与副作用一致性

长任务不应只把状态放在进程内存中。运行时可以在模型决策后、工具执行前后以及进入审批状态时保存 Checkpoint，记录状态版本、已完成动作、待执行动作和关键 Observation。

加载最近一次 Checkpoint
  ↓
核对状态版本、权限与外部资源现状
  ↓
确认上一次副作用工具是否已经成功
  ├─ 已成功：复用结果，继续下一步
  ├─ 未执行：安全执行
  └─ 状态未知：按幂等键查询或人工处理

Checkpoint 只能保证“恢复内部状态”，不能自动保证外部系统的 exactly-once。假如创建订单后进程崩溃，恢复时必须依靠幂等键、状态查询、去重表或补偿操作判断订单是否已经创建，不能直接重放。

5.2 并发运行中的状态隔离

多个用户或多个 Agent Run 并发执行时，不能把当前用户、租户和任务状态放在共享全局变量中。业务状态应按 run_id 与 tenant_id 隔离并持久化；Python 异步服务可用 ContextVar 传播请求级的 Trace ID、用户 ID 等轻量上下文，但数据库连接、任务进度和长期状态仍应由显式参数或持久化存储管理。

这样可以避免一个协程读取到另一个任务的身份或状态，也便于暂停、恢复和水平扩展。

6. 工具失败、重试与幂等

工具失败不能统一处理。网络超时、临时限流等通常可以退避重试；参数错误、权限不足和资源不存在通常不应原样重试，而应修正参数、请求授权或向用户说明。模型可以参与选择替代方案，但重试次数、时间和高风险操作规则应由确定性代码控制。

付款、创建订单、发送消息、删除资源等带副作用的工具不能因超时而盲目重试。超时只说明客户端没有拿到结果，并不能证明服务端没有执行。此时应先使用业务请求 ID 查询真实状态，并为写操作设置幂等键。

result = create_order(
    user_id="user_123",
    product_id="product_456",
    idempotency_key="run_789-create-order",
)

同一个逻辑动作重复提交相同幂等键时，服务端应返回第一次执行结果，而不是再次创建资源。

6.1 重复动作检测与 SAFE_STOP

除了最大轮数，运行时还应识别“没有取得新进展”的循环。例如模型连续三次调用同一个工具、参数相同且返回结果相同，继续执行通常不会带来新信息。

可以为每次动作计算 action_fingerprint，同时比较新增证据、状态变化和错误类型。当重复动作达到阈值、连续多轮没有新证据或同类错误无法恢复时，运行时进入 SAFE_STOP：停止继续调用工具，保存现场，并向用户说明已经完成的步骤、阻塞原因和需要的下一项输入。

6.2 Evidence Gate：不要只听模型说“完成了”

模型输出“任务已完成”只是一个候选结论。对于代码修改、文件生成、数据库写入或线上变更，运行时应设置独立的 Evidence Gate，用外部证据决定是否真正结束。

  • 代码任务：测试、静态检查、构建结果和目标文件差异。
  • 文档任务：真实文档链接、目录位置、回读到的标题与关键术语。
  • 数据任务：查询结果、影响行数、版本号和业务约束。
  • 部署任务：健康检查、请求响应、日志和监控指标。
decision = model.decide(context)

if decision.type == "final":
    evidence = verifier.check(goal, state)
    if evidence.passed:
        return FinalAnswer(decision.text, evidence=evidence)
    state.observations.append(evidence.failure_reason)
    continue

这使“完成”从语言判断变成可验证状态，也是可靠 Agent 与演示型 Agent 的关键区别。

7. 人工审批与暂停恢复

Agent 自主执行不等于无限权限。只读查询通常可以自动进行；可恢复的普通写操作可以在授权范围内执行并记录 Trace；支付、删除、生产环境变更和对外发送等高风险动作应进入人工审批。

if tool_call.name in HIGH_RISK_TOOLS:
    state.status = "PAUSED"
    state.pending_action = tool_call
    save_state(state)
    return ApprovalRequest(tool_call)

审批通过后应从已保存状态继续，而不是从头重跑整个任务。恢复时还要重新检查权限、资源版本和参数时效，避免用户批准的是旧状态下的操作。

固定退款流程更适合 Workflow，因为每一步都有明确业务规则；分析服务性能问题可能需要动态选择监控、日志、Trace、数据库或部署记录，更适合 Agent Loop。生产系统通常采用混合架构：确定性 Workflow 管住关键流程，只在需要判断的节点调用 Agent。

8.1 推荐架构：确定性外层 + 动态内层

确定性 Workflow
├─ 初始化任务、身份与权限
├─ 准备数据和隔离环境
├─ Agent Loop：动态诊断、检索与修改
├─ Evidence Gate：测试、规则与外部状态验证
└─ 发布、归档或请求人工介入

Workflow 固定关键阶段、安全边界和发布条件；Agent Loop 只处理路径无法预先穷举的部分。这样既保留模型的探索能力，也让高风险动作、成本和验收标准保持可控。

判断是否应该使用 Agent Loop 的简单标准是：如果下一步能在编码前明确写成稳定流程，就优先使用 Workflow；如果下一步必须根据未知的 Observation 动态选择，才让模型参与决策。

9. Agent Loop 与 Tool Calling、State、Trace 的关系

Tool Calling 是循环中的动作接口，解决“模型如何请求外部能力”；State 保存循环已经进行到哪里；Agent Loop 负责推动任务继续运行；Trace 则记录每一轮模型调用、工具执行、错误和状态变化。

Trace：分析订单服务故障
├─ Span：模型决定查询监控指标
├─ Span：执行 get_metrics
├─ Span：模型决定查询错误日志
├─ Span：执行 search_logs
├─ Span：模型判断数据库连接池不足
└─ Span：生成最终报告

Trace 用于回答“发生了什么、在哪一步失败、耗时和成本是多少”，不应保存或展示模型的私有思维链。生产记录应对完整提示词、凭证、Authorization Header、个人信息和原始工具结果进行脱敏或限制采集。

9.1 Trace 指标与 Agent 评测

单条 Trace 用于解释一次任务为什么成功或失败；聚合指标用于判断系统整体是否可靠。每个 Step 建议记录 trace_id、run_id、模型与版本、决策类型、工具名称、规范化参数、Observation 摘要、状态变化、耗时、Token、费用、重试次数和停止原因。

  • 效果：经 Evidence Gate 验证的任务成功率、工具选择准确率、人工验收通过率。
  • 效率：平均循环步数、P50/P95 延迟、Token 与费用、重复调用率。
  • 稳定性：工具错误率、自动恢复率、卡死率、人工介入率。
  • 安全性：越权请求数、高风险动作拦截率、敏感信息泄漏事件。

评测应使用固定任务集、可重复环境和明确验收规则。若只统计“模型给出了 final”，会把过早结束和幻觉也误判为成功。

10. 并行工具调用

如果多个工具彼此独立，例如同时查询 CPU、内存和数据库连接池，可以并行执行以降低总延迟。但如果第二个工具依赖第一个结果，则必须串行。运行时还需要限制并发数，避免模型一次产生大量调用压垮下游服务。

results = await asyncio.gather(
    get_cpu_metrics(service_id),
    get_memory_metrics(service_id),
    get_db_pool_metrics(service_id),
)

并行执行完成后，应按 tool_call_id 将每个结果与原调用准确关联，再一起反馈给模型。

11. 项目化案例：RepoPilot 与 AI4S

11.1 RepoPilot 类代码智能体

代码修复任务适合由确定性外层 Workflow 管理仓库准备、隔离环境、验收和发布，在“诊断—修改”阶段运行 Agent Loop。

接收 Issue 并建立基线
  ↓
搜索代码 → 形成故障假设 → 读取调用链
  ↓
修改文件 → 运行测试 → 观察失败或成功
  ↓
继续诊断，或进入 Evidence Gate
  ↓
测试 + 静态检查 + 差异审查通过后才允许结束

State 可以保存已搜索关键词、已读文件、当前假设、修改文件、测试结果、未解决错误和剩余预算。创建分支、提交代码、推送或创建 PR 都是有副作用的动作，应使用幂等键、权限检查和明确的发布策略。不能只凭模型说“已修复”就发布。

11.2 AnewScience / AI4S 型科研智能体

科研 Agent 可以围绕“生成候选—调用数据库或模拟器—获得计算结果—按领域约束筛选—更新假设”运行。LLM 适合负责任务规划、工具编排、假设生成和结果摘要；数值正确性、物理化学约束、数据质量和可复现性必须由领域工具、规则或专家复核。

State 应记录候选集合、数据与模型版本、参数、随机种子、计算任务 ID、已完成结果、不确定性和待验证假设。昂贵计算通常先返回 job_id，Agent 保存 Checkpoint 并进入 WAITING_TOOL，再由轮询、Webhook 或消息总线唤醒下一轮。

科研场景的 Evidence Gate 应检查计算是否完成、约束是否满足、结果能否复现和证据来源是否完整。预测结果不等于科学发现，单次模拟成功也不等于实验验证。

13. 常见错误认识

误区一：Agent Loop 就是一个 while 循环。while 只是代码形式，真正难点是状态、边界、权限、错误恢复和可观测性。

误区二：模型可以直接执行工具。模型只提出调用意图，真实执行必须由受控运行时完成。

误区三：工具失败就让模型无限重试。重试策略应由确定性代码限制，并区分副作用操作。

误区四：步骤越多越智能。更多轮次意味着更高的延迟、成本和出错概率；能用确定性 Workflow 解决的问题不必强行 Agent 化。

误区五：把所有历史消息都塞进模型。上下文窗口有限，生产系统需要摘要、检索、裁剪和重要性排序。

14. 60 秒面试回答

Agent Loop 是智能体完成复杂任务的核心执行机制。运行时把用户目标和当前上下文传给模型，模型决定生成最终答案、调用工具、请求人工介入或移交其他 Agent。如果模型调用工具，运行时负责参数校验、权限检查和真实执行，再把工具结果追加到上下文中重新调用模型，直到任务完成。生产环境还需要最大轮数、超时、分类重试、幂等、状态持久化、人工审批和 Trace，以防止无限循环、重复执行和越权操作。

15. 自测与小练习

请尝试设计一个“自动处理 GitHub Issue”的 Agent Loop，并回答：

  1. Goal 与可验证的成功标准分别是什么？
  2. State 至少需要保存哪些字段？State、Memory 与 Context 如何区分？
  3. 模型可以返回哪些 Decision？哪些决定必须由 Runtime 控制？
  4. 哪些工具具有副作用，如何防止重复提交或重复创建 PR？
  5. Evidence Gate 应检查测试、静态检查和代码差异中的哪些证据？
  6. 如何识别重复动作、连续无新证据和不可恢复错误？
  7. 如果测试需要十分钟，怎样用 job_id、Checkpoint 与 WAITING_TOOL 暂停并恢复？

参考方向：外层使用确定性 Workflow；诊断与修改阶段使用 Agent Loop；写操作使用幂等键；由测试、静态检查和差异审查构成 Evidence Gate；预算耗尽、权限不足或连续无新证据时进入 SAFE_STOP。
