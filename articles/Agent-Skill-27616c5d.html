Agent Skill：可复用工作流、渐进式加载与权限边界

本文讨论的 Skill，是以 SKILL.md 为核心的 Agent Skill：它把完成一类任务所需的指令、参考资料、模板和可选脚本组织成一个可复用工作流。不同 Agent 平台的字段和目录可能不同，但“按任务触发、按需加载、调用现有工具、接受运行时权限控制”的思想是相通的。

最重要的边界：Skill 教 Agent“怎样完成任务”，Tool 让 Agent“能够执行动作”。Skill 可以声明自己依赖哪些 Tool 或 MCP 服务，但不能因此获得 OAuth、文件系统、网络、业务数据或高风险操作权限。

1. 一句话理解 Skill

如果 Tool 是一把扳手，那么 Skill 就是一份经过验证的维修手册。扳手提供拧螺丝的能力；维修手册规定先检查什么、按什么顺序拆装、什么时候停止、出现异常如何处理，以及最后怎样验收。

因此，Skill 不是单次 Prompt 的华丽包装，也不是新的模型能力。它是一种面向特定任务的工程化工作流：同类任务再次出现时，Agent 不必临时重新规划全部步骤，而是加载已经沉淀好的操作规范。

3. Skill 解决什么工程问题

只靠临时 Prompt，模型每次都可能以不同顺序完成任务：有时漏掉前置检查，有时忘记验证结果，有时在失败后继续写入。Skill 把容易遗忘、需要重复执行的专业步骤固定下来，使任务从“模型临场发挥”变成“模型按照可审查的流程行动”。

一致性。同类请求采用相同的前置条件、执行顺序、异常处理和验收标准。

专业知识复用。团队成员可以把领域规则、术语、模板和经验沉淀到 Skill 中，而不必要求每位用户都写出完整 Prompt。

上下文节省。Host 先只保留 Skill 的名称和描述；真正需要时才加载完整指令和参考资料，避免所有操作手册同时占满上下文。

可维护与可测试。Skill 是文件化、可版本管理的资产，可以评审、回归测试和逐步改进。

4. 一个 Skill 的目录结构

my-skill/
├── SKILL.md              必需：元数据与执行指令
├── scripts/              可选：确定性脚本
├── references/           可选：规范、示例和领域资料
├── assets/               可选：模板、图片和其他资源
└── agents/
    └── openai.yaml       可选：界面信息、调用策略和依赖声明

SKILL.md 是入口文件。简单 Skill 可以只有这一份文件；当正文开始混入大量 API 说明、模板或长篇知识时，应把它们拆到 references/ 或 assets/，在执行到对应步骤时再读取。需要稳定计算、格式校验或重复机械操作时，可以把确定性逻辑放进 scripts/。

5. SKILL.md 的元数据与正文

在 OpenAI 的 Skill 约定中，SKILL.md 至少包含 name 和 description。名称用于标识 Skill；描述既说明用途，也承担触发匹配的职责，所以应明确写出“什么时候使用”和“什么时候不使用”。

---
name: lark-knowledge-author
description: Create or update Feishu Wiki articles when the user asks to land learning notes as a Feishu document. Do not use for chat messages or mail.
---

1. Verify the active user identity and target knowledge base.
2. Check for a same-title page before creating anything.
3. Choose the semantically correct parent node.
4. Write the article with the required document format.
5. Read back placement, outline, and key terms.
6. Report the verified document URL.

正文不应只写模糊目标，例如“帮用户创建高质量文档”。更可执行的写法会明确输入、输出、顺序、停止条件、失败处理和验证证据。模型仍然可以在步骤内部做判断，但关键边界不能依赖临场猜测。

6. 显式触发与隐式触发

显式触发是用户直接指定 Skill。以 OpenAI 当前产品为例，ChatGPT 可以通过 @ 选择 Skill，Codex CLI 或 IDE 扩展可以通过 /skills 或 $ 提及 Skill。显式触发适合用户已经知道要采用哪套流程的场景。

隐式触发是 Host 根据用户任务与 Skill 的 description 自动匹配。它降低了使用门槛，但也要求描述具有清晰边界。描述太宽会误触发，太抽象又可能永远匹配不到。

如果某个 Skill 涉及敏感操作、只适合专家主动调用，或隐式触发风险较高，可以在 agents/openai.yaml 中关闭隐式调用：

policy:
  allow_implicit_invocation: false

关闭隐式调用只改变“怎样选中 Skill”，不会改变 Tool 权限，也不会绕过审批。

7. Progressive Disclosure：为什么先只加载描述

Progressive Disclosure 通常翻译为“渐进式披露”或“渐进式加载”。核心思想是：先给模型最少但足够用于选择的信息，确定需要某个 Skill 后，再加载它的完整工作流；执行到具体步骤时，才读取对应参考资料、脚本或模板。

  1. 启动阶段：Host 向模型提供 Skill 的名称和描述。
  2. 选择阶段：用户显式指定，或模型根据描述匹配到 Skill。
  3. 加载阶段：Host 读取完整 SKILL.md。
  4. 执行阶段：按照指令，只读取当前需要的 references/、scripts/ 和 assets/。

这种设计同时解决两个问题：既让系统能够安装大量专业 Skill，又避免把每份完整操作手册永久塞进模型上下文。工程上也意味着描述必须短而准确，长知识应放到按需资源中。

8. Skill 的完整执行生命周期

  1. 发现：Host 扫描可用 Skill，并读取元数据。
  2. 匹配：根据显式选择或任务语义确定候选 Skill。
  3. 加载：读取 SKILL.md，确认适用范围、步骤和依赖。
  4. 准备：检查输入、身份、目标资源、所需 Tool 与权限。
  5. 执行：Agent Loop 按步骤调用 Tool、脚本或参考资料。
  6. 观察：把 Tool 结果写回状态，判断重试、改道、审批或停止。
  7. 验证：使用独立读操作核对产物，而不是只相信写接口返回成功。
  8. 交付：向用户报告结果、证据和仍未完成的部分。

Skill 只是为这个生命周期提供可复用规则；真正维护状态、循环执行和决定何时终止的，仍是 Agent Runtime 与 Agent Loop。

9. Skill 与 Prompt、Memory、Context、RAG 的区别

概念

主要保存什么

生命周期

与 Skill 的关键区别

Prompt

本次交互中的指令或问题

通常面向当前请求

Skill 是可复用、可版本化的工作流包；被加载后，其指令也会进入上下文

Memory

历史事实、偏好和过去决策

跨会话或长期

Memory 更像“以前发生了什么”，Skill 更像“这类事应该怎样做”

Context

模型当前能看到的全部信息

当前推理窗口

Skill 是上下文的潜在来源之一，不等于上下文本身

RAG

按查询检索出的知识片段

按请求动态获取

RAG 主要回答“相关知识是什么”，Skill 主要规定“任务按什么流程完成”

它们可以组合使用。例如，一个客服 Skill 规定处理投诉的步骤，RAG 检索退款政策，Memory 提供用户的历史订单，Prompt 给出本次投诉内容，最终所有必要信息共同进入 Context。

10. Skill 不等于权限

Skill 文件本质上是可读的工作流和资源。即使其中写着“删除数据库”“读取邮箱”或“调用生产环境工具”，也不代表这些动作被授权。Host 与运行时必须在每次执行前独立检查能力和权限。

Skill 请求使用某个 Tool
  ↓
Host 检查该 Tool 是否已安装并向当前 Agent 暴露
  ↓
检查 Agent Tool 白名单与租户策略
  ↓
检查用户身份、OAuth Scope 与目标资源 ACL
  ↓
必要时进行人工审批或风险确认
  ↓
执行，并记录审计日志

这也是为什么不能把第三方 Skill 当成普通文本随意信任。Skill 可能引导 Agent 读取文件、访问网络或执行脚本；安全系统应限制其可用 Tool、运行环境和数据范围，并对写入、转账、删除等高风险动作设置额外门槛。

11. Tool 依赖与 Agent 白名单

agents/openai.yaml 可以声明某个 Skill 依赖的工具，例如一个 MCP 服务。这个声明的作用是帮助 Host 识别和准备依赖，不是自动安装、自动登录或自动授权。

dependencies:
  tools:
    - type: mcp
      value: openaiDeveloperDocs
      description: OpenAI Docs MCP server
      transport: streamable_http
      url: https://developers.openai.com/mcp

运行时仍应取交集：Skill 需要的 Tool ∩ Host 已暴露的 Tool ∩ Agent 白名单 ∩ 当前用户权限。只有落在交集中的能力才可以执行。Skill 不能修改这几个集合，也不能用提示词要求模型绕过它们。

12. 实例：把“落地成飞书文档”做成 Skill

假设用户在学习对话结束后说“落地成飞书文档”。Tool 只提供创建、写入、查询等原子能力；真正决定完整质量的，是一套可复用的文档落地流程。

  1. 确认当前使用的是个人飞书身份，避免跨账号或跨租户写入。
  2. 定位目标知识库和语义最合适的父页面，不根据浏览器当前页面盲目推断。
  3. 列出父页面的现有子节点，检查同名文档，保证操作具有幂等性。
  4. 根据本次对话整理连贯大纲，并生成符合飞书文档格式的正文。
  5. 调用 Wiki 与文档 Tool 创建节点、写入正文。
  6. 重新查询父节点，验证页面层级和标题。
  7. 回读目录与多个区分性关键词，验证正文不是空页、错页或只写入了部分内容。
  8. 向用户交付真实 Wiki 链接和已验证范围。

在这个例子中，Skill 规定操作规范；Wiki/文档 Tool 完成读写；CLI 或 MCP 负责连接外部系统；OAuth 和文档 ACL 决定是否有权写入；Agent Loop 负责在每一步结果返回后继续推进。

13. 好 Skill 的设计原则

一个 Skill 聚焦一类工作。不要把代码审查、发邮件、部署和报销审批塞进同一套工作流。边界越清楚，触发越准确，维护越容易。

描述先写触发场景，再写边界。使用具体任务词和对象词，并明确不适用的相邻场景。描述是路由信息，不是宣传语。

步骤写成可执行指令。明确输入、输出、顺序、分支、停止条件和验证方式。对于不可逆操作，还应写明审批和回滚策略。

优先用指令，必要时才用脚本。需要理解语义、适应上下文的部分交给模型；格式校验、哈希计算、批量转换等必须稳定复现的部分适合脚本。

把长知识按需拆出。SKILL.md 保留导航和决策规则，详细 API、样例与模板放进对应目录，并明确何时读取。

把验证当作工作流的一部分。“接口返回成功”不等于用户目标已经实现。创建文档后要读回，修改代码后要测试，发送消息后要核对收件人和内容。

14. 常见错误

  • 描述过于宽泛：“处理所有开发任务”会导致误触发，也无法表达边界。
  • 把整本手册塞进 SKILL.md：每次加载都浪费上下文，还让关键步骤难以发现。
  • 把 Skill 当成 Tool：只有指令，没有可执行能力，最终仍无法访问外部系统。
  • 把依赖声明当成授权：声明需要 MCP 服务，不代表用户已登录或拥有目标资源权限。
  • 只写正常路径：未定义重试、幂等、审批、失败退出和回滚，会在真实环境中产生副作用。
  • 相信执行器的成功提示：缺少独立读回与验收，容易交付空文档、错目录或不完整结果。
  • 脚本无限制继承权限：脚本仍应运行在受控文件系统、网络和凭据边界内。

15. 面试回答模板

Skill 是面向特定任务的可复用工作流包。它通常通过 SKILL.md 描述触发条件、执行步骤和验证方式，并可附带参考资料、模板与确定性脚本。Host 先根据名称和描述选择 Skill，再按需加载完整指令，这叫渐进式披露。Skill 负责教 Agent 如何组合能力，但不会直接授予外部权限；真正的执行仍由 Tool 完成，并受 Tool 白名单、OAuth、资源 ACL、审批和沙箱控制。MCP 解决工具如何被统一发现和调用，Agent Loop 负责持续执行与观察，Plugin 则用于打包和分发 Skill 及连接器。
