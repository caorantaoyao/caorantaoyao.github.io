Agent State 与 Memory：智能体如何保存进度、会话与长期记忆

核心结论：State 让 Agent 知道“当前任务做到哪里”，Session 让它知道“这次会话聊过什么”，Long-term Memory 让它知道“过去有哪些信息值得未来继续使用”，Context 决定“这一轮模型实际能够看到什么”。

1. 为什么 Agent 需要状态与记忆

Agent Loop 解决的是如何持续决定下一步，但循环要可靠运行，还必须知道已经完成了哪些步骤、当前是否在等待审批、工具是否执行成功、用户之前说过什么，以及哪些历史信息值得在未来任务中复用。如果这些信息只保存在 Python 进程内存中，服务重启、任务暂停或用户开启新会话后就会丢失。

一个成熟的 Agent 平台需要同时管理执行状态、会话历史、长期记忆和模型上下文。它们都可能被保存，但生命周期、查询方式和用途不同，不能混成一个概念。

2. 四个核心概念

持久化存储
├─ Run State：当前任务进行到哪里
├─ Session Memory：当前会话之前聊了什么
└─ Long-term Memory：跨会话仍有价值的信息
                  ↓ 检索与筛选
LLM Context：这一轮真正发送给模型的内容

2.1 Run State：运行状态

Run State 是一次任务的执行快照，通常包含运行 ID、用户与租户、当前步骤、循环轮数、已经完成的工具调用、错误次数、待审批动作、预算和最终输出。它服务于 Agent Loop 推进、暂停恢复、故障重试与并发控制。

2.2 Session Memory：会话记忆

Session Memory 保存同一会话中的消息历史。例如用户先说“我的主要开发语言是 Python”，下一轮再问“我主要使用什么语言”，运行时会取出相同 Session 的历史并放进模型上下文，模型才能回答 Python。

2.3 Long-term Memory：长期记忆

长期记忆保存跨会话仍然有价值的信息，例如用户偏好、项目技术栈、长期目标、历史任务结果和从失败中总结的经验。用户即使新建会话，Agent 仍可以根据身份与当前问题检索这些记忆。

2.4 LLM Context：模型上下文

Context 是当前一轮真正发送给模型的信息。数据库里保存了信息，并不代表模型自动知道；运行时必须完成存储、检索、筛选和上下文组装。还要区分本地 Context 与 LLM Context：用户 ID、数据库连接和权限对象可以只供 Python 代码使用，不应默认发送给模型。

4. Python：定义 Run State

from datetime import datetime
from typing import Any, Literal

from pydantic import BaseModel, Field


class PendingAction(BaseModel):
    tool_call_id: str
    tool_name: str
    arguments: dict[str, Any]
    idempotency_key: str


class AgentRunState(BaseModel):
    run_id: str
    tenant_id: str
    user_id: str
    session_id: str

    status: Literal[
        "running",
        "waiting_user",
        "waiting_approval",
        "completed",
        "failed",
        "cancelled",
    ] = "running"

    current_step: str | None = None
    turn_count: int = 0
    tool_error_count: int = 0
    completed_tool_calls: list[str] = Field(default_factory=list)
    pending_action: PendingAction | None = None
    final_output: str | None = None
    version: int = 1
    updated_at: datetime

version 可以用于乐观锁，防止两个 Worker 同时恢复和修改同一个任务。State 中不要直接保存数据库连接、客户端对象或密钥；恢复时应通过依赖注入重新构造这些运行资源。

5. Checkpoint：为什么任务可以暂停后继续

假设退款 Agent 的流程是“查询订单—检查规则—等待人工批准—执行退款—通知用户”。进入人工审批后，原来的 HTTP 请求早已结束，服务甚至可能在第二天重启。因此系统必须把关键步骤保存成 Checkpoint。

{
  "run_id": "run_001",
  "status": "waiting_approval",
  "current_step": "refund_order",
  "order_id": "order_123",
  "pending_tool_call_id": "call_456",
  "approval_status": "pending",
  "version": 7
}

审批通过后，运行时读取 Checkpoint，校验版本，重新检查权限与订单当前状态，然后继续执行。恢复任务不能简单地从头重跑，否则可能重复发送消息、创建订单或扣款。

6. Session Memory：保存多轮会话

最直接的方案是以 tenant_id + user_id + session_id 为范围保存消息。用户可能同时拥有多个会话，因此不能把 user_id 直接当作 session_id。

CREATE TABLE conversation_messages (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT NOT NULL,
    user_id     TEXT NOT NULL,
    session_id  TEXT NOT NULL,
    role        TEXT NOT NULL,
    content     JSONB NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_messages_session
ON conversation_messages (
    tenant_id,
    user_id,
    session_id,
    created_at
);

读取时通常只取最近若干条消息，再结合较早历史的摘要，避免把全部历史无限塞进模型。

7. Python：使用 Session 保存会话

from agents import Agent, Runner, SQLiteSession


agent = Agent(
    name="Recruitment Assistant",
    instructions="帮助用户准备计算机秋招。",
)

session = SQLiteSession(
    "tenant_a:user_123:session_001",
    "agent_sessions.db",
)

await Runner.run(
    agent,
    "我的主要开发语言是 Python。",
    session=session,
)

result = await Runner.run(
    agent,
    "我的主要开发语言是什么？",
    session=session,
)

print(result.final_output)

SQLite 适合本地开发。单服务器 Agent 平台如果已经使用 PostgreSQL，可以直接通过 SQLAlchemy Session 保存会话，不必为了记忆额外引入很多中间件。

8. 为什么不能发送全部历史消息

随着消息不断增加，每轮都发送全部历史会导致 Token 成本和延迟上升、上下文超过限制、旧信息干扰当前任务以及敏感数据暴露范围扩大。生产系统通常使用分层上下文：

系统指令
+ 当前用户请求
+ 最近 10～30 条原始消息
+ 较早对话的结构化摘要
+ 与当前请求相关的长期记忆
+ RAG 检索出的知识
+ 当前任务状态摘要
+ 必要的工具结果

上下文管理的核心不是保存得越多，而是每一轮选择得越准确。

9. 长期记忆的三种类型

Semantic Memory（事实记忆）。保存相对稳定的事实，例如“用户主要使用 Python”“用户正在准备计算机秋招”。

Episodic Memory（经历记忆）。保存过去发生的事件，例如“用户已经学习 Agent Trace”“上次部署因连接池配置错误失败”。

Procedural Memory（方法记忆）。保存以后应该如何行动的经验，例如“秋招知识文档应包含 Python 示例与面试回答”“发送外部邮件前必须审批”。

10. 什么信息值得写入长期记忆

不是用户说的每句话都应该永久保存。“今天有点困”通常没有长期价值；“我的所有项目都使用 Python 3.12”可能值得保存。写入前应判断未来是否会复用、是否足够稳定、来源是否可信、是否敏感、是否已存在冲突记忆，以及是否需要过期时间。

class MemoryCandidate(BaseModel):

candidate = await extract_memory(message)

if candidate.confidence < 0.8:

模型可以负责提取候选记忆，但最终是否写入、保存多久和写入哪个命名空间，应由确定性规则控制。

11. 长期记忆如何召回

记忆较少时可以按字段精确读取；记忆较多时可以使用混合召回，将租户和用户过滤、关键词检索、向量相似度、时间新鲜度、重要性、可信度和使用频率结合起来。

memories = await memory_store.search(
    tenant_id=tenant_id,
    user_id=user_id,
    query=current_request,
    memory_types=["preference", "fact", "experience"],
    limit=5,
)

向量相似度只能解决“语义是否接近”，不能代替权限过滤、时间有效性和事实可信度。检索时必须先限制租户和用户范围。

Casbin 的元模型是什么

“用户使用 Python”属于 Memory；“Python GIL 的工作原理”属于 RAG 知识；“用户上次询问过 GIL”属于经历记忆。不要把消息、偏好和知识文档不加区分地塞进同一个向量库。

13. 记忆冲突、更新与遗忘

如果旧记忆是“用户使用 Python 3.11”，后来用户明确表示已升级到 3.12，系统不应同时把两者作为当前事实召回。可以用版本化记录新事实，并通过 supersedes 指向旧记忆。旧记录可以留作历史，但必须标记失效。

长期记忆应支持更新、删除、过期、用户纠正、来源追踪、可信度和审计记录。遗忘并不是缺陷：过期和删除能够减少错误召回、降低存储成本，并满足隐私要求。

14. 单服务器 Agent 平台的存储方案

第一阶段可以只使用 PostgreSQL 作为唯一事实来源，并在需要语义检索时增加 pgvector。无需为了“记忆”同时部署多个数据库。

PostgreSQL
├─ agent_runs：一次完整 Agent 任务
├─ run_checkpoints：关键步骤状态快照
├─ conversation_sessions：会话元数据
├─ conversation_messages：原始消息
├─ agent_memories：跨会话长期记忆
├─ tool_executions：工具调用与幂等状态
└─ approval_requests：等待人工审批的动作

Redis 是可选组件，适合热 Session 缓存、短期状态、任务队列和分布式锁。当并发 Worker、队列或热点读取需求明显增加后再引入；它不应成为唯一持久化来源。

15. 多租户隔离

所有 Run、Session、Message、Memory、Checkpoint 和 Tool Execution 都应包含 tenant_id 与 user_id。数据库查询、缓存键、向量检索和对象存储路径都必须携带租户边界。

SELECT *
FROM agent_memories
WHERE tenant_id = :tenant_id
  AND user_id = :user_id
ORDER BY created_at DESC;

建议在应用层过滤之外使用 PostgreSQL Row Level Security 作为第二层保护。不能依赖模型判断哪些数据属于当前租户。

16. Memory 的安全风险

密码、API Key、Access Token、Authorization Header、完整银行卡信息、无必要的证件数据、原始工具返回中的敏感信息和模型隐藏思维链，通常不应进入长期记忆。系统应提供最小化采集、字段级加密、保存期限、用户查看与删除、来源记录、审计日志和敏感信息检测。

如果 Run State 会被序列化或跨服务传输，也要把它视为持久化数据，避免将密钥和内部连接对象写入其中。

17. 常见错误认识

数据库保存了历史，模型就记得。错误。模型只能看到本轮 Context，存储和模型之间仍需要检索与组装。

把全部聊天记录发送给模型就是 Memory。错误。这只是未经管理的上下文堆积。

向量数据库就是长期记忆。错误。向量库只是检索工具，记忆还需要写入策略、命名空间、冲突更新、过期与删除。

State 和 Trace 是一回事。错误。State 用来继续执行，Trace 用来观察和排查；State 丢失可能导致任务无法恢复。

Session ID 可以直接等于 User ID。错误。一个用户可以同时拥有多个独立会话和多个任务运行。

19. 面试回答模板

Agent State 保存一次任务的当前执行状态，例如当前步骤、轮数、工具结果、待审批动作和错误信息，主要用于 Agent Loop 推进、故障恢复与暂停续跑。Session Memory 保存同一会话的多轮历史，Long-term Memory 保存跨会话仍有价值的用户事实、偏好和历史经验。数据库中的信息不会自动进入模型，运行时还要根据当前请求进行检索、筛选和上下文组装。生产环境可以使用 PostgreSQL 保存状态、消息和长期记忆，通过 Checkpoint 实现恢复，并为长期记忆设计租户命名空间、可信度、过期、冲突更新与删除机制。

21. 一句话总结

State 保存任务进度，Session 保存当前会话，Long-term Memory 保存跨会话的有价值信息，而 Context 负责在每一轮把最相关、最安全的信息交给模型。
