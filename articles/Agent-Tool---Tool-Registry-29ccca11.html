Agent Tool 白名单：从 Tool Registry 到运行时授权

Agent Tool 白名单解决的不是“模型会不会选工具”，而是“平台允许这个 Agent 看见并执行哪些工具”。它应当由 Host 或 Tool Gateway 在服务端强制执行，不能只写进 Prompt，也不能只依赖模型自觉。

核心结论：先用确定性的权限规则算出候选工具，再让模型在候选集合中选择；真正执行前还要再次鉴权。暴露工具不等于授权执行。

1. 一句话理解 Agent Tool 白名单

把 Agent 想成一名员工，把 Tool 想成公司的系统能力。Tool Registry 是全公司的“系统目录”，Agent 白名单则是这名员工的“岗位权限”。研究型 Agent 可以搜索资料，却不应该删除数据库；代码 Agent 可以读取工作区，却不一定能发布生产版本；审核 Agent 可以检查结果，却不应该修改原始数据。

因此，一个 Agent 最终能使用的工具集合，不应直接等于 MCP Server 返回的全部工具，也不应等于代码里注册的全部函数。它必须经过 Agent、租户、用户、环境与任务上下文的共同约束。

2. Host 到底怎样决定暴露哪些 Tool

Host 通常会先汇总本地函数、MCP Server、内部 API 等来源的工具，再根据平台策略过滤。过滤之后，Host 才把工具的名称、描述和输入 Schema 发给模型。模型看到的是最终候选集，而不是平台全部能力。

MCP tools/list 或本地注册
        ↓
Tool Registry：标准化名称、Schema、风险等级
        ↓
Agent 白名单：这个 Agent 被授予了什么
        ↓
租户、用户、环境、资源范围硬过滤
        ↓
相关性筛选：本轮任务真正需要哪些 Tool
        ↓
模型选择 Tool
        ↓
Tool Gateway 再鉴权、审批、限流与审计
        ↓
执行器调用真实系统

这里包含两个性质不同的判断：权限过滤是安全边界，必须由确定性代码完成；相关性筛选是上下文优化，可以使用规则、标签、Embedding、Tool Search 或模型路由。相关性算法可以漏选一个工具，但绝不能越过权限边界。

4. 有效工具集合怎样计算

可以把最终候选集理解为多个集合的交集：

EffectiveTools
= ServerCatalog
  ∩ AgentAllowlist
  ∩ TenantGrant
  ∩ UserPermission
  ∩ EnvironmentPolicy
  ∩ ResourceScope
  ∩ TaskRelevantTools
  − ExplicitDeny

ExplicitDeny 应当优先于 Allow。只要某个环境、租户或安全策略明确拒绝，就不能因为其他规则允许而重新开放。系统默认采用 Default Deny：未显式授权的工具一律不可见、不可执行。

5. 先建立稳定的 Tool Registry

白名单不能只保存一个容易重名的短名称。例如两个 MCP Server 都可能提供 search。实践中应使用稳定的规范化 ID，例如 feishu:docs.search、github:repo.read、prod-db:order.delete，并把展示名称与授权 ID 分开。

6. 白名单应该存在哪里

小型项目可以把策略放在版本控制中的 YAML 或 JSON 文件里；多租户平台通常把它存进控制面的数据库，由管理后台或 API 维护。无论放在哪里，Prompt 只负责向模型解释规则，真正的授权事实必须来自服务端策略。

一套常见的数据模型包括：

  • tool_registry：保存全部工具的规范化信息。
  • agent：保存 Agent 身份、所属租户与运行配置。
  • agent_tool_grant：记录某 Agent 对某 Tool 的 Allow 或 Deny、资源范围和有效期。
  • policy_version：记录策略版本、发布人和回滚点。
  • approval_ticket：记录高风险调用的审批状态。
  • tool_audit_log：记录谁在什么上下文中调用了什么工具及结果。

7. Agent 声明需求，平台决定授权

Agent 的 Manifest 可以声明“我希望使用哪些工具”，但不能自行给自己授权。控制面需要把“请求能力”与“已批准能力”分开：

agents:
  research-agent:
    requested_tools:
      - web:search
      - feishu:docs.read
      - feishu:docs.write
    granted_tools:
      - web:search
      - feishu:docs.read
    denied_tools:
      - feishu:docs.delete
    constraints:
      tenant_id: tenant-a
      environments: [dev]
      max_calls_per_run: 20
      expires_at: null
    policy_version: 7

上例中，即使 Agent 请求了文档写入，平台没有批准，它也不会出现在有效工具集中。生产系统还可以按工具组授权，例如 docs.readonly，在发布时展开为具体 Tool ID；但审计日志最好仍记录最终的具体工具。

8. Python 中怎样实现硬过滤

from dataclasses import dataclass
from typing import FrozenSet

@dataclass(frozen=True)
class ToolSpec:
    tool_id: str
    risk_level: str
    allowed_envs: FrozenSet[str]

@dataclass(frozen=True)
class AgentPolicy:
    allow: FrozenSet[str]
    deny: FrozenSet[str]
    tenant_id: str

@dataclass(frozen=True)
class RuntimeContext:
    tenant_id: str
    environment: str
    user_permissions: FrozenSet[str]

def compute_effective_tools(
    registry: dict[str, ToolSpec],
    policy: AgentPolicy,
    ctx: RuntimeContext,
) -> list[ToolSpec]:
    if ctx.tenant_id != policy.tenant_id:
        return []

    result = []
    for tool_id in policy.allow:
        if tool_id in policy.deny:
            continue
        tool = registry.get(tool_id)
        if tool is None:
            continue
        if ctx.environment not in tool.allowed_envs:
            continue
        if tool_id not in ctx.user_permissions:
            continue
        result.append(tool)
    return result

这里的 RuntimeContext 必须由登录态、服务端会话或网关注入，不能让模型通过 Tool 参数自行传入 tenant_id 或 user_id。否则模型只要修改参数就可能越权。

9. MCP 场景下怎样应用白名单

MCP Server 的 tools/list 告诉 Client“这个 Server 提供哪些工具”，但 Agent 白名单通常是 Host 的应用层策略，并不是远端 Server 自动替你完成的授权。

一个典型过程是：Host 连接 MCP Server，读取工具列表；把 Server 身份与工具名组合成规范化 ID；同步进 Tool Registry；根据当前 Agent Policy 过滤；只把过滤后的 Schema 交给模型。即使 Host 没有向模型暴露某个工具，MCP Server 仍然可能知道这个工具存在，所以 Server 端也必须验证调用者身份与资源权限。

换句话说，Host 的白名单负责缩小模型能力面，MCP Server 或 Tool Gateway 的鉴权负责保护真实资源。两层都要有。

10. 工具很多时还要做相关性筛选

一个 Agent 可能被允许使用数百个 Tool，但把全部 Schema 塞进上下文会消耗 Token，也会增加模型误选概率。因此可以在硬权限过滤之后，再按任务相关性选出 Top-K 工具。

常见方法包括按 Agent 类型预设工具组、根据当前工作流状态选择工具、用关键词或标签匹配、用 Embedding 检索 Tool 描述，以及通过 Tool Search 动态加载。顺序必须保持为：

权限硬过滤 → 相关性检索 → 模型选择

不能先从全量工具中做语义检索，再把结果直接交给模型，因为检索阶段也可能把未授权工具带入上下文。

11. 为什么执行前还要再次鉴权

模型看到 feishu:docs.write，只表示这个 Agent 在某类任务中可能被允许写文档，并不表示它可以修改任意文档。真正调用时还要检查目标资源、参数、当前用户权限、租户归属、审批状态、调用次数与策略版本。

def invoke_tool(ctx, tool_id: str, arguments: dict):
    tool = registry.get(tool_id)
    if tool is None:
        raise PermissionError("unknown tool")

    decision = policy_engine.authorize(
        actor=ctx.actor,
        agent_id=ctx.agent_id,
        tenant_id=ctx.tenant_id,
        tool_id=tool_id,
        resource=extract_resource(tool_id, arguments),
        environment=ctx.environment,
        policy_version=ctx.policy_version,
    )
    if not decision.allowed:
        raise PermissionError(decision.reason)
    if decision.requires_approval:
        return approval_service.create_ticket(ctx, tool_id, arguments)

    return tool_gateway.execute(tool, arguments, ctx)

这次授权应当基于服务端可信上下文，并记录决策原因。这样即使模型被提示注入诱导，或者旧会话中的 Tool Schema 还残留在上下文里，执行层仍能拒绝越权调用。

12. 不要只控制 Tool，还要控制资源范围

只允许 database:query 仍然太宽。更完整的授权还应限制可以访问的租户、数据库、表、知识库、仓库、目录、网络域名和 Secret。对写操作，还可以约束最大影响行数、允许的 HTTP 方法、可写分支、每日调用次数以及是否必须人工确认。

例如，代码 Agent 可以获得 filesystem:write，但资源范围只允许当前工作区；研究 Agent 可以获得 web:fetch，但网络策略拒绝内网地址和云元数据地址；客服 Agent 可以获得 order:refund，但金额超过阈值时必须审批。

13. Multi-Agent 平台怎样分配白名单

Agent

建议允许

建议拒绝或限制

Supervisor

创建子任务、查看状态、汇总结果

默认不直接接触数据库、文件系统和生产发布

Research Agent

搜索、网页读取、知识库只读

禁止删除、支付、生产写入

Code Agent

当前工作区读写、测试、受控终端

限制目录、网络和 Secret；生产部署需单独授权

Reviewer

读取变更、运行只读分析

不修改代码，不绕过审批合并

Deployment Agent

指定环境的发布与回滚

生产环境短时授权，强制审批和完整审计

Supervisor 调用子 Agent 时，也应把允许的 Tool Scope 一并下发，而且子 Agent 的权限只能比父任务更窄，不能因为“被委派”而自动获得平台全部工具。

14. 动态授权、版本与缓存

白名单可以静态，也可以动态。日常只读工具适合长期授权；生产写入、删除、支付等能力适合带过期时间的临时授权。每次 Agent Run 应绑定一个 policy_version，便于复现当时为什么允许或拒绝某次调用。

如果 Host 缓存了工具列表，策略变更后要有失效机制。高风险撤权应立即生效，不能等 Agent 会话结束。常见做法是短 TTL、策略版本校验和事件通知结合；执行网关在每次调用时对比当前版本，发现旧版本就重新授权。

15. 审计日志应记录什么

审计日志至少需要记录 run_id、trace_id、用户、Agent、租户、Tool ID、策略版本、参数摘要、目标资源、授权结果、审批票据、幂等键、执行结果和耗时。敏感参数不要原样落盘，应脱敏或只记录哈希。

日志不仅用于追责，也用于回答三个工程问题：某个 Tool 为什么被暴露；某次调用为什么被拒绝；策略升级后哪些 Agent 的能力发生了变化。

16. 常见错误

  • 只在 Prompt 中写“不要调用危险工具”。 Prompt 不是安全边界，模型可能被提示注入影响。
  • 把 MCP Server 的全部 tools/list 原样交给模型。 这会扩大能力面，也浪费上下文。
  • 只在暴露阶段检查一次权限。 真正执行时的资源和参数尚未确定，必须再次鉴权。
  • 相信模型传入的 tenant_id、user_id。 身份与租户必须来自服务端可信上下文。
  • 只按工具名授权。 同名工具可能来自不同 Server，应使用规范化 Tool ID。
  • 长期授予生产危险能力。 高风险能力应短时授权、强制审批并可立即撤销。
  • 没有策略版本与拒绝原因。 出问题后将无法复现当时的授权决策。

18. 面试回答

Agent 白名单通常由 Host 或控制面维护，而不是让模型自己决定。平台先把本地函数和 MCP Server 的工具同步到 Tool Registry，再根据 Agent 授权、租户、用户权限、运行环境和资源范围做确定性过滤，只把候选 Tool Schema 暴露给模型。工具很多时，可以在权限过滤后再做语义 Top-K。模型发起调用后，Tool Gateway 还要结合具体参数重新鉴权，并处理审批、限流、幂等和审计。因此“模型能看见工具”和“这次调用能真正执行”是两道不同的安全关卡，系统应当默认拒绝、显式授权，并支持策略版本和撤权即时生效。
