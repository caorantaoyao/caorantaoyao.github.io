Agent Trace：从执行链路到可观测性

一句话理解：Agent Trace 把一次 Agent 任务从用户请求到最终结果的每一步记录成一棵执行树，让我们能够还原模型调用、工具执行、RAG、RPC、审批、重试、耗时和费用。

Agent 的执行路径由模型动态决定，同一个输入可能产生不同工具选择和调用次数。仅查看最终答案或零散日志，很难解释 Agent 为什么成功、失败、变慢或陷入循环，因此 Trace 是 Agent 生产化的基础能力。

1. 先看一次完整的 Agent Trace

用户提出：“查询订单 20260729001，如果已经发货就给我发送通知。”

Trace: order_notification_agent
│

├── Span: agent_turn_1                 840ms
│   └── Span: llm_generation           825ms
│       └── 决定调用 query_order
├── Span: tool.query_order             125ms
│   └── Span: rpc.order_service        110ms
│       └── 返回 status=shipped
├── Span: agent_turn_2                 760ms
│   └── 决定调用 send_notification
├── Span: approval                       8s
│   └── 用户确认发送
├── Span: tool.send_notification       230ms
└── Span: final_response               580ms

这棵树既展示控制流，也展示每一步的父子关系、耗时、状态和业务信息。

2. Trace 与 Span

2.1 Trace

Trace 表示一次完整的端到端操作，例如“查询订单并发送通知”，通常拥有唯一 trace_id。它是所有相关 Span 的容器。

2.2 Span

Span 表示一个具有开始和结束时间的具体操作，例如模型生成、工具调用、数据库查询或人工审批。Span 通常包含：

  • span_id：当前操作的唯一标识；
  • parent_span_id：父操作标识；
  • 开始、结束时间与耗时；
  • 状态、属性和事件；
  • 异常、重试和业务元数据。
Trace: agent.run
└── Span: tool.query_order
    └── Span: rpc.order_service
        └── Span: db.select_order

3. Log、Metric 与 Trace 的区别

类型

主要回答的问题

示例

Log

具体发生了什么事件？

订单 RPC 返回 504

Metric

系统整体运行得怎么样？

P95 延迟升到 12 秒

Trace

这一次请求经过了哪些步骤？

慢在工具 RPC，而不是模型

Metric 发现趋势，Trace 定位链路，Log 提供具体细节。三者互相补充，而不是互相替代。

4. 为什么 Agent 特别需要 Trace

普通后端服务通常执行固定的 Controller、Service、Repository 路径；Agent 会根据模型结果动态选择工具、决定是否重试、是否 Handoff、是否继续循环。非确定性使得“同样输入、不同轨迹”成为常态。

  • 回答慢：到底慢在模型、RAG、工具还是人工审批？
  • 结果错：选择了错误工具，还是工具返回了错误数据？
  • 成本高：模型调用过多，还是上下文过长？
  • 产生副作用：为什么重复发邮件或重复创建任务？
  • 陷入循环：哪些工具被重复调用，停止条件为何没有触发？

5. Agent Trace 应记录哪些步骤

步骤

建议记录

Agent Run

Agent、工作流版本、总状态、总步骤、总 Token、费用

模型调用

模型、Prompt 版本、Token、首 Token 延迟、停止原因、重试

工具调用

tool_call_id、工具名、参数摘要、结果、耗时、幂等键

RAG

查询、top_k、文档 ID、分数、重排、权限过滤、最终上下文

状态变化

当前节点、下一节点、Checkpoint、重试、剩余预算

Handoff

源 Agent、目标 Agent、原因、传递上下文与子任务结果

Guardrail

触发规则、允许、阻止或修改结果

人工审批

审批状态、等待时间和决定，不记录不必要的个人信息

6. Trace 不等于模型思维链

Agent Trace 记录的是可观察系统行为：调用了哪个工具、结构化参数是什么、工具返回什么、状态如何变化、发生哪些重试。它不要求记录模型隐藏的完整思维过程。

推荐记录“决策结果”，例如 decision=tool_call、tool=query_order，而不是强迫模型输出或存储冗长内部推理。

7. Trace、Run、Thread 与会话

不建议把整个长期对话做成一个无限增长的 Trace。更合理的是“一次用户任务一个 Trace”，再通过 thread_id、conversation_id 或 group_id 将多个 Trace 关联起来。

Thread: conversation_123
├── Trace 1: 查询订单
├── Trace 2: 修改收货地址
└── Trace 3: 申请退款

run_id 表示一次 Agent 执行；trace_id 表示一次端到端链路；不同框架的命名可能略有差异，但核心关系相同。

8. 跨 HTTP、RPC 传播 Trace

如果 Agent 编排服务通过 RPC 调用模型网关、工具服务和订单服务，Trace Context 必须跨服务传播。HTTP 常使用 W3C traceparent Header：

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  1. 上游创建或读取 Trace Context。
  2. 下游创建新的子 Span。
  3. 通过 Header 继续向更下游传播。
  4. 最终在可观测平台还原完整调用树。
Agent Run
└── tool.query_order
    └── HTTP order-service
        └── SQL SELECT orders

9. 通过消息队列传播 Trace

长任务进入 Kafka、RabbitMQ 或其他队列时，应把 Trace Context 放入消息 Header，而不是仅放在进程内存中。

{
  "traceparent": "00-...",
  "task_id": "task_123",
  "run_id": "run_456",
  "checkpoint_id": "cp_789"
}

Worker 消费后继续创建 Consumer Span。由于异步任务可能很久以后执行，还应持久化 task_id、run_id、tenant_id 和工作流版本。

Trace: document_processing
├── producer.publish_task
└── consumer.process_task
    ├── parse_pdf
    ├── embedding
    └── save_vectors

10. Python：使用 OpenTelemetry 手动埋点

from opentelemetry import trace

tracer = trace.get_tracer("agent-platform")


def run_agent(user_input: str):
    with tracer.start_as_current_span("agent.run") as run_span:
        run_span.set_attribute("agent.name", "order-agent")
        run_span.set_attribute("agent.workflow_version", "v1.3")

        with tracer.start_as_current_span("llm.generate") as model_span:
            response = call_model(user_input)

            model_span.set_attribute("gen_ai.model", response.model)
            model_span.set_attribute(
                "gen_ai.usage.input_tokens",
                response.input_tokens,
            )
            model_span.set_attribute(
                "gen_ai.usage.output_tokens",
                response.output_tokens,
            )

        if response.tool_call:
            return execute_tool_with_trace(response.tool_call)

        return response.final_output
def execute_tool_with_trace(tool_call):
    span_name = f"tool.{tool_call.name}"

    with tracer.start_as_current_span(span_name) as span:
        span.set_attribute("tool.name", tool_call.name)
        span.set_attribute("tool.call_id", tool_call.id)

        try:
            result = execute_tool(
                name=tool_call.name,
                arguments=tool_call.arguments,
            )
            span.set_attribute("tool.success", True)
            return result
        except Exception as exc:
            span.set_attribute("tool.success", False)
            span.record_exception(exc)
            raise

11. 使用 Agent 框架的自动 Trace

许多 Agent 框架会自动记录模型生成、函数工具、Guardrail 与 Handoff。以 OpenAI Agents SDK 的概念为例：

from agents import Agent, Runner, trace

agent = Agent(
    name="Order Agent",
    instructions="帮助用户查询订单。",
    tools=[query_order],
)


async def handle_request(user_input: str):
    with trace(
        "Order Agent Workflow",
        group_id="conversation_123",
        metadata={
            "environment": "production",
            "workflow_version": "v1.3",
        },
    ):
        return await Runner.run(agent, user_input)

自动埋点适合快速开始，但生产环境仍需为数据库、Redis、RPC、消息队列和业务状态增加 Span。

13. 敏感数据与隐私

以下内容可能包含敏感信息：

  • System Prompt、用户完整输入和模型完整输出；
  • 工具参数、工具结果和数据库记录；
  • RAG 检索文本和企业文档正文；
  • Authorization Header、Cookie、Access Token 和密钥；
  • 邮箱、手机号、身份证号等个人信息。

生产环境应默认禁止记录密钥和认证头，对 Prompt 与工具参数按字段脱敏，设置采样率、保留期限、租户隔离和访问审计。必要时只记录摘要、长度、分类或内容哈希。

15. Trace 如何帮助排查问题

15.1 回答特别慢

LLM: 1.2 秒
RAG: 0.3 秒
工具 RPC: 18 秒

问题明显在工具服务，而不是模型。

15.2 重复发送邮件

send_email → timeout → retry → send_email

这通常说明写操作缺少稳定幂等键，或超时后的状态判断不正确。

15.3 Agent 陷入循环

search → model → search → model → search

应增加最大步骤数、重复调用检测、结果去重和费用预算。

15.4 引用了其他租户文档

RAG 检索 → tenant_filter 缺失 → 命中其他租户文档

Trace 可以证明问题发生在权限过滤，而不是简单归因于模型幻觉。

16. Trace 与评测的关系

失败 Trace 可以沉淀为评测样本，包括输入、期望工具、实际工具、参数、工具结果、最终答案和错误位置。

生产失败 Trace
    ↓ 提取样本
回归评测集
    ↓ 修改模型、Prompt、工具或工作流
重新运行
    ↓
比较轨迹与最终结果
  • Trace：回答这一次发生了什么。
  • Evaluation：回答多次运行整体表现如何。
  • Monitoring：回答生产系统是否正在恶化。

每个用户任务生成 run_id 和 trace_id；模型、工具、RAG、RPC 与队列创建独立 Span；工作流和 Prompt 都记录版本；写操作额外记录幂等键与审批状态。

19. 面试回答模板

Agent Trace 是对一次 Agent 任务端到端执行过程的链路追踪。一个 Trace 表示完整任务，内部由多个具有父子关系的 Span 组成，分别记录模型调用、RAG 检索、工具执行、RPC、Handoff、Guardrail、人工审批和状态持久化等步骤。它可以帮助定位延迟、错误、重复副作用和工具调用循环，并统计 Token、费用及任务成功率。生产环境需要通过 Trace Context 跨 HTTP、RPC 和消息队列传播，同时对 Prompt、工具参数、Token 和用户数据进行脱敏与采样。
