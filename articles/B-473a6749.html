索引与 B+ 树：为什么数据库不用哈希表或二叉搜索树保存所有索引

这篇文档承接《一条 SQL 是怎样执行的：从连接、解析、优化，到索引、存储引擎与磁盘》，继续回答执行计划中的一个核心问题：数据库为什么经常选择树形索引，以及为什么常见实现不是普通二叉搜索树，也不能把全部索引都换成哈希表。

先记住结论：B+ 树不保证每一种查询都最快，但它能在页式存储上同时兼顾等值查询、范围查询、排序、前缀扫描、动态增删和稳定性能，因此成为通用有序索引的经典选择。哈希表和其他索引结构仍然有价值，只是适用范围更窄。

1. 索引到底解决什么问题

如果一张表有一千万行，而查询条件是 WHERE user_id = 10086，没有可用索引时，数据库可能需要逐页读取并检查大量记录。索引额外保存“可搜索的键”和“记录位置或记录本身”，让数据库先缩小候选范围，再访问真正的数据。

索引并不是数据的免费副本。它要占用磁盘和缓存，插入、删除、更新时也要维护。因此准确的理解是：索引用额外空间和写入成本，换取特定读取路径的速度。

2. 数据库以页为单位管理数据

理解数据库索引时，不能只看算法课里的“比较次数”。关系数据库通常把磁盘文件划分为固定大小的页，缓存和读取也以页为基本单位。以 MySQL 8.4 的 InnoDB 为例，默认页大小是 16 KiB，也可以在实例初始化时选择其他支持的页大小。

一次索引查找访问的树节点，通常对应一个页。页面已经位于 Buffer Pool 时，这是一次内存访问；页面不在缓存时，才需要物理 I/O。磁盘或远程存储访问通常比内存比较昂贵得多，所以索引结构的重要目标不是只减少比较次数，而是用尽可能少的页访问定位记录。

单看等值查询，哈希表很有吸引力；单看内存中的有序集合，平衡二叉树也很好。但数据库要在页式存储、有限缓存和混合查询下工作，所以需要更综合的结构。

4. 为什么普通二叉搜索树不合适

二叉搜索树规定左子树的键更小、右子树的键更大。理想情况下它可以通过不断折半查找数据，但普通二叉搜索树没有自动平衡能力。如果键按递增顺序插入，它可能退化成一条链。

10
  └─ 20
       └─ 30
            └─ 40
                 └─ 50

此时查找最坏会从 O(log n) 退化为 O(n)。数据库不能接受数据分布或插入顺序稍有变化，查询延迟就从稳定变成不可预测。

5. 平衡二叉树为什么仍不是磁盘索引的首选

AVL 树和红黑树能控制高度，避免退化，在内存中的映射、集合和调度结构里非常实用。但它们的分支数通常只有 2。数据量很大时，即使高度是对数级，也可能需要经过较多层。

更关键的是，每个磁盘页能容纳很多键和指针。如果一个页只发挥“左、右两个孩子”的作用，就没有充分利用整页空间。树越高，冷缓存情况下可能需要访问的页面越多。平衡二叉树解决了“会不会退化”的问题，却没有充分解决“每次 I/O 能带回多少导航信息”的问题。

6. 从二叉树走向多路平衡树

B 树家族允许一个节点包含多个键和多个子指针。一个内部页可以同时划分几十、几百甚至更多个键区间，使每下降一层就排除绝大多数数据。这个性质叫高扇出。

做一个只用于建立直觉的简化估算：如果一个内部页可以保存约 500 个有效分支，三层导航理论上就能覆盖约 500 × 500 × 500 个叶子范围。真实容量还会受到键长度、页头、记录格式和填充率影响，但结论不变：多路树通常很矮。

7. B+ 树的基本结构

B+ 树是一种多路、平衡、有序的搜索树。所有叶子通常位于同一深度；内部节点主要保存分隔键和子页指针，用于导航；真正的索引记录集中在叶子层；相邻叶子页通常按键顺序连接。

                    [30 | 60]
                  /     |      \
          [10 | 20] [40 | 50] [70 | 80]
               叶子页按键顺序相连
 [10,20]  <->  [30,40,50]  <->  [60,70,80]

严格的节点格式、页目录和链表实现因数据库产品而异。工程资料有时把实现统称为 B-tree 索引；本文用 B+ 树模型理解“内部页负责导航、叶子层保存索引记录、范围扫描沿叶子推进”这一组核心特性。

8. 一次等值查找怎样穿过 B+ 树

假设要查找键 47。数据库先在根页判断它落在 30 到 60 之间，于是选择中间子页；再在该内部页继续确定目标范围，最后到达包含 47 的叶子页并定位记录。

根页
  -> 选择键区间
内部页
  -> 选择更小区间
叶子页
  -> 二分或页内目录定位索引记录

树高决定了导航最多跨越多少层，但并不等于每层必然发生磁盘 I/O。根页和高层内部页经常留在 Buffer Pool 中，真正的物理读取可能主要发生在叶子页。

9. B+ 树为什么适合范围查询和排序

执行 WHERE score BETWEEN 80 AND 90 时，数据库先沿树找到第一个不小于 80 的叶子位置，然后按叶子层的顺序继续向后扫描，直到键超过 90。它不需要为区间内的每一个值重新从根开始查找。

同样的有序性还能服务于 ORDER BY、最小值、最大值和部分前缀匹配。优化器是否最终选索引仍取决于选择性、返回行数、排序方向、覆盖情况和成本估算；“存在索引”不等于“必然走索引”。

哈希表最大的局限不是“碰撞一定很慢”，而是哈希函数会打散原始顺序。相邻键可能落在完全不同的桶里，因此它很难直接回答“大于、小于、区间、排序、前缀”等问题。数据库的查询类型非常丰富，不能只为等值查询优化。

11. 数据库什么时候仍会使用哈希

哈希结构并没有被数据库放弃，而是被放到更匹配的场景。PostgreSQL 提供 Hash 索引，主要服务简单等值比较；MySQL 的 MEMORY 存储引擎支持 HASH 索引；查询执行器还经常使用哈希表完成 Hash Join 或 Hash Aggregate。某些数据库也会在内存中构建自适应或临时哈希结构来加速热点等值访问。

因此更准确的说法是：哈希适合“我只关心这个键是否完全相等”的路径；B+ 树更适合作为要覆盖多类查询的通用有序索引。

B 树不是错误结构，B+ 树也不是所有条件下都绝对优于 B 树。数据库偏爱 B+ 树式布局，主要因为它更贴合页式存储、范围扫描和可预测的访问路径。

13. 插入数据时如何保持平衡

新索引键会被写入目标叶子页。如果页还有空间，只需在页内找到正确位置并更新相关元数据；如果页满了，数据库会把记录分配到两个页，并把新的分隔信息向父节点传播，这就是页分裂。父页也满时，分裂可能继续向上，极端情况下会产生新的根页，树高增加一层。

原叶子页：[10, 20, 30, 40]  +  插入 35
                     |
                     v
左页：[10, 20, 30]       右页：[35, 40]
                     |
                     v
父页增加一个指向右页的分隔键

连续递增主键通常更容易在索引右侧追加；随机主键可能让写入分散到多个页并增加分裂、缓存失效和空间碎片。它们的实际影响仍与数据规模、页填充率和存储引擎策略有关。

14. 删除数据时会发生什么

删除并不总是立刻把物理空间紧凑地收回。数据库可能先把记录标记为删除，之后由清理过程回收；当页面利用率下降到一定程度时，存储引擎可能尝试与相邻页合并或重新组织页面。以 InnoDB 为例，索引页还有可配置的合并阈值。

这是工程实现和教材伪代码的差别：理论上可以每次严格重平衡，现实系统还要考虑并发、日志、锁、写放大和后台清理成本。

15. InnoDB 的聚簇索引

在 InnoDB 中，每张表都有一个聚簇索引。通常主键就是聚簇索引；如果没有主键，InnoDB 会按规则选择合适的唯一非空索引，否则生成隐藏的聚簇索引。

聚簇索引的叶子记录保存行数据，因此通过主键查找时，沿索引到达目标叶子页就能接触到这一行。这里“聚簇”强调的是索引组织与行数据存放方式，而不是说所有行在磁盘文件中形成一段永不移动的连续字节。

16. 二级索引、主键与回表

InnoDB 中，非聚簇索引称为二级索引。二级索引的叶子记录包含二级索引列以及对应的主键列。查询若还需要其他列，存储引擎先在二级索引中得到主键，再用主键搜索聚簇索引，这个第二次查找通常称为回表。

CREATE INDEX idx_user_email ON users(email);

SELECT id, nickname
FROM users
WHERE email = 'caoran@example.com';
idx_user_email
  -> 找到 email 对应的主键 id
  -> 用 id 查聚簇索引
  -> 读取 nickname 等完整行字段

这也解释了为什么主键过长会放大二级索引：每条二级索引记录都要携带主键列。

17. 覆盖索引为什么能减少回表

如果查询所需的列都能从某个索引记录中取得，就称该索引覆盖了这次查询。此时执行器可能不必再为每条候选记录访问主数据页。

CREATE INDEX idx_order_user_status
ON orders(user_id, status);

SELECT user_id, status
FROM orders
WHERE user_id = 10086;

覆盖关系属于“索引与具体查询”的关系，不是索引永久自带的标签。同一个索引可能覆盖查询 A，却不能覆盖还要读取 created_at 的查询 B。不同数据库还可能因为事务可见性等原因进行额外访问，所以应结合执行计划判断实际行为。

18. 联合索引与最左前缀

联合索引 (name, age) 不是两棵独立的树，而是先按 name 排序；name 相同时，再按 age 排序。它的全局顺序首先由第一列决定。

(Alice, 18)
(Alice, 25)
(Bob,   20)
(Bob,   31)
(Cathy, 22)

因此，按 name 查询，或先限定 name 再查询 age，通常能利用连续的索引范围；只按 age 查询时，所有年龄值散布在不同姓名分组中，通常无法像使用首列那样直接定位一个连续区间。少数数据库有 Skip Scan 等优化，但不应把它当作联合索引设计的默认保证。

-- 通常可以有效使用 (name, age)
SELECT * FROM users WHERE name = 'Alice';
SELECT * FROM users WHERE name = 'Alice' AND age = 25;

-- 通常不能像首列查询那样直接定位连续范围
SELECT * FROM users WHERE age = 25;

19. 为什么索引会让写入变慢

插入一行不只要写表数据，还要向每个相关索引插入记录；更新被索引列时可能要删除旧索引项并插入新索引项；删除也要维护所有索引、事务日志和可能的页面结构。随机写入还可能触发页分裂和更多缓存页面变脏。

所以索引不是越多越好。一个“从未被有效查询使用”的索引仍然会消耗磁盘、缓存和写入吞吐。

20. 应该怎样选择索引

索引设计应从真实查询模式出发，而不是给每个字段机械建索引。重点观察过滤条件、连接条件、排序、分组、返回列和查询频率，并用执行计划验证。

  • 高频且选择性较好的过滤列：更可能明显减少扫描行数。
  • 联合索引列顺序：结合等值条件、范围条件、排序和最左前缀安排。
  • 覆盖需求：适量加入常读列可能减少回表，但会让索引变大、写入更贵。
  • 低选择性列：例如只有少量状态值，单列索引不一定有收益，要结合数据分布和组合条件。
  • 写多读少的表：更要控制索引数量，避免维护成本吞噬吞吐。

最终不要只靠经验判断。使用 EXPLAIN 或等价工具观察访问方式、估算行数、实际行数、回表与排序，再根据真实负载调整。

22. 这道题背后的核心矛盾

如果数据全部常驻内存，而且只做等值查询，哈希表往往很合适；如果要在内存里维护通用有序集合，红黑树也很自然；如果数据远大于内存、需要以页读写、还要支持等值、范围和排序，B+ 树的高扇出、低高度和有序叶子就很有优势。

所以真正的决策链是：

  + 缓存命中
  + 读写比例
  + 并发与恢复成本

23. 常见误区

  • “哈希查找是 O(1)，一定比 B+ 树快。”复杂度只描述特定假设下的增长趋势，没有覆盖范围查询、碰撞、缓存局部性、扩容和持久化维护。
  • “B+ 树查一次就一定发生三四次磁盘 I/O。”访问层数不等于物理 I/O 次数，页面可能已在 Buffer Pool 中。
  • “建立索引后查询一定更快。”返回比例过高、统计信息不准、隐式转换或表达式不匹配时，优化器可能选择全表扫描。
  • “二级索引叶子保存的是物理地址。”以 InnoDB 为例，它保存主键列，再通过聚簇索引定位行。
  • “联合索引包含 age，所以只查 age 一定能高效使用。”联合键的排序首先由左侧列决定。
  • “索引越多越保险。”每个索引都会增加空间和写入维护成本。

24. 面试时可以怎样回答

数据库不是单纯选择理论查找复杂度最低的结构，而是要适配页式存储和多种查询。普通二叉搜索树可能退化；即使使用平衡二叉树，分支数仍然只有 2，树较高，无法充分利用一个磁盘页。B+ 树的内部节点只保留大量分隔键和子页指针，扇出高、树高低，叶子有序连接，所以既能做等值查找，也适合范围查询和排序。哈希表平均等值查询很快，但不保序，难以直接支持范围、排序和前缀扫描，因此更适合专门的等值场景，而不是替代所有索引。

如果面试官继续追问，可以顺着“页与 Buffer Pool → 聚簇索引和二级索引 → 回表与覆盖索引 → 联合索引最左前缀 → 页分裂与写入成本”展开。

25. 自检问题与下一步

  1. 为什么平衡二叉树已经是 O(log n)，数据库仍然关心它的树高？
  2. 为什么哈希索引适合 =，却不适合 BETWEEN 和 ORDER BY？
  3. InnoDB 用二级索引查到主键后，为什么可能还要回表？
  4. 联合索引 (a, b) 为什么通常不能把只查 b 当作一个连续范围？
  5. 覆盖索引优化了读取，但会带来什么写入和空间代价？

建议下一步：学习“事务、ACID 与并发异常：两个请求同时修改数据库时，怎样保证数据正确”。这会把目前的“数据如何查得快”推进到“并发读写时数据如何保持正确”。
