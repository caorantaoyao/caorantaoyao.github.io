缓存一致性：Cache-Aside 与失效策略

一句话结论

缓存一致性不是让缓存与数据库在任意瞬间绝对相同，而是在可接受的不一致窗口内，通过正确的读写顺序、失效策略和兜底机制，使缓存最终收敛到数据库真值。

前置知识与边界

  • 前置知识：数据库事务、并发写、缓存命中与淘汰。
  • 适用范围：数据库是事实源、缓存用于加速读取的互联网业务。
  • 不解决的问题：跨多个事实源的强一致事务；这属于分布式事务或共识问题。

核心原理与执行流程

Cache-Aside 的读流程是：先读缓存；未命中则读数据库；再把数据库结果写入缓存。写流程通常是：先提交数据库，再删除缓存。

“先更新数据库、再删除缓存”优于双写更新缓存，因为删除是幂等操作，且不需要在应用侧重现数据库中的复杂计算。它仍存在一个短暂竞态：旧读请求可能在写事务提交后把旧值回填缓存。工程上通过合理 TTL、延迟双删、版本号或 CDC 驱动失效缩短和修复这个窗口。

工程实现

  • 缓存键包含业务实体和版本边界，避免不同语义共享一个 Key。
  • TTL 增加随机抖动，防止大量 Key 同时过期造成缓存雪崩。
  • 删除失败进入可重试队列或由 CDC 消费数据库变更再次失效。
  • 热点 Key 使用请求合并、互斥重建、逻辑过期或多级缓存。
  • 监控命中率、回源 QPS、重建延迟、删除失败和脏读投诉。

故障模式与排查

  1. 命中率骤降：检查批量过期、淘汰策略、内存上限和 Key 设计。
  2. 数据长期陈旧：检查数据库已提交但缓存删除失败、重试队列和 CDC 消费积压。
  3. 数据库被打满：检查热点 Key 失效、穿透请求、请求合并和限流是否生效。
  4. 缓存穿透：检查不存在对象是否进行短 TTL 的空值缓存或布隆过滤。
  5. 难以复现的脏读：按请求时间线关联数据库提交时间、缓存读写日志和版本字段。

面试问答阶梯

  1. 为什么一般选择“更新数据库后删除缓存”，而不是更新缓存？
  2. 删除缓存失败怎么办？重试为什么仍可能乱序？
  3. 延迟双删解决了什么，不能解决什么？
  4. 如何用版本号或 CDC 防止旧值覆盖新值？
  5. 在高并发商品详情系统中，如何同时处理一致性、热点和数据库保护？

验证与实践

  • 最小实验：并发运行一个更新线程和多个读线程，记录数据库版本与缓存版本的时间线。
  • 关键指标：脏读窗口、缓存命中率、回源 QPS、P99 重建延迟和删除失败率。
  • 项目应用：为缓存条目加入单调版本号，并模拟删除失败与消息重放。
  • 延伸方向：缓存击穿、雪崩、穿透；事务消息；CDC；一致性哈希。
