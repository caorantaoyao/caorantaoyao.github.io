Casbin PERM 元模型：从请求到授权决策

一句话结论

Casbin 不把权限系统固定成某一种 RBAC，而是用 PERM 元模型把授权决策拆成 Request、Policy、Matchers 和 Effect 四部分。model.conf 定义计算规则，Policy 保存动态授权数据，Enforcer 将一次访问请求与所有候选策略匹配并合并为允许或拒绝。

前置知识与边界

  • 前置知识：认证与授权的区别、ACL、RBAC 的基本概念。
  • 适用范围：需要 ACL、RBAC、多租户 RBAC、ABAC 或混合授权模型的后端系统。
  • 不解决的问题：Casbin 不负责登录、签发 JWT、校验用户密码，也不负责资源数据本身的存储。
  • 核心边界：身份认证回答“你是谁”，Casbin 授权回答“你能做什么”。

PERM 表示：

  • P — Policy：一条权限策略包含哪些字段。
  • E — Effect：多条匹配策略的 allow / deny 如何合并。
  • R — Request：一次鉴权请求包含哪些参数。
  • M — Matchers：请求与策略之间满足什么条件才算匹配。

RBAC 使用的 [role_definition] 是角色关系扩展，不属于 PERM 四个字母，但会在 Matcher 中参与计算。

2. 最小 ACL 模型

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act

策略数据：

p, alice, order:1001, read
p, bob, order:1001, update

Python 调用：

import casbin

enforcer = casbin.Enforcer("model.conf", "policy.csv")
allowed = enforcer.enforce("alice", "order:1001", "read")

参数会按 Request Definition 的顺序绑定：

r.sub = "alice"
r.obj = "order:1001"
r.act = "read"

3. Request：定义问题的形状

[request_definition]
r = sub, obj, act

sub、obj、act 分别表示访问主体、目标资源和操作。字段名和数量可以自定义，但 enforce() 的参数数量与顺序必须严格一致。

多租户系统可以定义为：

r = sub, dom, obj, act

对应调用：

enforcer.enforce("alice", "tenant-a", "order:1001", "read")

此时 dom 可以代表租户、公司、项目或工作空间。

4. Policy：定义授权数据的形状

[policy_definition]
p = sub, obj, act, eft

策略示例：

p, alice, order:1001, read, allow
p, alice, order:1001, delete, deny

一行策略会绑定到 p.sub、p.obj、p.act 和 p.eft。eft 表示该策略的效果，通常是 allow 或 deny；未声明 eft 时，匹配策略默认按 allow 处理。

模型与策略应分开治理：模型随代码评审和发布，策略作为动态业务数据存储在数据库或其他 Adapter 中。

5. Matchers：找出与请求相关的策略

最基本的 Matcher 是精确匹配：

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act

对请求 alice / order:1001 / read，Casbin 会把请求与候选策略逐条代入表达式。只有表达式为真的策略，才进入 Effect 聚合阶段。

Matcher 也可以调用内置匹配函数：

m = r.sub == p.sub && keyMatch(r.obj, p.obj) && r.act == p.act

这样策略资源 /orders/* 可以匹配请求资源 /orders/1001。工程上应把成本低、过滤性强的条件放在前面，减少昂贵函数和角色图查询的执行次数。

PyCasbin 还可以注册自定义函数：

def is_owner(user_id: str, owner_id: str) -> bool:
    return user_id == owner_id

enforcer.add_function("isOwner", is_owner)

然后在 Matcher 中使用：

m = isOwner(r.sub, r.owner) || r.sub == "root"

自定义函数应保持纯函数、低延迟和可测试，避免在每条策略匹配时执行数据库或网络查询。

6. Effect：合并多条匹配结果

一次请求可能同时匹配多条 allow 和 deny 策略，因此需要 Effect 决定最终结果。

任意允许即可

e = some(where (p.eft == allow))

只要存在一条匹配的 allow 策略就允许。这个表达式不会让 deny 自动覆盖 allow。

拒绝优先

e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

必须至少存在一条 allow，并且不能存在任何 deny。

最终决策

deny

只有 allow

allow

只有 deny

Effect 解决的是“已经匹配的策略如何合并”，Matcher 解决的是“哪些策略与当前请求相关”，两者不能混为一谈。

7. RBAC：在 PERM 上增加角色关系

[role_definition]
g = _, _

g 表示“用户属于角色”的二元关系：

g, alice, admin
g, bob, reviewer

权限授予角色：

p, admin, order:1001, delete
p, reviewer, order:1001, read

Matcher 改为：

m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act

此时 g(alice, admin) 为真，因此 Alice 可以匹配授予 admin 的策略。角色还可以继承其他角色，但角色层级过深会增加理解和排查成本。

8. 多租户 RBAC

互联网后端常见的模型是“用户在不同租户拥有不同角色”：

[request_definition]
r = sub, dom, obj, act

[policy_definition]
p = sub, dom, obj, act, eft

[role_definition]
g = _, _, _

[policy_effect]
e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

[matchers]
m = g(r.sub, p.sub, r.dom) &&
    r.dom == p.dom &&
    keyMatch(r.obj, p.obj) &&
    r.act == p.act

角色关系：

g, alice, admin, tenant-a
g, alice, member, tenant-b

策略：

p, admin, tenant-a, /orders/*, read, allow
p, admin, tenant-a, /orders/*, write, allow
p, member, tenant-b, /orders/*, read, allow

相同用户可以在不同 Domain 拥有不同角色，避免把租户信息拼进角色名称。

9. 一次鉴权的完整执行流程

抽象表达为：

授权结果 = Effect(Matcher(Request, Policy₁), Matcher(Request, Policy₂), ...)

可以把四部分记成：Request 提出问题，Policy 提供候选答案，Matchers 找出相关答案，Effect 合并所有答案。

10. 工程落地

  • 模型文件进入 Git，模型变更需要评审、自动化测试和版本记录。
  • 动态策略存数据库，不要把生产权限长期维护在 CSV 中。
  • 请求中的 sub 使用稳定用户 ID，而不是可能改名的昵称。
  • obj 采用稳定、可审计的资源命名规范，例如 order:1001 或 /orders/1001。
  • 默认拒绝；Casbin 调用失败、超时或模型未初始化时不要绕过鉴权。
  • Policy 管理接口本身也必须鉴权，避免普通用户为自己添加权限。
  • 记录主体、资源、动作、最终决策、命中策略和请求追踪 ID，但不要在日志中泄露敏感数据。
  • 为 allow、deny、无匹配、角色继承、租户隔离和冲突策略分别编写测试。
  • 使用 Casbin Server 时，每次鉴权是网络调用，应设置超时、复用 gRPC Channel，并评估不可用时的 fail-closed 策略。

11. 常见误区与故障排查

  1. 把认证当授权：JWT 有效只代表用户身份可信，不代表用户可以访问任意资源。
  2. enforce() 参数顺序错误：先对照 Request Definition 检查数量和顺序。
  3. 策略字段数量不匹配：Policy 数据必须与 Policy Definition 对齐。
  4. 认为 deny 天然优先：最终冲突规则由 Effect 决定，必须显式检查表达式。
  5. RBAC 忘记调用 g()：仅定义角色关系但 Matcher 不使用 g()，角色不会参与鉴权。
  6. 多租户遗漏 Domain 条件：可能导致租户间权限串用，测试必须覆盖跨租户拒绝。
  7. Matcher 中进行远程查询：Matcher 可能对多条策略重复执行，容易造成延迟放大。
  8. 修改数据库策略后结果未更新：检查 Adapter、Watcher、策略加载和多实例同步链路。

验证与实践

最小测试矩阵：

cases = [
    ("alice", "tenant-a", "/orders/1001", "read", True),
    ("alice", "tenant-a", "/orders/1001", "write", True),
    ("alice", "tenant-b", "/orders/1001", "write", False),
    ("unknown", "tenant-a", "/orders/1001", "read", False),
]

for sub, dom, obj, act, expected in cases:
    assert enforcer.enforce(sub, dom, obj, act) is expected
  • 关键指标：鉴权 QPS、P95/P99 延迟、拒绝率、无匹配率、策略加载耗时和同步延迟。
  • 项目应用：为一个多租户订单 API 实现 read、write、delete 权限并覆盖跨租户测试。
  • 延伸方向：ABAC、RBAC with Domains、Policy Adapter、Watcher、缓存与分布式策略同步。
