一次请求的完整链路：从 DNS 到数据库再到响应返回

1. 先建立正确的整体模型

核心结论：一次业务请求不是一条 TCP 连接从浏览器贯穿到数据库，而是一串彼此独立的网络 hop。一个逻辑请求会跨越多条连接，一条可复用连接也可以承载许多请求。

分析完整链路时，始终先问两个问题：当前这一跳是谁在和谁通信？当前是在新建连接，还是在复用已有连接？

浏览器
  ⇄ 连接 A：TCP + TLS + HTTP
Nginx
  ⇄ 连接 B：TCP + HTTP 或 HTTPS
FastAPI / Uvicorn
  ⇄ 连接 C：TCP + HTTP/2 + gRPC
内部服务
  ⇄ 连接 D：TCP + 数据库协议
PostgreSQL

冷链路。首次访问或连接失效时，可能需要 DNS 查询、TCP 三次握手、TLS 握手、建立 gRPC 底层连接以及创建数据库连接。

热链路。DNS 命中缓存、HTTP 连接仍可复用、gRPC Channel 和数据库连接池已有可用资源时，请求可以跳过大部分建连步骤。

2. 客户端到入口：DNS、TCP、TLS 与 HTTP

2.1 DNS：域名变成入口地址

用户访问 https://api.example.com/v1/agent/runs 时，客户端先解析出协议、域名、默认端口 443 和路径。如果没有可复用连接，会从浏览器缓存、操作系统缓存和递归解析器中查找域名对应的 A 或 AAAA 记录；递归解析器必要时沿 DNS 委派关系查询，结果再按照 TTL 缓存。

浏览器缓存 → 操作系统缓存 → 递归 DNS
                               ↓
                      根 → 顶级域 → 权威 DNS
                               ↓
                    api.example.com → 入口 IP

DNS 返回的通常是 CDN、云负载均衡或 Nginx 集群的入口地址，而不是某个 FastAPI Worker 的真实地址。端口通常由 URL 协议决定，不是普通 A/AAAA 记录告诉客户端的。

2.2 TCP：建立可靠字节流

客户端                         服务端
SYN              ─────────────→
                 ←───────────── SYN + ACK
ACK              ─────────────→
连接进入 ESTABLISHED

TCP 三次握手让双方交换并确认初始序列号。建立后，TCP提供可靠、有序、双向的字节流，并负责确认、丢包重传、流量控制和拥塞控制。TCP ACK 表示下一步期望收到的序列号，不是 HTTP 业务成功响应。

2.3 TLS：认证并加密入口连接

HTTPS 通常在 TCP 之上进行 TLS 握手。ClientHello 会携带 SNI、支持的密码套件、密钥材料和 ALPN 候选协议；服务端返回证书和握手证明。客户端校验证书链、域名和签名后，双方得到对称会话密钥。ALPN 可以在握手中协商使用 http/1.1 或 h2。

TLS保护的是某一段连接。如果 TLS 在 Nginx 终止，Nginx 到 FastAPI 是另一条安全边界，需要单独决定使用内网明文、TLS还是mTLS。

2.4 HTTP：表达业务请求

POST /v1/agent/runs HTTP/1.1
Host: api.example.com
Authorization: Bearer ...
Content-Type: application/json
Idempotency-Key: 8ef1...

{"agent_id":"research-agent","input":"分析这份材料"}

HTTP定义方法、路径、Header、请求体、状态码和响应体。HTTP/1.1 默认使用持久连接；HTTP/2则把请求映射为独立 Stream，让一条连接同时承载多个并发请求。

现代例外。如果入口使用 HTTP/3，客户端会使用基于 UDP 的 QUIC，并把 TLS 集成到 QUIC 握手中，因此入口段不再是传统的“TCP → TLS”；后端各跳仍需独立分析。

3. 四层与七层负载均衡

四层和七层负载均衡解决的不是同一个粒度的问题。它们经常同时存在：四层入口先把连接分给多台 Nginx，Nginx 再按 HTTP 语义把请求路由给业务实例。

调度对象

把请求分给不同业务服务

判断 L4 和 L7 的关键不是“有没有终止 TLS”，而是是否解析并依据应用层语义做决策。

gRPC通常在一条 HTTP/2 长连接上承载很多 RPC。纯四层负载均衡会把整条连接固定到一个后端，可能造成实例间不均；理解 gRPC 的七层代理可以按 RPC Stream 选择后端，但已经开始的 Stream 不能中途迁移。

4. Nginx：TLS 终止、路由与反向代理

Nginx 在典型架构中既是客户端连接上的服务器，也是 FastAPI 上游连接上的客户端。它可能完成 TLS 终止、HTTP 解析、请求大小限制、鉴权、限流、访问日志、Trace ID 传递以及上游选择。

浏览器请求
  ↓ TLS 解密
Nginx 解析 Host、Path、Header
  ↓ 路由与负载均衡
选择 FastAPI 实例
  ↓
通过独立上游连接转发

必须牢牢记住：

浏览器 ← 连接 A → Nginx ← 连接 B → Uvicorn / FastAPI

连接 A 和连接 B 可以使用不同的 HTTP 版本、TLS策略、空闲时间和缓冲策略。浏览器 Keep-Alive 不代表 Nginx 到 FastAPI 的连接一定仍然可用；Nginx需要维护自己的上游连接复用机制。

Nginx也可以直接代理gRPC。无论代理HTTP还是gRPC，只有尚未开始向客户端发送响应时，才可能切换到其他上游；响应一旦已经发送一部分，就不能通过换后端重新生成同一响应。

5. Uvicorn 与 FastAPI：请求进入 Python 应用

Uvicorn负责接受连接、解析HTTP并通过ASGI调用FastAPI。ASGI的核心接口可以抽象为：

async def app(scope, receive, send):
    ...

scope保存协议、方法、路径和Header等元数据；receive用于异步接收请求体或断开事件；send用于发送响应头和响应体。

Uvicorn解析HTTP
  → ASGI scope / receive / send
  → FastAPI中间件
  → 路由匹配
  → 身份认证与依赖注入
  → 参数校验
  → endpoint
  → 响应序列化

async def路由在等待异步数据库、HTTP或gRPC I/O时会让出事件循环，因此同一Worker可以继续处理其他请求。普通def路由通常在线程池中执行；但是在async def中直接调用一个阻塞函数，并不会自动把它移到线程池。

逻辑同步不等于线程阻塞。FastAPI执行await agent_stub.CreateRun(...)时，当前业务请求必须等待RPC结果才能继续，因此是同步依赖；但等待期间事件循环线程仍可调度其他协程。

6. gRPC：同步调用内部服务

FastAPI把内部服务调用交给生成的Stub。一次gRPC调用通常会经历：

  1. 把Python对象序列化为Protocol Buffers消息。
  2. 复用长期存在的gRPC Channel和底层HTTP/2连接。
  3. 在连接上创建新的HTTP/2 Stream。
  4. 发送方法名、Metadata、Deadline和消息体。
  5. 等待服务端返回Protobuf消息与grpc-status trailers。
  6. 反序列化为应用对象并交还FastAPI。
一条 gRPC HTTP/2 连接
├─ Stream 1：CreateRun
├─ Stream 3：GetRun
├─ Stream 5：CancelRun
└─ Stream 7：ReportToolResult

HTTP/2允许多个RPC并发复用同一连接，因此Channel通常应作为应用生命周期级资源，而不是每个HTTP请求都重新创建。达到并发Stream上限时，新的RPC仍可能在客户端排队。

gRPC默认不替业务设置合理Deadline，调用方应明确给出总等待边界，并将剩余时间向下游传播。客户端Deadline到期只表示不再等待，不会自动撤销服务端已经完成的数据库副作用。

7. 数据库：连接池、事务与 SQL 执行

数据库访问可能发生在FastAPI，也可能发生在被调用的gRPC服务中。应用一般不会为每条SQL重新建立数据库连接，而是从SQLAlchemy Engine的连接池中借用已有连接。

等待连接池
  → checkout连接
  → BEGIN
  → 发送SQL
  → 解析、重写、优化、执行
  → MVCC、锁、缓存或磁盘访问
  → COMMIT或ROLLBACK
  → reset并归还连接池

连接池等待也是延迟。连接池只有20条连接而同时到达100个数据库操作时，20个请求能够执行，另外80个会等待。排查慢请求时要把“等待连接”“等待锁”和“SQL执行”分别统计。

数据库连接总量不能只看单个Worker。粗略上限通常是：

应用实例数 × 每实例Worker数 × 每Worker连接池上限

池过小会让应用排队，池过大则会把压力直接推给数据库。连接对象的close()通常表示把连接归还池，而不是立即关闭底层TCP连接。

PostgreSQL收到SQL后会经过parser、rewriter、planner/optimizer和executor。执行器结合MVCC、索引、锁、Buffer Cache与存储系统读取或修改数据；事务最终提交或回滚后，连接才应安全归还。

8. 响应如何返回浏览器

数据库完成后，逻辑结果逐层向外返回，但不是同一个协议包原路透传。每一层都把自己的协议对象转换为上一层能够理解的表示。

PostgreSQL查询结果或提交结果
  → 数据库驱动解码
  → gRPC服务构造Protobuf响应
  → gRPC message + grpc-status trailers
  → FastAPI客户端反序列化
  → endpoint构造响应对象
  → FastAPI序列化JSON
  → ASGI response事件
  → Uvicorn编码HTTP响应
  → Nginx缓冲或流式转发
  → TLS record加密
  → TCP分段传输
  → 浏览器解密、解析并更新页面

数据库错误可能被映射成gRPC状态，再由FastAPI映射成HTTP状态码。如果映射不清晰，客户端最终只会看到笼统的500错误，失去定位价值。

返回阶段通常复用刚才各hop上的现有连接，不会重新执行DNS、TCP和TLS。响应包是新发送的数据包，并不是请求数据包倒着移动；现实网络的去程和回程路由甚至可能不完全相同。

如果是普通JSON接口，通常生成完整响应后返回；如果是流式gRPC、SSE或WebSocket，响应可能在业务尚未结束时持续发送，此时超时、断开检测和取消传播需要单独设计。

9. Keep-Alive 与连接池

“Keep-Alive”在不同层代表不同机制，不能混为一谈。

机制

所在层

解决的问题

HTTP持久连接

HTTP连接管理

让后续HTTP请求复用已经建立的传输连接，减少TCP/TLS握手

TCP keepalive

操作系统TCP

对长期空闲连接发送探针，发现已经失效的对端或网络路径

gRPC keepalive

gRPC / HTTP/2

使用HTTP/2 PING检测长期连接是否仍可用

业务心跳

应用层

确认用户会话、Worker或业务任务是否仍然健康

HTTP Keep-Alive不是心跳，TCP keepalive也不证明服务端业务健康，gRPC keepalive更不等于RPC Deadline。

连接池不是一个“大连接”。它管理一组可复用连接的创建、借出、归还、健康检查、空闲回收和数量上限。请求到达后可能直接取得空闲连接，也可能新建、排队，最后因等待过久触发pool timeout。

位置

管理对象

主要风险

Nginx upstream

Nginx Worker到FastAPI的连接

每个Worker独立，容易低估总连接数

HTTP客户端

到下游HTTP服务的连接

陈旧连接、连接数过多、池等待

gRPC Channel

HTTP/2连接和并发Stream

Stream达到上限后排队，长流影响负载分布

SQLAlchemy

数据库驱动连接

连接泄漏、pool timeout、超过数据库上限

一句话区分：Keep-Alive表示“这条连接先不要关闭”，连接池表示“统一管理一组可以借用和复用的连接”，HTTP/2多路复用则表示“一条连接可以同时承载多个Stream”。

10. 超时：为整条调用链分配时间预算

完整链路不能只有一个笼统的“请求超时”。不同超时约束的是不同等待阶段。

超时

约束阶段

DNS timeout

等待名称解析

TCP connect timeout

等待建立传输连接

TLS handshake timeout

等待完成TLS协商与认证

pool acquisition timeout

等待HTTP、gRPC或数据库连接池资源

send / write timeout

发送请求数据的停滞时间

read timeout

等待下一批响应数据的停滞时间

gRPC Deadline

调用方愿意等待整个RPC的总时间

DB lock / statement timeout

数据库锁等待或语句执行

overall deadline

用户操作的端到端总预算

idle keep-alive timeout

两个请求之间允许连接空闲多久

推荐使用递减时间预算，让内层比外层更早失败，给错误转换、资源释放和响应返回留出时间：

客户端整体预算：3.0s
└─ 网关 / FastAPI：2.8s
   └─ gRPC Deadline：2.0s
      ├─ 数据库连接池等待：0.1s
      └─ 数据库语句：1.5s

Nginx的proxy_read_timeout通常限制两次读取之间能够沉默多久，不是整个请求的总时长。流式接口只要持续输出数据，就可能运行得远超该值，因此仍需应用层overall deadline。

调用方超时或客户端断开，只表示调用方不再等待；服务端可能仍在运行，数据库也可能已经提交。取消信号应尽量向下传播，但不能把“收到取消”误认为“副作用自动回滚”。

11. 重试：必须与幂等一起设计

重试最危险的问题不是“能不能再发一次”，而是“第一次到底有没有产生业务效果”。

服务端已经INSERT并COMMIT
  → 返回响应时连接断开
  → 客户端只看到超时
  → 客户端重试POST
  → 可能重复创建两条Agent Run

“没有收到响应”不等于“服务端没有执行”。创建订单、支付、启动Agent等有副作用的接口，应使用稳定业务ID或幂等键：

Idempotency-Key: 8ef1...

服务端把“租户 + 接口 + 幂等键”建立唯一约束或幂等记录。相同请求再次到达时返回第一次结果，而不是重新创建业务对象。

安全的重试策略应同时满足：

  • 只重试明确的瞬态故障，例如临时不可用、连接建立失败或符合策略的限流。
  • 操作本身幂等，或者通过幂等键和唯一约束实现业务幂等。
  • 限制最大尝试次数，使用指数退避与随机抖动。
  • 所有尝试共享overall deadline和retry budget。
  • 明确一个主要重试层，避免客户端、Nginx、FastAPI和gRPC同时重试。
客户端最多3次 × Nginx最多2次 × gRPC最多3次
= 最坏18次下游调用

Nginx默认不会在请求已经发给上游后随意重试POST、PATCH等非幂等请求；gRPC虽然具有重试机制，但没有默认业务retry policy，透明重试也只覆盖能够确认尚未进入服务端业务处理的有限情况。

12. AI Agent 平台中的推荐链路

如果Agent只做一次很快的查询，FastAPI同步等待gRPC和数据库结果是合理的。但长时间运行的Agent Loop不应一直占用普通HTTP请求。

创建Run的短链路：

POST /agent/runs
  → FastAPI鉴权与参数校验
  → 创建Run记录
  → 写入消息队列
  → 返回202 Accepted + run_id

后台执行链路：

Agent Worker消费任务
  → 执行Agent Loop
  → 调用LLM与Tool
  → 保存State、Checkpoint和Trace
  → 更新Run状态
  → 通过SSE或WebSocket推送进度

这样客户端只需要重试“创建Run”这个短操作，并通过幂等键防止重复创建。长任务由消息队列、状态机和Checkpoint负责恢复；用户刷新页面后，可以依据run_id重新读取进度。

如果使用WebSocket或SSE持续推送，需要把连接存活、业务任务存活和客户端在线状态分开建模：连接断开不应自动等于Agent任务失败，Agent任务结束也不一定要求立即关闭用户的会话连接。

13. 面试回答

用户访问一个HTTPS接口时，客户端先通过DNS缓存或递归解析得到负载均衡入口IP。如果没有可复用连接，就通过TCP三次握手建立可靠字节流，再进行TLS握手，验证服务器证书、协商密钥，并通过ALPN选择HTTP/1.1或HTTP/2。

请求可能先经过四层负载均衡，四层按连接选择Nginx节点。Nginx终止TLS并解析HTTP，根据Host、路径和Header进行七层路由，再通过独立的上游连接把请求转发给Uvicorn和FastAPI。Uvicorn把HTTP转换为ASGI事件，FastAPI执行中间件、鉴权、依赖注入、参数校验和业务代码。

FastAPI如果需要调用内部服务，会复用gRPC Channel，在HTTP/2连接上创建独立Stream并发送Protobuf消息。下游服务再从数据库连接池借出连接，在事务中执行SQL。SQL经过解析、重写、优化和执行后提交，数据库连接被归还连接池。

结果随后通过数据库协议、gRPC、FastAPI、Nginx、TLS和TCP逐层返回浏览器。整个过程不是一条TCP连接贯穿到底，而是多条相互独立的连接。HTTP Keep-Alive负责复用HTTP连接，TCP keepalive负责探测失效连接，gRPC keepalive使用HTTP/2 PING。超时要按层传递剩余预算，重试必须配合幂等键、次数上限和指数退避，避免数据库已经提交但响应丢失时造成重复写入。
