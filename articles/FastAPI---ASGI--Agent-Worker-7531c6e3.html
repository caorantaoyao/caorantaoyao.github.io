FastAPI 服务模型：从 ASGI 到 Agent Worker

核心结论：FastAPI 不是“每个请求一个线程”的服务器。FastAPI 是 ASGI Application，Uvicorn 是 ASGI Server。一个典型 Uvicorn Worker 是一个独立进程，内部通常运行一个事件循环；异步路由在事件循环上协作执行，同步路由由共享线程池承接，重要的长时间 Agent 任务则应进入独立任务 Worker。

1. 先建立正确心智模型

理解 FastAPI 时，不能只看路由函数。完整服务由网络服务器、ASGI 协议、Web 框架、进程、事件循环和线程池共同组成。FastAPI 负责路由、参数校验、依赖注入和业务函数；Uvicorn 负责监听端口、接收连接、解析 HTTP 或 WebSocket，并把请求按照 ASGI 规范交给 FastAPI。

客户端
  ↓ HTTP / WebSocket
Nginx 或负载均衡器（可选）
  ↓
Uvicorn：ASGI Server
  ├─ 监听端口与接收连接
  ├─ 解析 HTTP / WebSocket
  ├─ 运行 Event Loop
  └─ 调用 ASGI Application
                 ↓
             FastAPI
             ├─ 中间件
             ├─ 路由匹配
             ├─ 参数校验
             ├─ 依赖注入
             ├─ 执行业务函数
             └─ 构造响应

Uvicorn 和 FastAPI 通常处于同一个 Worker 进程内。它们是“服务器与应用”的逻辑边界，不是两个需要通过网络调用的微服务。

1.1 ASGI 解决了什么问题

ASGI 是服务器与 Python Web 应用之间的接口规范。它把服务器实现和框架实现解耦，因此 Uvicorn 可以运行 FastAPI、Starlette 等不同 ASGI 应用。一个 ASGI 应用在概念上是一个异步可调用对象：

async def app(scope, receive, send):
    ...

scope 描述请求或连接，例如方法、路径、请求头和协议类型；receive 用于接收请求体或 WebSocket 消息；send 用于发送响应头、响应体或 WebSocket 消息。HTTP scope 通常对应一次请求，而 WebSocket scope 会持续到连接关闭。

2. 一次请求怎样经过 FastAPI

假设客户端调用 POST /agent/runs，请求会经历以下路径：

  1. Uvicorn 从 Socket 接收网络数据并解析 HTTP 请求。
  2. Uvicorn 为请求构造 ASGI scope，并准备 receive、send 通道。
  3. 事件循环创建并调度处理该请求的异步 Task。
  4. 请求依次经过 Trace、鉴权、CORS 等中间件。
  5. FastAPI 匹配路由，读取路径、查询参数和请求体。
  6. Pydantic 完成数据解析与校验，FastAPI 解析依赖关系。
  7. FastAPI 执行路由函数和依赖函数。
  8. 返回值被转换成响应，Uvicorn 通过 send 发回客户端。

关键点是：一个请求通常对应事件循环中的一个异步 Task，而不是一个专属线程。请求等待数据库、Redis、LLM 或其他网络服务时，可以让出执行权，让事件循环继续推进其他请求。

3.1 异步路由

@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await database.get_user(user_id)
    return user

执行到 await 时，如果数据库结果尚未返回，当前 Task 暂停并把执行权交还事件循环。事件循环可以去执行其他已经就绪的请求。数据库返回后，原 Task 再从等待点继续运行。因此单个 Worker 就能让大量 I/O 型请求处于“正在进行”状态。

需要注意，async def 不会让代码自动变快。它只允许任务在等待期间让出执行权。如果函数一直进行 CPU 计算，或者调用阻塞函数而没有真正的 await，事件循环仍会被占住。

3.2 同步路由

@app.get("/legacy")
def call_legacy_service():
    return blocking_sdk_call()

FastAPI 会把普通 def 路由交给 Starlette 的共享线程池执行，再异步等待结果。这里不是“每个请求新建一个线程”，而是多个同步任务竞争同一个受限线程池。Starlette 当前默认的线程限制是 40 个 token，普通 def 路由、同步依赖、同步后台任务和部分文件操作会共同消耗这份容量。

3.3 最容易答错的情况

@app.get("/bad")
async def bad():
    result = blocking_sdk_call()
    return result

FastAPI 只会自动调度它亲自调用的路由函数和依赖函数。上面的 blocking_sdk_call() 是业务代码直接调用的普通函数，它不会自动进入线程池，而会阻塞事件循环。同一个 Worker 上的其他 HTTP 请求、SSE 和 WebSocket 事件都可能因此延迟。

可以把整个路由改成普通 def，也可以显式桥接到线程池：

import anyio

@app.get("/legacy")
async def legacy():
    result = await anyio.to_thread.run_sync(blocking_sdk_call)
    return result

显式放进线程池仍应配合并发上限、超时和背压。线程池容量有限，下游数据库和第三方 API 的容量也有限，不能把“移到线程”理解成“可以无限并发”。

4. Worker、进程、事件循环与线程池

默认启动 uvicorn main:app 时，通常只有一个 Worker 进程：

一个 Uvicorn Worker 进程
├─ 一个独立 Python 解释器和内存空间
├─ 一个 FastAPI 应用实例
├─ 一个 Event Loop
├─ 多个异步请求 Task
├─ 一个 AnyIO 共享线程池
├─ 一个数据库连接池
└─ 一个 HTTP / LLM 客户端连接池

单个 Worker 已能借助事件循环并发处理大量 I/O 请求。使用 --workers 4 启动的是四个独立进程，不是四个线程：

Uvicorn 进程管理器
├─ Worker 1：Event Loop + FastAPI + 连接池
├─ Worker 2：Event Loop + FastAPI + 连接池
├─ Worker 3：Event Loop + FastAPI + 连接池
└─ Worker 4：Event Loop + FastAPI + 连接池

多 Worker 可以利用多个 CPU 核心，也能提供一定的进程级故障隔离。但每个 Worker 有自己的普通 Python 内存。一个 1 GB 的本地模型如果由四个 Worker 分别加载，理论上可能占用约 4 GB 内存。

4.1 全局变量为什么并不全局

jobs = {}
counter = 0

四个 Worker 会得到四份独立的 jobs 和 counter。第一次请求写入 Worker 1 的字典，第二次查询如果被分配到 Worker 3，就可能看不到前一次写入。因此用户会话、Agent State、Checkpoint、任务进度和分布式锁应放到数据库或 Redis。

asyncio.Lock 只能协调当前事件循环中的协程，threading.Lock 也不能保护其他进程。需要跨 Worker 协调时，应使用数据库约束、Redis 锁、消息队列或其他外部协调机制。

5. Lifespan 与连接池

数据库连接池、HTTP 客户端和模型客户端不应在每个请求中重复创建。FastAPI 推荐使用 lifespan 在 Worker 启动时初始化资源，在 Worker 退出时释放资源。

from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http_client = httpx.AsyncClient()
    app.state.db_pool = await create_db_pool()

    yield

    await app.state.http_client.aclose()
    await app.state.db_pool.close()

app = FastAPI(lifespan=lifespan)

yield 之前的代码在开始接收请求前执行，yield 之后的代码在服务关闭时执行。多 Worker 情况下，每个 Worker 都会执行自己的 lifespan，所以数据库池、HTTP 连接池和模型对象通常都是每个 Worker 一份。

连接数需要按照 Worker 总数计算。例如四个 Worker、每个数据库连接池上限 20，数据库可能面对约 80 个连接；如果连接池还允许 overflow，也要把额外连接计入总量。请求级 ORM Session 应从当前 Worker 的连接池取得，并在请求完成后归还，不能把一个 Session 作为全局对象供所有请求共享。

6. BackgroundTasks 不等于任务队列

FastAPI 的 BackgroundTasks 可以在响应发送后继续完成短小操作，例如写审计日志或发送非关键通知：

from fastapi import BackgroundTasks

@app.post("/register")
async def register(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(send_email, email)
    return {"message": "注册成功"}

它仍然运行在当前 FastAPI Worker 进程中。同步后台函数还会使用共享线程池。进程异常退出或服务重启时，它没有消息队列那样的持久化、确认、重试与恢复保证。

因此 BackgroundTasks 适合短小、可重做、丢失后影响较低的工作，不适合长时间 Agent Loop、必须重试的任务、CPU 密集计算或需要 Checkpoint 恢复的工作流。后台任务也不应直接复用请求依赖里即将关闭的数据库 Session；更稳妥的做法是传递 user_id、run_id 等稳定标识，在后台任务内部重新获取自己的资源。

7. AI Agent 平台中的服务模型

Agent 平台通常应把快速响应的控制面和长时间运行的执行面分开：

FastAPI 控制面
├─ 接收请求与身份认证
├─ 创建 Agent Run 记录
├─ 写入数据库
├─ 向消息队列投递任务
├─ 返回 run_id
└─ 通过 SSE / WebSocket 推送事件
              ↓
          消息队列
              ↓
Agent Worker 执行面
├─ 执行 Agent Loop
├─ 调用 LLM 与 Tool
├─ 保存 State 与 Checkpoint
├─ 处理超时、重试和取消
└─ 持久化进度与 Trace
@app.post("/runs")
async def create_run(request: RunRequest):
    run_id = await run_store.create(request)

    await message_queue.publish({
        "run_id": run_id,
    })

    return {
        "run_id": run_id,
        "status": "queued",
    }

客户端得到 run_id 后，可以轮询状态接口，也可以通过 SSE 接收单向事件流，或者通过 WebSocket 进行双向交互。即使只有一台云服务器，也可以在同一台机器上分别运行 FastAPI 进程、Agent Worker 进程、Redis 和数据库。这里首先是职责、资源和故障边界的拆分，不要求一开始就拥有很多服务器。

8. 常见错误

在 async 路由里使用 requests、time.sleep 或同步数据库驱动。这些调用会阻塞事件循环。应优先选择异步客户端，或者显式放入受限线程池。

认为 def 路由可以解决 CPU 密集任务。def 路由只是把任务转移到线程池。默认启用 GIL 的 CPython 中，纯 Python CPU 计算并不会因为进入线程池就获得理想的多核并行，还会长期占用线程池容量。应使用进程池或独立计算 Worker。

使用全局字典保存 Agent 任务状态。多 Worker 不共享内存，服务重启也会清空状态。应将关键状态持久化。

使用 asyncio.create_task 承载关键长任务。它只创建当前进程内的异步任务，没有持久化确认和恢复保证。适合生命周期受控的进程内协作，不适合作为可靠任务队列。

盲目增加 Worker 和线程数。更多 Worker 会同步放大内存、数据库连接池和 HTTP 连接池；更多线程也会增加内存、上下文切换以及下游压力。容量应根据 CPU、内存、下游限额和延迟指标压测决定。

没有背压、超时和并发上限。FastAPI 可以快速接收大量请求，但数据库、LLM 服务和 Tool 通常都有容量上限。应在入口、任务队列和下游调用处设置并发限制、队列长度、超时、重试预算和取消策略。

9. 面试回答

FastAPI 本质上是一个 ASGI Application，Uvicorn 是负责网络连接、协议解析、事件循环和进程管理的 ASGI Server。一个 Uvicorn Worker 是一个独立进程，通常拥有自己的事件循环、FastAPI 实例、共享线程池和连接池。async def 路由直接在事件循环中协作执行，普通 def 路由和同步依赖由 Starlette 放入 AnyIO 线程池。多 Worker 可以利用多核，但进程之间不共享普通全局变量，因此用户会话、Agent State 和 Checkpoint 应放到数据库或 Redis。短小的响应后操作可以使用 BackgroundTasks，而 CPU 密集或需要可靠重试、恢复的长时间 Agent 任务应交给独立任务 Worker。
