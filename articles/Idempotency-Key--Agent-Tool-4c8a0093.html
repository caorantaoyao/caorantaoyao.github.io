幂等：从 Idempotency-Key、唯一约束到 Agent Tool 副作用

1. 真正的问题：客户端不知道第一次是否成功

核心结论：幂等真正解决的不是“把相同代码再执行一次”，而是调用方无法判断第一次是否已经产生业务效果时，允许它安全地再次表达同一个业务意图。

客户端发起POST /agent/runs后，服务端可能已经成功创建run_123，但响应在返回途中丢失。客户端只看到超时，无法判断请求处于哪种情况。

客户端看到的现象

服务端真实情况

超时

请求根本没有到达服务端

超时

请求已经到达，但尚未执行

超时

数据库已经提交，只是响应丢失

超时

任务仍在执行，最终结果未知

服务端已经执行成功
  → 响应返回前网络断开
  → 客户端不知道是否成功
  → 客户端重新发送请求

客户端缺少足够信息，只能重试。幂等的任务就是保证这次重试不会创建第二个Agent Run、重复扣款、重复发送邮件或重复执行其他外部副作用。

2. 幂等不等于每次响应完全相同

幂等判断的是业务效果，而不是每次响应的状态码和响应体是否逐字相同。

例如删除用户：

DELETE /users/123

第一次可能返回204 No Content，第二次可能返回404 Not Found。响应不同，但最终业务状态都是“用户123不存在”，因此业务效果仍然幂等。

天然容易幂等的操作通常是“把状态设置为目标值”：

UPDATE agent_runs
SET status = 'cancelled'
WHERE id = 'run_123';

执行一次和执行十次，最终状态都为cancelled。相反，下面的增量操作不是天然幂等：

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

HTTP方法的规范语义只能提供设计提示：GET、HEAD等安全方法和PUT、DELETE在规范上具有幂等语义，POST则不天然幂等。但最终是否幂等仍取决于服务端业务实现，不能因为接口使用PUT就自动认为安全。

3. 工程上实现幂等的五种方法

3.1 把增量动作改成目标状态

非幂等操作依赖旧值，例如value = value + 1；目标状态操作则让系统收敛到确定结果，例如status = 'completed'。能设计为状态机或资源最终状态时，通常优先采用这种方式。

3.2 使用稳定业务ID和唯一约束

客户端或业务系统为一次逻辑操作生成稳定ID，例如run_id、order_no或payment_no，数据库再为该字段建立唯一约束。相同操作重试时继续使用同一个ID，第二次插入会被数据库原子拒绝。

3.3 使用 Idempotency-Key

POST /agent/runs
Idempotency-Key: 01JXYZ8Y6AQ...

幂等键代表“一次逻辑操作”，而不是“一次网络请求”。网络重试必须复用原Key；如果每次重试都生成新Key，服务端会把它们视为不同业务操作。

3.4 使用状态机和条件更新

UPDATE orders
SET status = 'PAYING'
WHERE id = :order_id
  AND status = 'CREATED';

数据库只有在当前状态允许时才执行转换。通过检查影响行数，可以判断当前请求是否取得执行权。版本号乐观锁也是同类方法：只有持有预期版本的请求能够更新。

3.5 使用 Inbox 对重复消息去重

消息队列通常按至少一次投递设计，消费者必须假设同一个事件会重复送达。以consumer_name + event_id建立唯一约束，并在同一事务中写入Inbox记录和本地业务变更，可以让重复消息安全返回。

4. Idempotency-Key 的完整处理状态机

一个生产级Idempotency-Key机制不能只保存“见过这个Key”。它至少需要记录作用域、请求摘要、执行状态和第一次业务结果。

命中情况

处理方式

Key不存在

原子创建PROCESSING记录并取得执行权

Key存在，request_hash不同

拒绝请求；同一Key不能代表两个业务意图

Key存在，状态为PROCESSING

返回处理中、202或409，或引导查询状态

Key存在，状态为SUCCEEDED

返回第一次的resource_id或已保存响应

Key存在，状态为可重试FAILED

按策略重新取得执行权

Key应限定在明确作用域中：

tenant_id + operation + idempotency_key

如果只使用Key，不同租户或不同接口可能意外冲突。同一个Key对应的请求参数也必须校验。常见做法是把规范化后的请求体计算SHA-256摘要：

import hashlib
import orjson

def request_hash(payload: dict) -> str:
    canonical = orjson.dumps(
        payload,
        option=orjson.OPT_SORT_KEYS,
    )
    return hashlib.sha256(canonical).hexdigest()

请求体Hash不应直接取代客户端生成的幂等键，因为用户可能确实想连续提交两次内容完全相同的任务。正确语义是：幂等键标识业务意图，Hash只用于阻止同一个Key被错误复用于不同参数。

对于异步接口，第一次成功通常表示“Run已经被接受并获得run_id”，不表示整个Agent执行结束。重试同一Key时应返回同一个run_id，真实进度再通过查询接口获得。

5. 数据库并发：为什么必须有唯一约束

下面这种“先查询、再插入”不能保证幂等：

if not await run_exists(run_id):
    await create_run(run_id)
请求A查询：不存在
请求B查询：不存在
请求A插入：成功
请求B插入：也尝试成功

应用层检查和数据库写入之间存在竞态窗口。多进程、多实例环境中，本地锁也无法保护其他实例，因此最终必须依靠数据库的唯一约束、条件更新或其他原子原语。

CREATE UNIQUE INDEX uk_idempotency_scope
ON idempotency_records(
    tenant_id,
    operation,
    idempotency_key
);

PostgreSQL可以使用INSERT ... ON CONFLICT竞争执行权：

INSERT INTO idempotency_records(
    tenant_id,
    operation,
    idempotency_key,
    request_hash,
    status
)
VALUES (:tenant, :operation, :key, :hash, 'PROCESSING')
ON CONFLICT DO NOTHING
RETURNING idempotency_key;

只有拿到RETURNING结果的请求创建了记录并获得执行权。没有拿到结果的请求必须读取已有记录，验证request_hash和状态，而不是继续执行业务。

创建业务记录与把幂等记录标记为SUCCEEDED应尽量放在同一个本地数据库事务中。这样数据库提交后即使HTTP响应丢失，重试请求仍能读取之前保存的业务结果。

6. Python、FastAPI 与 SQLAlchemy 实现

幂等记录可以包含以下字段：

class IdempotencyRecord(Base):
    __tablename__ = "idempotency_records"

    tenant_id: Mapped[str]
    operation: Mapped[str]
    key: Mapped[str]
    request_hash: Mapped[str]
    status: Mapped[str]
    resource_id: Mapped[str | None]
    response_body: Mapped[dict | None]

    __table_args__ = (
        UniqueConstraint(
            "tenant_id",
            "operation",
            "key",
            name="uk_idempotency_scope",
        ),
    )

FastAPI接口的核心流程如下。示例省略了具体Repository实现，但事务边界和状态判断不能省略。

@app.post("/agent/runs")
async def create_agent_run(
    request: CreateRunRequest,
    idempotency_key: str = Header(alias="Idempotency-Key"),
    session: AsyncSession = Depends(get_session),
):
    payload_hash = request_hash(request.model_dump())

    async with session.begin():
        inserted = await try_insert_idempotency_record(
            session,
            tenant_id=request.tenant_id,
            operation="create_agent_run",
            key=idempotency_key,
            request_hash=payload_hash,
        )

        if not inserted:
            record = await get_idempotency_record(
                session,
                request.tenant_id,
                "create_agent_run",
                idempotency_key,
            )

            if record.request_hash != payload_hash:
                raise HTTPException(409, "幂等键对应了不同请求")

            if record.status == "SUCCEEDED":
                return record.response_body

            if record.status == "PROCESSING":
                raise HTTPException(409, "请求正在处理中")

        run = AgentRun(
            id=generate_run_id(),
            tenant_id=request.tenant_id,
            status="queued",
        )
        session.add(run)

        response = {
            "run_id": run.id,
            "status": "queued",
        }

        await mark_idempotency_succeeded(
            session,
            request.tenant_id,
            "create_agent_run",
            idempotency_key,
            run.id,
            response,
        )

    return response

这里最重要的是：业务记录和幂等执行结果在同一个事务中提交。若事务失败，两者都不生效；若事务成功但响应丢失，下一次重试读取SUCCEEDED记录并返回第一次结果。

长时间Agent Loop不应该在这个事务里运行。接口只原子完成“创建Run、写queued状态、写Outbox事件、保存幂等结果”，然后尽快返回202 + run_id。

7. 为什么不能只用 Redis 保存幂等键

Redis可以用于快速拦截重复请求，但如果业务数据保存在关系数据库中，单独依赖Redis无法自动保证跨系统原子性。

执行顺序

失败结果

先写Redis成功，数据库失败

重试被误判为已经执行，但业务记录不存在

数据库成功，写Redis失败

重试无法看到Key，可能重复创建业务记录

Redis Key提前过期

迟到的重试再次穿透并执行业务

Redis故障或主从切换丢数据

幂等判定失去可靠依据

因此Redis适合作为缓存、限流或前置过滤，真正的业务唯一性仍应由业务数据库唯一约束、状态机或下游业务ID保证。跨服务场景则需要Outbox、Inbox、稳定业务ID和下游幂等能力共同完成。

8. 最困难的窗口：外部调用成功，本地记录失败

最困难的情况不是本地数据库事务，而是外部系统已经成功，本地却来不及保存结果。

Agent调用发送邮件Tool
  → 邮件服务发送成功
  → Agent准备保存Tool结果
  → Worker突然崩溃
  → Checkpoint只看到步骤未完成
  → 恢复后再次发送邮件

这时本地系统无法仅凭自己的数据库判断邮件是否已经发送。最佳方案是为每次副作用调用生成稳定的tool_call_id，并把它作为下游幂等键：

await mail_service.send(
    idempotency_key=tool_call_id,
    to=user_email,
    content=content,
)

下游服务应保证同一个tool_call_id只产生一次业务效果。支付、发邮件、创建飞书文档、提交代码、创建云资源和删除数据等Tool都属于有副作用工具。

如果下游不支持幂等键，可以使用可查询的外部业务ID，在恢复时先查询结果；仍无法判断时，应把步骤标记为UNKNOWN并执行对账或人工确认，而不是盲目重试不可逆操作。

这揭示了一个边界：本地幂等记录只能保护本地副作用。端到端幂等需要调用链上的每个有副作用系统共同支持，或者提供可靠查询和补偿机制。

9. 消息队列中的 Inbox、Outbox 与 effectively once

消息系统中的“恰好一次”需要拆开理解。消息可能因为确认丢失而重复投递，因此可靠做法通常是“至少一次投递 + 幂等处理”，得到业务上的effectively once。

9.1 Outbox：本地状态和发消息保持一致

在创建Agent Run的同一个数据库事务中，同时写入业务表和Outbox表：

BEGIN
  → INSERT agent_runs
  → INSERT outbox_events
COMMIT

独立Publisher不断扫描Outbox，把事件发送到消息队列；发送失败可以重试。这样不会出现“业务提交了但消息永远没发出”，也不会要求数据库和消息队列参加同一个分布式事务。

9.2 Inbox：消费者对重复消息去重

CREATE TABLE consumed_events (
    consumer_name TEXT NOT NULL,
    event_id TEXT NOT NULL,
    consumed_at TIMESTAMP NOT NULL,
    UNIQUE (consumer_name, event_id)
);

消费者在一个事务中先原子写入Inbox记录，再执行本地业务更新。若唯一约束冲突，说明该消费者已经处理过该事件，可以直接确认消息。

机制

解决的问题

Outbox

本地数据库提交与“最终发出事件”之间的一致性

Inbox

消息重复投递导致消费者重复执行业务

业务唯一约束

即使去重代码并发失效，数据库仍不产生重复业务结果

所谓端到端Exactly Once通常依赖非常严格的边界。跨数据库、消息队列、第三方API和用户设备时，更现实的目标是允许传输和代码重复执行，但让业务副作用只生效一次。

10. PROCESSING 状态、租约与崩溃恢复

如果服务端写入PROCESSING后进程崩溃，记录可能永久停留在处理中。长任务不能只靠一个没有期限的布尔状态。

status = PROCESSING
owner_token = worker_abc
locked_until = 10:30:00
fencing_token = 42

租约。locked_until表示当前Worker的执行权到何时有效。租约过期后，其他Worker才有资格尝试接管。

Owner Token。只有持有当前Owner Token的Worker才能续租或提交结果，避免无关Worker误更新。

Fencing Token。每次接管都递增版本号。下游写入只接受更大的Token，可以阻止失去租约的旧Worker恢复后继续覆盖新结果。

租约过期不自动证明旧Worker已经停止，也不证明外部副作用没有发生。接管前仍要判断操作是否可安全重试、是否存在可查询的外部业务ID，以及是否需要对账。

对于短HTTP事务，通常不应保持长时间PROCESSING锁；对于长时间Agent任务，应把“请求已接受”“Run正在执行”“某一步Tool是否完成”拆成不同状态机，并通过Checkpoint持久化。

11. 幂等窗口与记录过期时间

幂等记录通常不能无限保存，但TTL也不能随意设置。假设记录只保留5分钟，而离线客户端在10分钟后重试，同一个业务操作就可能被当成新请求。

幂等窗口至少要覆盖：

  • 客户端SDK和人工操作可能持续重试的最长时间。
  • 网关、服务端和RPC层的总重试时间。
  • 消息队列的最大重投与死信恢复时间。
  • 离线设备恢复后可能重新发送请求的时间。
  • 业务允许判断“重复提交”的周期。

需要区分两类数据：

数据

保留策略

响应缓存、HTTP状态码

可以按合理幂等窗口设置TTL

订单号、支付号、run_id等业务唯一身份

通常应长期保留唯一约束

即使Idempotency-Key响应缓存过期，也不应因此删除真正的业务唯一性，否则较晚的重试仍可能重复产生核心副作用。

12. AI Agent 平台的三层幂等设计

AI Agent平台至少需要三层幂等，每层负责不同的重复来源。

层级

稳定身份

防止的重复

创建Run

client_operation_id / Idempotency-Key

HTTP超时重试创建两个Run

消息消费

consumer_name + event_id

队列重复投递启动两个Worker执行

Tool调用

run_id + step_id + tool_call_id

Checkpoint恢复后重复执行外部副作用

用户操作ID
  → run_id
    → step_id
      → tool_call_id
        → 外部系统业务ID

每一级都需要稳定身份，系统才能回答“这次逻辑操作以前是否执行过”。

创建Run。POST /agent/runs使用幂等键，首次提交创建queued记录并返回run_id；相同Key重试始终返回同一个run_id。

Worker执行。队列事件包含稳定event_id，Worker通过Inbox去重。Run状态转换使用条件更新，防止两个Worker同时取得同一任务。

Tool调用。在调用有副作用Tool之前持久化tool_call_id和调用意图；调用完成后保存外部结果。恢复时优先查询已有结果或向下游复用相同幂等键。

LLM调用。大模型输出可能不确定，重复调用还会产生额外成本。虽然它通常不像支付那样修改外部业务状态，也应按照run_id、step_id和attempt记录调用，明确哪些失败允许重试、是否复用已成功结果。

对于删除资源、发送消息、提交代码等高风险Tool，幂等不能代替权限、审批和审计。幂等只回答“重复执行是否产生第二次效果”，不回答“第一次执行是否应该被允许”。

13. 常见错误

  1. 重试时生成新Key。服务端会把每次请求视为新业务操作。
  2. 把请求体Hash直接当Key。用户可能确实想创建两个内容相同的任务，Hash只能校验参数，不能自动代表业务意图。
  3. 只做先查询再插入。并发请求仍可能同时通过检查。
  4. 只使用进程内锁。多Worker和多实例之间无法共享本地锁。
  5. Key没有租户与操作作用域。不同租户或接口可能错误冲突。
  6. 同一Key允许不同参数。重试可能拿到与当前请求不匹配的旧结果。
  7. 业务提交与幂等记录分开写。崩溃窗口会造成业务成功但去重状态不存在。
  8. 只用Redis去重。Redis和业务数据库之间没有天然原子提交。
  9. 把超时当成未执行。超时恰恰是执行结果最不确定的情况。
  10. 把幂等当成Exactly Once。网络包、消息和代码仍可能执行多次，幂等只控制业务副作用。
  11. 永久保留PROCESSING。进程崩溃后请求会永远无法恢复。
  12. 幂等记录TTL过短。迟到重试会穿透并重新执行。

15. 面试回答

幂等在工程上主要解决超时后的结果不确定性。客户端没有收到响应，并不能判断服务端是否已经提交，所以重试可能造成重复扣款、重复创建任务或重复发送消息。

常见实现方式包括把操作设计成设置目标状态、使用稳定业务ID和数据库唯一约束、为POST接口增加Idempotency-Key、使用状态机条件更新，以及在消息消费者中使用Inbox去重。Idempotency-Key需要按租户和接口限定作用域，并保存request_hash、PROCESSING或SUCCEEDED状态以及第一次结果；同一个Key对应不同参数必须拒绝。

业务记录与幂等结果应在同一个数据库事务中提交，不能只依赖“先查询再插入”或Redis。跨服务调用时，最难的是外部副作用已经成功、本地记录却失败，因此还要把稳定tool_call_id传给下游作为幂等键，或者通过外部业务ID查询和对账。

在Agent平台中，我会分别保证创建Run、消息消费和Tool调用三层幂等。消息链路采用Outbox保证业务提交后最终发出事件，采用Inbox应对重复投递，从而以至少一次传输配合幂等处理获得业务上的effectively once。
