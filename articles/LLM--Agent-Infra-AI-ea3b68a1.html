LLM 应用 / Agent Infra / AI 平台秋招八股清单（简历反推版）

本文根据《曹然-LLM-Agent-AI平台-秋招简历(4)》逐项反推面试知识点。它不是一份平均用力的通用八股目录，而是一张“简历写了什么，就必须能讲到什么深度”的准备地图。

每个写进“我的职责”的关键词，至少要能连续回答五层：它是什么、项目里怎样实现、为什么这样设计、失败时怎样处理、用什么证据验证。

1. 核心判断：这份简历会把面试引向哪里

这份简历的优势是工程密度高：它写了架构拆分、隔离、安全、状态机、云原生迁移和可量化结果。相应的风险是，面试官不会满足于“我用过某个框架”，而会沿着机制、边界和故障场景连续追问。

最主要的四条追问主线是：Agent 如何执行和保存状态；后端服务如何处理并发与分布式失败；沙箱、鉴权和多租户怎样建立真正的安全边界；大模型应用如何做检索、约束生成、评测和推理服务。

因此，准备策略不是平均背完整套语言语法，而是先把简历承诺的机制讲透，再补大厂通用基础和 AI Infra 加分项。每个模块都应能画出真实架构或时序图，并给出至少一个实际故障案例。

3. Agent Loop、LangGraph 与 Multi-Agent

必须掌握的主干

Agent Loop 至少包含输入与状态读取、模型决策、工具执行、结果观察、状态更新和终止判断。循环不是越长越智能，必须有最大步数、Token、时间和费用预算，并能在证据不足、越权或连续失败时安全停止。

LangGraph 需要讲清 Graph State、Node、Conditional Edge、Reducer、Checkpoint、Interrupt/Resume 和持久化之间的关系。尤其要知道：节点重试可能再次执行带副作用的工具，因此 Checkpoint 只能恢复状态，不能天然保证外部操作恰好执行一次。

Multi-Agent 追问

Leader、Diagnostician、Fixer 和 Verifier 的价值不在于拥有四段不同 Prompt，而在于职责、上下文和运行时权限真正隔离。需要说明任务如何委派、结果如何汇总、共享状态由谁提交，以及 Sub-Agent 的工具、递归深度、Token 和时间怎样受限。

高频追问：同一个模型既修复又验证是否存在自证偏差？Verifier 凭什么可信？两个 Agent 同时更新状态如何避免覆盖？工具已经成功但节点超时重试怎么办？

Token Budget 需要在系统指令、当前问题、历史消息、Skill、检索结果和工具输出之间分配。保持 Prompt 前缀稳定有利于复用前缀缓存，但不能为了缓存而保留已经失效的信息。

异步 Memory 写入必须处理重复抽取、并发覆盖、旧事实更新、删除请求和跨用户污染。“原子持久化”需要落实为数据库事务、唯一键、版本号或 CAS，而不是一个抽象形容词。

Trace 与评测

Trace 应记录模型调用、工具调用、状态变化、耗时、Token、错误和关联 ID；日志用于事件细节，指标用于聚合趋势，Trace 用于跨组件还原链路。Agent 评测至少区分任务成功率、工具成功率、步骤数、成本、延迟、越权率和人工接受率。

简历中的 QPR 需要定义分子、分母、候选筛选规则和样本范围。创建 PR 不等于修复成功；还应说明测试通过、维护者接受或最终合并等更严格指标。

6. Python 并发、FastAPI 与 ContextVar

Python 并发模型

必须能区分进程、线程和协程，解释 GIL 限制的是同一 CPython 进程内多个线程并行执行 Python 字节码，而不是“Python 不能并发”。I/O 型任务适合协程或线程，CPU 型 Python 计算通常需要多进程、原生扩展或外部计算服务。

async def 不会自动让代码非阻塞。协程内部调用阻塞数据库驱动、文件操作或 CPU 密集函数，仍会阻塞事件循环。需要掌握事件循环、I/O 多路复用、任务取消、超时、背压和协程泄漏。

FastAPI 服务模型

需要区分 WSGI 与 ASGI，理解 Uvicorn、Gunicorn 和多 Worker 的关系。多 Worker 是多个进程，内存状态不会自动共享；可靠后台任务不能只依赖进程内 BackgroundTask。

还要掌握同步路由与异步路由如何执行、依赖注入、Middleware、生命周期钩子、流式响应、客户端断开、连接池和优雅关闭。

ContextVar 的边界

ContextVar 适合在同一异步调用链中传递请求上下文，但它不负责验证身份，也不会自动跨线程池、子进程或 gRPC 调用传播。可信 user_id 必须由认证层建立，跨服务传播还需要签名凭证或受信任的元数据与服务间认证。

需要能从 DNS、TCP、TLS、HTTP、Nginx、FastAPI、gRPC、数据库一直讲到响应返回，并解释 Keep-Alive、连接池、超时、重试、四层与七层负载均衡。

WebSocket 只提供字节流或消息传输能力，不天然保证 exactly-once。per-topic cursor 需要与事件 ID、去重记录、顺序规则和历史补偿结合；慢消费者还需要缓冲上限、合并更新或丢弃策略。

需要掌握 Protobuf、HTTP/2、Unary/Streaming、deadline、cancel、status code、拦截器和连接复用。任何自动重试都必须结合幂等性；鉴权服务不可用时还要明确 fail-open 还是 fail-closed。

PostgreSQL 基础

需要掌握 SQL 从解析、优化、执行到存储的路径，B+ 树、联合索引、最左前缀、覆盖索引、执行计划、连接池、事务、隔离级别、锁、死锁和 WAL。

SQLAlchemy

需要区分 Engine、Connection 和 Session；解释连接池、Unit of Work、Identity Map、flush、commit、rollback、懒加载、预加载与 N+1。Session 和 AsyncSession 都不应被多个并发任务随意共享。

9. 分布式任务、状态机与可靠性

任务状态机

“任务创建→Handler 路由→Argo/Serverless 提交→状态轮询→结果回写”需要有明确状态、合法迁移、终态和错误状态。两个 Worker 同时迁移同一 Run 时，应使用版本号、条件更新或 CAS 防止覆盖。

失败与恢复

最典型的问题是：外部 Workflow 已提交成功，但数据库回写失败。解决思路包括稳定的业务任务 ID、记录外部 Workflow ID、幂等提交、定期 reconcile 和人工可审计的恢复入口。

网络系统很难提供真正的 exactly-once。工程上通常接受至少一次投递，再通过幂等键、去重表、状态查询和补偿，让业务效果接近“只发生一次”。重试需要 deadline、指数退避、随机抖动和上限。

Reaper、Lease 与 Heartbeat

Reaper 不能只看“超过某个时间”就认定任务死亡，否则会回收仍在运行但心跳延迟的任务。需要 lease 到期、心跳版本、所有权校验和幂等回收，并允许后续状态对账。

事件日志与 Event Sourcing

记录状态变化事件不等于事件溯源。只有当前状态能够以事件序列为主要事实源重建，才适合称为 Event Sourcing。面试时必须准确说明项目实际采用哪一种。

跨服务一致性

还应掌握消息队列、Outbox、幂等消费、死信队列、Saga 和补偿操作。控制面与计算面拆分会带来故障隔离，也会增加网络失败、状态同步和分布式事务成本。

10. 身份认证、Casbin、多租户与 Secret

认证与授权

Authentication 回答“你是谁”，Authorization 回答“你能做什么”。需要掌握 Session、Cookie、JWT、OAuth、Magic Link 的边界。Magic Link 必须有短有效期、一次性消费、防重放、用户绑定和 redirect 白名单。

Casbin

需要能写出项目真实的 PERM 元模型：request_definition、policy_definition、role_definition、policy_effect 和 matcher，并给出 owner/member 在多租户 Domain 下的策略例子。还要说明 Enforce(sub, obj, act) 位于哪一层、策略从哪里加载、如何缓存和更新。

把 Casbin 独立成 Go gRPC 服务会获得语言无关和集中策略管理能力，也会引入网络延迟与单点风险。鉴权超时通常应 fail-closed；若为了可用性选择缓存，必须说明缓存过期、策略更新和撤权传播。

“完成 141 个项目策略迁移与核验”不能只证明数量一致。应能说明映射规则、去重、回滚、owner/member 操作矩阵，以及是否使用新旧鉴权 shadow comparison 验证语义兼容。

可信身份与多租户

请求参数里的 user_id 不可信；必须由登录态、签名 Token 或可信身份提供者建立内部身份。ContextVar 只负责传播，不负责认证。租户隔离还要覆盖数据库查询、对象存储 Key、目录、Sandbox、Memory、缓存和审计日志。

Secret 与预签名上传

需要掌握最小权限、Secret 轮换、日志脱敏和环境变量泄漏渠道。Kubernetes Secret 默认的 Base64 表示并不等于加密。TOS 预签名 URL 还应限制方法、对象 Key、有效期、文件大小与类型，并在上传后核验对象和校验和。

11. Sandbox、Linux、Docker 与安全边界

容器隔离的底层机制

Docker 主要组合 namespace、cgroup、文件系统、capability 和网络规则。namespace 隔离进程、挂载、网络等视图，cgroup 限制 CPU、内存和进程数量；seccomp 限制系统调用，capability drop 缩小 root 权限。

执行不可信代码时还应使用非 root 用户、只读根文件系统、临时工作区、CPU/内存/PID/磁盘限制、网络出口控制、执行超时和进程组终止。不能挂载 Docker Socket，也不能把宿主机敏感目录直接写入容器。

容器复用

按 user/project/thread 复用容器可以降低冷启动，但必须定义复用键、并发模型、工作目录、残留进程、缓存、环境变量和 Secret 的清理策略。空闲回收与新请求并发发生时，需要引用计数、租约或状态机避免误删正在使用的环境。

路径安全

只拒绝 ../ 不足以防路径穿越。需要处理绝对路径、URL 编码、规范化、符号链接和检查后替换的 TOCTOU 竞态；最终访问路径必须落在允许根目录内，并尽量使用操作系统提供的安全打开方式。

必须避免的错误表述

  • “用了 Docker，所以已经实现绝对安全隔离。”
  • “超时后杀掉父进程，所有子进程就一定结束。”
  • “把 Secret 从日志里替换掉，就不会泄露。”
  • “路径字符串以前缀开头，就一定在目标目录内。”

Kubernetes 基础对象

必须掌握 Pod、Deployment、Service、Ingress、ConfigMap、Secret、Job、Namespace 的职责，以及服务发现、容器网络、资源 requests/limits 和 OOMKilled。

探针与滚动发布

Argo Workflow 与 Serverless

需要讲清 DAG、步骤依赖、产物、重试、取消和任务状态。Argo 更适合可观察的 Kubernetes 工作流，Serverless 适合按需弹性和免运维执行；选择时要比较冷启动、最长运行时间、GPU 资源、成本和调度约束。

CI/CD 与镜像

从 commit 到发布应绑定 commit SHA、镜像 digest、配置版本和验证报告。要掌握多阶段构建、依赖锁定、ARM 构建 linux/amd64 镜像、多架构差异、镜像扫描、回滚和 smoke test。滚动发布成功不等于业务回归通过。

简历中的“基础设施 Owner”意味着还要能画出 VPC、子网、入口、VKE、CR、TOS、RDS、Redis 的实际拓扑，并解释容量、备份、RPO/RTO、切流和回滚决策。

13. RAG、BGE-M3 与约束解码

BGE-M3 与向量召回

需要知道 BGE-M3 支持 dense、sparse 和 multi-vector 表达，并明确项目实际使用哪一种。简历写了余弦召回，就要能写出余弦相似度公式，解释 L2 归一化后余弦与点积的关系。

Chunk 大小和 overlap 是召回粒度与语义完整性的权衡。还需要掌握 Top-K、ANN、Reranker，以及 Recall@K、MRR、人工标注和困难负样本。不能只用几个演示案例证明检索效果。

约束解码

Logits Mask 通常在采样前把当前语法状态下非法 Token 的分数屏蔽，使 softmax 后无法选中。难点是 Token 并不等于单个字符，一个 Token 可能包含多个 JSON 字符，因此需要基于 Tokenizer 和合法前缀状态计算可选集合。

普通有限状态机不天然表达无限层嵌套结构。项目必须说清采用的是受限 Schema、有限深度展开，还是额外维护栈或解析器状态。约束解码能提高语法或 Schema 合法率，却不能保证字段内容真实正确。

必须准备的实验口径

至少记录格式成功率、平均重试次数、每 Token 额外开销、端到端延迟，以及检索的 Recall@K 和生成忠实度。docxtpl 流水线还应说明字段缺失、表格循环、图片、单任务失败隔离和批量重试。

算法边界、Tokenizer 处理、真实评测集和前后对比指标

如果某个词只是方向性设计、尚未真正落地，应在面试中明确区分“已实现”“已验证”“设计方案”和“未来计划”。宁可缩小表述，也不要让面试官发现项目名词与真实证据不匹配。

六条边界结论：Docker 不等于绝对隔离；WebSocket 不保证 exactly-once；ContextVar 不自动跨线程、进程和服务；Prompt 中的 allowed-tools 不等于授权；Kubernetes Secret 默认不等于密文存储；创建 PR 不等于修复成功。
