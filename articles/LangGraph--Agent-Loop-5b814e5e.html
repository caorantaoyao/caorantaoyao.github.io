LangGraph：把 Agent Loop 工程化为可持久化状态图

1. 从 Agent Loop 到 LangGraph

核心结论：LangGraph 不是大模型，也不是新的 RAG 技术。它是一个低层 Agent 编排框架与运行时，用 State、Node 和 Edge 把 Agent Loop 显式建模，并补上持久化、暂停恢复、人机协作和故障恢复等生产能力。

如果把模型看成负责判断下一步的“大脑”，LangGraph 更像负责组织整个任务的“执行控制器”。它既能运行完全确定性的业务步骤，也能在局部节点中调用大模型，让模型根据 Observation 动态选择工具和路径。

Agent Loop：决策 → 行动 → 观察 → 更新状态 → 继续或结束
LangGraph：Node → Edge → Node → 更新 State → 下一轮

因此，Agent Loop 是一种设计思想，LangGraph 是帮助开发者实现这种思想的工程框架。它可以独立使用，也可以配合 LangChain 的模型、工具和检索组件使用。

2. 为什么需要 LangGraph

最简单的 Agent 可以直接写成一个 while 循环：

while True:
    decision = model.decide(state)

    if decision.is_final:
        break

    result = execute_tool(decision.tool)
    state.update(result)

这个版本适合学习，但进入生产环境后会立即遇到新的问题：进程崩溃后怎样恢复；用户审批期间怎样暂停几个小时；多个分支怎样并行并合并结果；工具超时后应该重试、换方案还是结束；如何查看每一步 State；多个子 Agent 怎样协作；以及写数据库节点恢复时被重复执行怎么办。

LangGraph 的价值不是让模型变聪明，而是把这些运行时问题显式化。开发者可以看见每个节点、每次状态变化和每条控制路径，并为循环设置最大步数、权限、预算、错误处理和 Evidence Gate。

如果任务只是一次模型调用、一次 RAG 检索或非常简单的工具调用，直接使用普通函数或高层 Agent 通常更省事；只有当控制流、状态和恢复开始复杂时，LangGraph 的优势才明显。

3. 核心抽象：State、Node 与 Edge

LangGraph 的核心可以记成一句话：State 保存当前快照，Node 做事情，Edge 决定下一步。

抽象

作用

典型内容

State

保存当前任务快照

消息、计划、Observation、预算、错误和最终结果

Node

执行一个计算或副作用

调用 LLM、查询数据库、执行工具、权限校验

Edge

决定下一个节点

固定跳转、条件分支、循环、并行扇出

START / END

虚拟入口与终点

标记图从哪里开始、在哪里结束

Reducer

合并同一字段的状态更新

覆盖旧值、追加消息、合并并行结果

Command

同时更新状态和控制跳转

update、goto、resume、父图导航

State。通常用 TypedDict、Dataclass 或其他 Schema 定义。它不是任意共享全局变量，而是运行时管理的状态快照。节点通常只返回需要更新的字段。

Node。本质是同步或异步 Python 函数。它可以调用 LLM，也可以只是普通代码，因此 Node 不等于模型。

Edge。普通 Edge 表示固定跳转，Conditional Edge 根据 State 选择下一节点。如果同一个节点路由到多个目标，它们可以在下一轮并行执行。

Reducer。默认更新通常覆盖旧值。如果消息列表需要追加、并行节点需要同时写入结果，就必须定义正确的 Reducer，否则可能丢数据或发生更新冲突。

4. 一张 Graph 是怎样执行的

构建时先定义 State Schema，再添加 Node 和 Edge，最后调用 compile() 得到可执行图。编译阶段会检查图结构，并接入 Checkpointer、缓存、调试等运行能力。

START
  ↓
model_node：模型判断下一步
  ├─ 产生工具调用 → tool_node → Observation → model_node
  ├─ 需要审批 → review_node → 暂停与恢复
  └─ 生成最终答案 → verifier_node → END

LangGraph 的执行受到 Pregel 风格的 super-step 启发。可以把一个 super-step 理解为图的一次“时钟跳动”：运行时确定本轮被激活的节点，让可以并行的节点执行，再合并它们产生的状态更新，然后进入下一轮。

顺序节点属于不同 super-step，并行节点属于同一个 super-step。同一轮的并行节点通常读取相同的旧状态，它们的更新会在该轮结束时按 Reducer 合并。因此，并行写同一字段时必须提前设计合并规则。

只要后续 Edge 再次指向前面的节点，图就会形成循环，所以 Graph 不等于 DAG。当没有节点继续被激活，或执行到 END 时，图才结束。生产系统还应设置执行步数、时间、Token 和费用上限，避免无限循环。

5. Python：最小可运行示例

下面的例子不调用真实模型，而是专门展示 StateGraph、条件分支、Checkpoint、Interrupt 和恢复机制。删除类操作会先进入人工审批。

from typing import Literal
from typing_extensions import NotRequired, TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, interrupt


class State(TypedDict):
    action: str
    approved: NotRequired[bool]
    result: NotRequired[str]


def normalize(state: State):
    return {"action": state["action"].strip()}


def route(state: State) -> Literal["review", "execute"]:
    if state["action"].lower().startswith("delete"):
        return "review"
    return "execute"


def review(state: State) -> Command[Literal["execute", "cancel"]]:
    approved = interrupt({
        "question": "是否批准这个操作？",
        "action": state["action"],
    })

    return Command(
        update={"approved": bool(approved)},
        goto="execute" if approved else "cancel",
    )


def execute(state: State):
    # 教学示例，不执行真实删除
    return {"result": f"已执行：{state['action']}"}


def cancel(state: State):
    return {"result": "操作已取消"}


builder = StateGraph(State)
builder.add_node("normalize", normalize)
builder.add_node("review", review)
builder.add_node("execute", execute)
builder.add_node("cancel", cancel)

builder.add_edge(START, "normalize")
builder.add_conditional_edges("normalize", route)
builder.add_edge("execute", END)
builder.add_edge("cancel", END)

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "demo-1"}}

# 第一次运行在 review 节点暂停
paused = graph.invoke(
    {"action": "delete temporary files"},
    config,
)
print(paused["__interrupt__"])

# 使用相同 thread_id 恢复
result = graph.invoke(Command(resume=True), config)
print(result["result"])

执行关系是 START → normalize → review / execute → END。真实 Agent 只需要把 normalize 或其他决策节点替换成模型调用，并把工具结果写回 State，就可以形成工具调用循环。

InMemorySaver 只适合学习和测试，进程退出后数据会消失。生产环境应使用数据库支持的持久化 Checkpointer。

6. Checkpointer、Thread 与 Store

LangGraph 中需要区分线程级状态和跨线程长期记忆。

机制

保存内容

典型用途

Checkpointer

某个 Thread 的 Graph State 快照

对话连续性、暂停恢复、故障恢复、Time Travel

Store

应用定义的跨 Thread 数据

用户偏好、稳定事实、共享知识、长期记忆

Graph 编译时接入 Checkpointer，调用时通过 thread_id 标识一条连续任务：

graph = builder.compile(checkpointer=checkpointer)

config = {
    "configurable": {
        "thread_id": "task-123",
    }
}

graph.invoke(input_state, config)

复用同一个 thread_id，运行时就能找到这一任务之前的 Checkpoint；换一个 ID 则创建新的独立 Thread。可以把 Thread 理解为“这条会话或任务的持久游标”，但它不等于操作系统线程。

Checkpointer 保存的是当前运行的短期状态，例如消息、计划、工具结果和待审批动作。Store 保存的是跨任务仍值得使用的信息。长期 Memory 不应全部注入每轮 Context，而应根据当前节点检索和选择。

7. Interrupt、Command 与人工审批

interrupt(value) 用于在节点内部动态暂停执行。它特别适合删除、支付、生产发布、发送外部消息等需要人工确认的动作。

  1. 节点调用 interrupt()，并提供 JSON 可序列化的审批信息。
  2. Checkpointer 保存当前 Graph State。
  3. 调用方收到中断信息，向用户展示。
  4. 用户作出决定后，使用同一个 thread_id 调用 Command(resume=...)。
  5. 恢复值成为节点中 interrupt() 的返回值，图继续路由。

Command 是统一的控制对象：update 更新 State，goto 指定下一个节点，resume 恢复中断，graph 可用于从子图导航到父图。

return Command(
    update={"status": "approved"},
    goto="execute",
)

同一个节点最好只选择一种动态路由方式。如果节点返回 Command(goto=...)，又为它配置普通静态出边，两条路径可能同时执行。

关键细节：恢复后并不是从 Python 的 interrupt() 下一行原地继续，而是包含该中断的节点从开头重新执行。因此，中断前的副作用必须可幂等；也不要用普通 try/except 吞掉 LangGraph 用来触发暂停的内部中断信号。

8. Durable Execution、恢复与幂等

Durable Execution 表示任务的执行进度被持久化。进程故障、人工暂停或长时间等待之后，可以从已保存的状态继续，而不必从整个任务的第一步重做。

它不等于保存 Python 调用栈，也不是代码行级续跑。Checkpoint 通常位于图的执行边界，恢复时相关节点可能重新运行。因此必须把“内部状态恢复”和“外部副作用一致性”分开理解。

加载最近 Checkpoint
  ↓
发现上一次写操作状态未知
  ↓
使用幂等键或业务请求 ID 查询外部系统
  ├─ 已成功：复用原结果
  ├─ 未执行：安全执行
  └─ 无法判断：人工处理或补偿

付款、创建订单、发送消息、创建容器和提交任务都不能因为超时而直接重试。客户端没有收到响应，不代表服务端没有执行。可靠做法包括幂等键、Upsert、read-before-write、请求去重表、状态查询和补偿操作。

如果一个节点内部包含多个昂贵或非确定性操作，可以把它们拆成更小节点，或使用可被 Checkpointer 记录结果的 Task。这样恢复时可以跳过已完成工作，降低重复调用风险。

持久化策略本身还存在可靠性与性能权衡：越频繁、越同步地保存，恢复窗口越小，但写入开销越高。选择策略时要结合任务价值、节点耗时和允许重复的范围。

9. 并行、Send、Subgraph 与多 Agent

如果一个节点拥有多个普通出边，多个目标节点可以在下一 super-step 并行执行。例如诊断服务故障时，可以同时查询指标、日志和 Trace，再把结果汇总。

diagnose
  ├─ get_metrics ─┐
  ├─ search_logs ─┼→ aggregate → planner
  └─ read_traces ─┘

并行节点通常读取同一份输入 State，所以不能依赖另一个并行节点在本轮刚写入的值。它们的结果要在 super-step 结束时通过 Reducer 合并。并发修改同一外部资源时还需要锁、版本号或串行化，Reducer 只能合并内部 State，不能解决外部竞态。

Send。当并行分支数量在运行前未知时，可以动态返回多个 Send。例如模型先生成十个研究问题，再为每个问题启动一个检索节点，最后进行 Map-Reduce 汇总。

Subgraph。子图是作为父图一个节点使用的另一张图，适合模块复用和多 Agent 编排。父子图共享 State 字段时可以直接通信；Schema 不同时，应在父节点中显式完成输入和输出映射。

多 Agent。可以把代码诊断 Agent、数据库 Agent 和文档 Agent 分别做成子图，再由 Supervisor 根据任务分派。但 Subgraph 首先是执行模块，不一定等于 Agent；普通确定性流程也可以封装成子图。

子 Agent 是否保留跨调用状态应显式设计。临时子任务可以每次隔离；需要连续对话或长期任务的子 Agent 才需要按 Thread 持久化自己的状态。

10. Streaming、Time Travel 与可观测性

Streaming。LangGraph 可以在图运行期间持续输出事件，而不是等整张图结束才返回。前端可以接收模型 Token、节点状态更新、工具进度、中断请求和任务完成事件。Streaming 是运行事件的投影层，不会改变图本身的执行语义。

在 Web 应用中，后端通常把这些事件通过 SSE 或 WebSocket 推送给浏览器。用户看到“正在检索、正在执行工具、等待审批”时，本质上是在订阅 Graph Run 的事件流。

Time Travel。有 Checkpoint 历史后，可以查看过去状态、从某个历史 Checkpoint 重放后续执行，或者修改历史状态后 Fork 出新分支。它适合调试 Agent 为什么走错路径、比较不同提示词或人工修正某一步。

Time Travel 也不是代码行级回滚。Checkpoint 之后的模型调用、API 调用和 Interrupt 可能重新发生，因此仍要遵守幂等和可重放约束。

可观测性。一次运行至少应记录 run_id、thread_id、节点名称、状态版本、路由结果、模型与工具耗时、Token、费用、错误、重试和最终停止原因。聚合后可观察任务成功率、平均步数、重复调用率、人工介入率和 P95 延迟。

LangSmith 可以用于 Trace、调试和评测，但 LangGraph 并不强制必须使用 LangSmith；也可以接入自己的 OpenTelemetry、日志和指标系统。

如果只需要常见的 Tool Calling Loop，高层 Agent 能减少样板代码。需要自定义 State、复杂条件分支、人工审批、多个子 Agent 或持久化恢复时，才值得直接编写 LangGraph。

生产架构通常不是“Workflow 或 Agent 二选一”，而是确定性外层与动态内层结合：初始化、权限、预算、验收和发布使用确定性节点；诊断、检索、规划等路径不确定的步骤由模型驱动。

LangGraph 解决的是 Agent 编排，不是通用业务系统的全部问题。纯审批、ETL、财务结算等完全确定性的长事务，传统工作流引擎或普通状态机可能更合适。

12. 在 AI Agent 平台中的架构位置

在你的 AI Agent 运行平台中，可以把 LangGraph 放在“单次 Agent Run 的编排层”，而不是让它包办整个平台。

HTTP / WebSocket API
  ↓
任务队列与 Worker 调度
  ↓
LangGraph：单次 Run 的状态与控制流
  ├─ load_context
  ├─ planner
  ├─ tool_executor → observe → planner
  ├─ human_review → interrupt
  ├─ verifier
  └─ finalizer / safe_stop
  ↓
工具服务、数据库、沙箱容器、第三方 API

Graph State。保存消息、当前计划、Observation、Artifact 引用、待执行动作、预算消耗、错误次数和任务状态。大型日志、文件和模型输出应放在对象存储或数据库中，State 只保存摘要和引用。

Runtime Context。user_id、tenant_id、角色、授权范围、模型配置和数据库连接等可信信息应来自后端运行上下文，而不是由模型可修改的 State 决定。每次工具执行仍要重新做身份、权限和租户校验。

持久化。每个 Run 使用稳定的 thread_id，生产 Checkpointer 保存执行状态；Store 保存跨会话记忆；业务数据库保存用户、Agent 配置和审计信息。

基础设施边界。消息队列负责把任务分配给 Worker；容器或沙箱负责隔离代码执行；WebSocket/SSE 负责把事件推送到前端；Redis 可以承载缓存、锁或短期协调；数据库负责可靠持久化。LangGraph 负责的是这些能力之间的 Agent 控制流，不会替代它们。

验收。模型产生 final 之后仍应进入 Verifier。代码任务检查测试与差异，文档任务回读真实内容，部署任务检查健康状态。只有 Evidence Gate 通过，Graph 才进入成功终点。

13. 适用与不适用场景

适合使用 LangGraph 的场景：

  • 任务可能运行很久，需要暂停、等待和故障恢复。
  • 控制路径包含循环、复杂条件分支或动态并行。
  • 需要人工审批、人工修改状态或补充信息。
  • 需要多个专业 Agent 或可复用子流程协作。
  • 需要查看历史 State、重放执行或从历史分叉。
  • 必须把确定性业务规则和模型决策组合在一起。

不必使用 LangGraph 的场景：

  • 一次模型调用即可完成的问答、分类或文本生成。
  • 一次检索加一次生成的简单 RAG。
  • 只有少量固定步骤且不需要恢复的业务逻辑。
  • 完全确定性的 ETL、审批或定时任务，已有工作流工具更直接。
  • 只是想快速体验通用 Tool Calling Agent，没有自定义编排需求。

判断标准不是“项目里有没有 LLM”，而是“任务是否需要显式状态、复杂控制流、持久化恢复或人工介入”。为了显得先进而把所有函数都包装成 Node，只会增加调试和维护成本。

14. 生产级设计清单

将 LangGraph 用于生产环境时，可以逐项检查：

☐ 为 State 定义清晰、版本化的 Schema

☐ 为追加字段和并行写入字段定义正确 Reducer

☐ 为每次连续任务分配稳定且不可冲突的 thread_id

☐ 生产环境使用持久化 Checkpointer，不依赖 InMemorySaver

☐ 区分 Thread State 与跨 Thread 的长期 Store

☐ 为模型调用、工具调用和整次 Run 设置超时

☐ 限制循环步数、Token、费用、工具次数和并发数

☐ 副作用节点具备幂等键、状态查询、去重或补偿机制

☐ 工具执行前校验身份、权限、租户、参数和资源范围

☐ 高风险动作在副作用发生前进入 Interrupt 审批

☐ 模型产生 final 后仍经过外部 Evidence Gate

☐ 记录节点路径、状态变化、错误、耗时、Token 与停止原因

☐ 支持用户取消、SAFE_STOP、资源清理和崩溃恢复

☐ 图和 State Schema 升级时考虑已有 Checkpoint 的兼容性

尤其要注意代码升级：旧 Thread 恢复时可能使用当前部署的新图。重命名节点、改变 State 字段含义或调整业务规则，都可能影响仍在等待中的任务，因此应在 State 中保存行为版本，并为长期运行任务设计迁移策略。

15. 常见错误认识

误区一：LangGraph 是一个大模型。它不生成答案，只负责编排模型、工具和普通代码。

误区二：Graph 只能是 DAG。LangGraph 支持循环，工具调用 Agent 正是通过工具节点返回模型节点形成 Loop。

误区三：每个 Node 都必须调用 LLM。权限校验、数据库查询、格式转换、测试和验收都可以是确定性节点。

误区四：State 就是聊天记录。State 还可以保存计划、工具结果、预算、待审批动作、Artifact 和任务状态。

误区五：Checkpoint 可以保证外部操作只执行一次。Checkpoint 只保存图状态，写数据库、付款和发消息仍需要幂等与状态查询。

误区六：Interrupt 会从下一行继续。恢复时相关 Node 会从开头重新执行，中断前的代码可能再次运行。

误区七：Memory 越多越好。Store 可以保存长期信息，但 Context 仍应按当前节点选择和压缩，避免成本、噪声与过期事实。

误区八：用了 LangGraph 就不需要队列、容器和权限系统。LangGraph 负责单次 Run 的编排，其他基础设施仍各自承担调度、隔离、存储和安全职责。

16. 60 秒面试回答

LangGraph 是一个用于构建长时间运行、有状态 Agent 的低层编排框架。它把 Agent 工作流表示为 State、Node 和 Edge：State 保存当前任务快照，Node 执行模型、工具或普通代码，Edge 根据状态决定下一步。它支持循环、条件分支、并行、Checkpoint、Interrupt、人工审批和故障恢复。与普通 while Agent Loop 相比，LangGraph 把控制流、状态持久化和暂停恢复显式化；但外部副作用仍需要幂等、权限校验和 Evidence Gate。实际项目中，我会用确定性节点管理权限、预算和验收，只把路径不确定的诊断、检索和规划交给模型。

17. 学习顺序与小练习

建议按依赖关系学习，而不是先背所有 API：

  1. State 与 Reducer：先理解节点为什么只返回局部更新，以及并行更新如何合并。
  2. Node、Edge 与条件路由：实现一个不调用 LLM 的小型状态图。
  3. Checkpointer 与 thread_id：让同一任务能够连续运行并查看历史 State。
  4. Interrupt 与 Command：实现审批、拒绝和恢复。
  5. Tool Calling Loop：接入模型和工具节点，让 Observation 返回模型节点。
  6. Subgraph、Streaming 与 Time Travel：再扩展到多 Agent、实时 UI 和调试。

小练习：设计一个“自动处理 GitHub Issue”的 Graph，回答以下问题：

  1. State 应保存哪些字段，哪些信息应放在 Runtime Context？
  2. 搜索、修改、测试、审批和发布分别是什么 Node？
  3. 测试失败后如何回到诊断节点，怎样防止无限循环？
  4. 创建分支、提交和 PR 如何保证幂等？
  5. 什么证据通过后才能进入 END？
  6. 测试运行十分钟时，怎样暂停、保存 job_id 并恢复？

下一学习点：优先深入 LangGraph State 与 Reducer。State 更新语义是条件分支、并行、Checkpoint 和多 Agent 的共同基础。

19. 一句话总结

LangGraph 把 Agent Loop 显式建模为 State、Node 和 Edge：State 保存进度，Node 执行模型、工具或确定性代码，Edge 控制下一步；Checkpointer 负责保存执行现场，Interrupt 与 Command 负责暂停恢复，Subgraph 负责模块化和多 Agent 编排。它让 Agent 的执行过程变得可控制、可恢复、可观察，但权限、幂等、外部存储和验收仍需要平台自己正确设计。
