MCP 与 Tool：工具发现、远程调用与协议边界

Tool 是模型可调用的能力，MCP 则是一套让客户端发现并调用外部 Tool 的标准协议。MCP 不替你实现业务函数，也不自动解决权限问题；它主要统一“工具怎样被描述、列出、调用和返回结果”。总览文档见 。

2. MCP 的三个主要角色

Agent 应用 / IDE / 桌面端（Host）
        -> 为某个 Server 建立 MCP Client
        -> MCP Server
             ├─ Tools
             ├─ Resources
             └─ Prompts
        -> 数据库、GitHub、飞书、文件系统等真实系统

Host 是承载模型、会话、权限界面和 Agent Loop 的应用。Client 负责与一个 MCP Server 建立连接并收发协议消息。Server 把某个外部系统的能力包装为 Tool、Resource 或 Prompt。

Tool 通常由模型选择；Resource 更像可读取的上下文资源；Prompt 是服务器提供的可复用提示模板。三者都通过 MCP 暴露，但用途不同。

3. Tool 发现：tools/list

连接建立后，MCP Client 可以调用 tools/list 获取服务器提供的工具。每个工具通常包含名称、描述和输入 Schema；新版本协议还可以携带输出 Schema、标题和附加元数据。

{
  "name": "get_order_status",
  "description": "查询当前租户下订单状态，只读",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string"}
    },
    "required": ["order_id"]
  }
}

Host 会把当前允许使用的 Tool 描述放进模型上下文。模型并不因为服务器提供了某个 Tool 就必然拥有调用权限；Host 可以根据用户、租户和当前任务过滤工具列表。

4. Tool 调用：tools/call

模型生成 Tool Call 后，Host 先进行本地安全检查，再由 MCP Client 向 Server 发送 tools/call。Server 执行真实操作并返回结果。

{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "get_order_status",
    "arguments": {
      "order_id": "order-10086"
    }
  }
}
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [
      {"type": "text", "text": "订单已发货"}
    ],
    "structuredContent": {
      "status": "shipped",
      "tracking_number": "SF123456"
    },
    "isError": false
  }
}

结构化结果适合程序继续处理，文本结果适合直接进入模型上下文。大型文件或数据集更适合返回 Resource Link 或 Artifact 引用，而不是把全部内容复制进 Tool Result。

5. 一次 MCP Tool 调用的完整生命周期

1. Host 与 MCP Server 建立连接
2. Client 获取 tools/list
3. Host 按用户、租户和任务过滤可见 Tool
4. Tool Schema 被加入模型上下文
5. 模型生成工具名与 arguments
6. Host 校验 Schema、权限、预算和审批
7. Client 发送 tools/call
8. Server 调用真实 API、数据库或本地程序
9. Tool Result 返回 Host
10. Host 记录 Trace，并把安全处理后的结果交给模型
11. 模型继续调用 Tool 或生成最终答案

MCP 标准化的是第 2、7、9 步附近的协议交互；身份认证、业务权限、审批、租户隔离和最终呈现仍然由 Host、Gateway 与 Server 共同负责。

7. MCP 不等于安全边界

MCP Server 声明的名称、描述和 Schema 只是接口元数据，不代表服务器天然可信。Host 应维护允许连接的 Server 列表，并在暴露 Tool 前进行身份、来源和配置校验。

  • 只连接经过审核的 Server，固定版本和发布来源。
  • 根据任务动态过滤 Tool，不把所有能力默认交给模型。
  • 调用前展示高风险参数并请求人工批准。
  • 对每次调用重新鉴权，不能把模型给出的 tenant_id 当作可信身份。
  • 限制 Server 能访问的文件、网络、数据库和密钥。
  • 把 Tool Result 当作外部不可信数据，防范 Prompt Injection。
  • 记录 Server、Tool、参数摘要、结果、耗时和权限决策。

8. 错误应该在哪里表达

协议层错误表示请求无法被 MCP 正常处理，例如方法不存在或请求格式非法。工具执行失败则更适合放进 Tool Result，并设置 isError=true，这样模型能看到业务错误并尝试修正参数或改变计划。

9. Python 项目中的推荐分层

domain/
  order_service.py       # 核心业务逻辑

tools/
  order_tools.py         # Tool Schema 与适配器

gateway/
  policy.py              # 鉴权、审批、幂等
  executor.py            # 统一执行管线

mcp_server/
  server.py              # tools/list、tools/call 协议适配

agent/
  runtime.py             # Agent Loop 与上下文管理

业务服务不依赖 MCP；MCP Server 只把已有 Tool 暴露为标准协议。这样即使将来更换 Agent 框架或通信方式，核心业务逻辑仍然可以复用。

10. Tool、Resource 与 RAG 的关系

如果模型需要主动查询实时数据库，可以提供 Tool；如果只是读取一个可寻址的静态资源，可以暴露 Resource；如果要从大量文档中按语义召回相关片段，通常由 RAG 或搜索 Tool 完成。MCP 可以承载这些接口，但不会替你完成切分、向量化、重排或权限过滤。

11. MCP 与 Function Calling、普通 API 的区别

这三个概念处在不同层次。Function Calling 是模型表达“我要调用哪个函数、传什么参数”的结构化输出机制；MCP 是 Host 与外部能力提供者之间进行发现和调用的标准协议；普通 API 则是业务系统真正提供的数据或操作接口。

12. stdio 与 Streamable HTTP

MCP 使用 JSON-RPC 表达消息，但消息可以通过不同传输方式发送。最常见的是 stdio 和 Streamable HTTP。

stdio

Host 启动本地 MCP Server 子进程，通过标准输入输出交换消息

文件系统、Git、本地开发工具、单机插件

stdout 只能输出协议消息，日志应写 stderr；进程权限应尽量收窄

Streamable HTTP

MCP Server 独立部署，Host 连接统一 HTTP 端点

飞书、GitHub、企业数据库、多用户 Agent 平台

需要认证、Origin 校验、租户隔离、限流和连接管理

选择原则很简单：能力只服务本机并且需要访问本地资源时，优先 stdio；需要跨机器、多人共享、独立扩缩容或统一运维时，使用 Streamable HTTP。旧式 HTTP 加 SSE 传输属于兼容路径，新服务优先采用 Streamable HTTP。

13. Python SDK v2 最小实现

下面示例按照 2026 年 8 月官方 Python SDK v2 稳定线编写。它把一个普通 Python 函数暴露为 MCP Tool，类型注解会参与生成输入 Schema。

uv add "mcp[cli]"
from mcp.server import MCPServer

mcp = MCPServer("recruitment-knowledge-base")


@mcp.tool()
def search_notes(keyword: str) -> list[str]:
    """搜索秋招知识库中的笔记。"""
    notes = [
        "Redis：缓存、持久化与分布式锁",
        "消息队列：削峰、解耦与异步",
        "MCP：Host、Client 与 Server",
    ]
    return [note for note in notes if keyword.lower() in note.lower()]
uv run mcp run server.py --transport streamable-http
import asyncio
from mcp import Client


async def main() -> None:
    async with Client("http://localhost:8000/mcp") as client:
        result = await client.call_tool(
            "search_notes",
            {"keyword": "Redis"},
        )
        print(result.structured_content)


asyncio.run(main())

生产代码不要把数据库访问、鉴权和核心业务逻辑直接写进协议装饰器。MCP Server 应保持为薄适配层，调用独立的领域服务和 Tool Gateway。SDK 仍在快速演进；如果项目使用 v1 的 FastMCP API，应锁定依赖版本，并按官方迁移指南升级。

14. MCP 与 Agent Tool 白名单

MCP Server 的 tools/list 只表示“这个 Server 提供哪些 Tool”，并不表示当前 Agent 自动获得了全部权限。Host 应先把工具同步进 Tool Registry，再根据 Agent、租户、用户、环境和资源范围进行确定性过滤，只把允许的 Tool Schema 交给模型。

MCP tools/list
      ↓
Tool Registry
      ↓
Agent 白名单与租户、用户、环境硬过滤
      ↓
相关性 Top-K
      ↓
模型选择 Tool
      ↓
tools/call
      ↓
Tool Gateway 按具体参数再次鉴权、审批和审计

这里存在两道不同的安全关卡：Host 控制模型能看见哪些工具；Tool Gateway 和 MCP Server 控制这一次调用是否真的可以执行。即使旧会话中残留了某个 Tool Schema，执行层也必须能够拒绝已经撤权的调用。

  • ：Agent Tool 白名单、Default Deny、策略版本与运行时二次鉴权。
  • ：Tool Gateway 的多租户鉴权、幂等、审批与隔离。

15. 面试回答

MCP 是连接 AI Host 与外部能力的标准协议，采用 Host、Client、Server 架构。Server 可以暴露 Tool、Resource 和 Prompt；Client 通过 tools/list 发现工具，通过 tools/call 发起调用，消息通常经 stdio 或 Streamable HTTP 传输。Function Calling 解决模型怎样表达调用意图，MCP 解决 Host 怎样发现和调用外部能力，真实业务仍由 API、SDK、数据库或本地程序完成。MCP 本身不是安全边界：Host 需要按 Agent 白名单过滤可见工具，执行阶段还要由 Tool Gateway 和 Server 检查用户、租户、资源、参数与审批状态。
