MVCC 与锁：快照读、当前读、行锁和版本链怎样共同工作

这篇文档承接 《事务、ACID 与并发异常》，回答一个更具体的问题：多个事务同时读写同一批数据时，数据库为什么既能让普通查询少等待，又能防止写入互相覆盖？核心答案不是“只靠 MVCC”或“只靠锁”，而是二者分工协作。

本文采用 MySQL 8.4 / InnoDB 的术语。MVCC 的思想具有通用性，但 PostgreSQL 等数据库保存版本、生成快照和回收旧版本的具体方式不同。

1. 一句话理解 MVCC

MVCC 是 Multi-Version Concurrency Control，即多版本并发控制。它允许一条逻辑记录在一段时间内存在多个可供判断的版本；每个事务根据自己的可见性规则，选择其中“对自己可见”的那个版本。

直觉上，可以把它理解为：读者不必抢走作者手中的纸，而是根据自己的阅读时点查看合适的历史稿；作者继续修改当前稿。这样，普通读取和写入就不必总是互相阻塞。

2. 为什么不能所有并发都只靠锁

如果事务读取一行时必须加锁，并一直持有到事务结束，那么慢查询、报表和大量并发请求会阻塞更新；更新也会让随后到达的读取排队。数据虽然正确，但吞吐量和响应时间会迅速恶化。

MVCC 主要优化“读与写”的并发：写事务修改当前版本时，普通读取仍可通过旧版本得到一致结果。不过，两个事务同时写同一行时仍可能冲突，因此写写竞争以及需要保护业务条件的读取仍然要靠锁、条件更新或乐观并发控制。

3. MVCC 不是一个锁，也不是一种隔离级别

这三个概念处于不同层次：MVCC 是实现并发控制的机制；锁是协调冲突访问的手段；隔离级别是数据库向应用提供的可见性保证。InnoDB 会组合 MVCC 和锁来实现 Read Committed、Repeatable Read 等隔离级别。

所以，“开启了 MVCC 就没有锁”是错误的；“MVCC 等于可重复读”也不准确。相同的多版本能力，可以通过不同的快照生成规则服务于不同隔离级别。

4. InnoDB 如何表示一条记录的版本

在 InnoDB 的聚簇索引记录中，除了业务字段，还包含用于并发控制的隐藏信息。理解 MVCC 最关键的是下面两个字段。

字段

作用

直觉

DB_TRX_ID

记录最后一次插入或更新该行的事务 ID

“这个版本是谁写的”

DB_ROLL_PTR

指向 Undo Log 中可用于重建旧版本的信息

“上一版从哪里找”

没有显式主键或合适唯一非空索引时，InnoDB 还会生成隐藏的 DB_ROW_ID。它与版本可见性不是同一个概念，但也说明 InnoDB 的聚簇记录含有数据库维护的隐藏字段。

5. Undo Log 与逻辑版本链

事务把余额从 100 改成 80 时，InnoDB 不需要在数据页里并排保存许多完整行。当前记录保存新值与新的事务 ID，Undo Log 保存撤销或重建旧值所需的信息，DB_ROLL_PTR 将它们串联起来。

当前记录：balance=60, DB_TRX_ID=300
        ↓ DB_ROLL_PTR
旧版本：balance=80,  DB_TRX_ID=200
        ↓ DB_ROLL_PTR
更旧版本：balance=100, DB_TRX_ID=100

这条链通常被称为“版本链”。它是逻辑上的历史链条，不应简单理解为磁盘上永久保存了三份完整数据。旧版本是否还能被读取，取决于 Undo 信息是否仍被活跃事务需要。

6. Read View 是什么

只有版本链还不够，数据库还需要回答“当前事务能看到哪一个版本”。Read View 可以理解为生成一致性读取时使用的可见性快照，它记录当时活跃事务的边界和集合。

从逻辑上看，判断规则包括：本事务自己已经完成的修改可见；在快照建立前已经提交的事务通常可见；快照建立时仍活跃的事务产生的版本不可见；快照建立后才开始的事务产生的版本也不可见。MySQL 内部字段名和边界判断较细，但面试时先掌握这四条语义即可。

7. 一次 MVCC 读取怎样找到结果

普通查询访问一行时，InnoDB 先检查当前记录的 DB_TRX_ID。如果该版本对本次 Read View 可见，就直接返回；如果不可见，就沿 DB_ROLL_PTR 到 Undo Log 重建上一个版本，再次判断；如此继续，直到找到可见版本或确认这行在当前快照中尚不存在。

读取当前记录
  → 检查创建该版本的事务
  → 对 Read View 可见？是：返回
  → 否：沿 Roll Pointer 找上一版本
  → 重复判断

因此，MVCC 的完整心智模型应是：版本信息 + Undo 版本链 + Read View 可见性规则 + 旧版本回收。

8. 快照读是什么

在 InnoDB 的 Read Committed 和 Repeatable Read 下，普通 SELECT 通常属于一致性非锁定读，也就是常说的快照读。它读取符合快照的版本，不为目标记录加共享锁，因此通常不会被正在修改该行但尚未提交的事务阻塞。

SELECT balance
FROM accounts
WHERE id = 1;

“不加记录锁”不等于完全没有任何数据库内部同步，也不等于可以读取其他事务未提交的数据。快照读仍遵守事务隔离规则。

9. 当前读是什么

有些操作不能只看历史版本。例如准备扣库存时，应用需要基于最新可用状态做决定，并阻止其他事务同时改变这项条件。此时应使用当前读：读取最新可用版本，并对相关索引记录或范围加锁；如果锁已被其他事务持有，请求可能等待。

SELECT stock
FROM products
WHERE id = 1001
FOR UPDATE;

SELECT ... FOR UPDATE、SELECT ... FOR SHARE 属于显式锁定读；UPDATE 和 DELETE 为了修改数据，也会执行当前读取并取得相应锁。

11. Read Committed 怎样使用快照

在 Read Committed 下，同一事务里的每次一致性读取通常都会建立新的 Read View。事务第一次查询得到余额 100，其他事务提交余额 80 后，第一次事务再次执行同一普通查询，可能看到 80。这就是为什么 Read Committed 允许不可重复读。

它的优势是更快看到其他事务已经提交的变化，也往往减少某些范围锁的影响；代价是同一事务内两次相同查询不保证得到同一快照结果。

12. Repeatable Read 怎样使用快照

在 InnoDB 的 Repeatable Read 下，同一事务中的一致性读取通常复用第一次一致性读取所建立的快照。因此，第一次普通查询看到余额 100 后，其他事务即使提交余额 80，本事务后续普通查询通常仍看到 100。

需要注意，BEGIN 本身不一定立即建立这个一致性快照；通常是第一次一致性读取建立它。若应用确实依赖“事务开始时刻”的快照，应理解所用语句和数据库的具体行为，而不要仅凭方法名推断。

13. 同一事务为什么可能看到两个不同的值

Repeatable Read 保证的是一致性读取复用快照，不代表所有语句都只能看历史。一个事务先用普通 SELECT 看到旧值 100，随后执行 SELECT ... FOR UPDATE，后者属于当前读，可能在等待其他事务提交后看到新值 80。

这并非数据库自相矛盾，而是两条语句采用了不同的读取语义。排查“同一事务为什么读到不同值”时，第一步应确认每条 SQL 是快照读还是当前读。

14. MVCC 与锁怎样分工

MVCC 负责版本可见性。 它让普通读取在很多场景下绕开正在写入的最新版本，从历史版本获得一致结果。

锁负责冲突协调。 当两个事务要修改同一记录，或一个事务需要保证“我检查过的条件在提交前不能被别人破坏”时，数据库需要让冲突操作等待、失败或形成可检测的死锁。

简化记忆：读旧版本解决读写并发，锁住当前数据解决写写竞争和受保护读取。

15. InnoDB 的“行锁”本质上锁什么

InnoDB 的行级锁本质上是索引记录锁。查询通过主键或唯一索引精确定位时，通常能锁住很小的范围；范围条件、非唯一索引或缺少合适索引时，数据库可能扫描并锁住更多索引记录与间隙。

所以，“SQL 只返回一行，就一定只锁一行”并不可靠。判断锁范围要同时看隔离级别、访问索引、查询条件、执行计划以及语句类型。

18. 索引为什么会影响锁范围

假设 id 是主键，WHERE id = 1001 可以直接定位一个索引记录；而 WHERE status = 'pending' 如果没有合适索引，就可能扫描大量记录。锁定读或更新语句通常会对扫描到并需要保护的索引记录或范围加锁，因此缺失索引不仅让查询变慢，也可能扩大锁冲突面。

优化并发问题时，不能只问“有没有行锁”，还要问“SQL 走了哪个索引、扫描了多少记录、锁住了哪些区间”。

19. 两个事务同时更新同一行会怎样

事务 A 更新账户 1 后获得相应排他锁，但尚未提交。事务 B 也尝试更新账户 1 时，不能通过读取旧版本来完成写入，因为它最终要修改当前记录；B 通常会等待 A 提交或回滚。A 提交后，B 基于最新可用记录继续执行；等待超过限制则可能得到锁等待超时。

事务 A：UPDATE 行 1 → 获得 X 锁 → 暂未提交
事务 B：UPDATE 行 1 → 请求 X 锁 → 等待
事务 A：COMMIT → 释放锁
事务 B：获得锁 → 继续更新 → COMMIT

20. 为什么“先查再改”仍可能丢失更新

应用先用快照读查到库存 10，在 Python 中计算为 9，再把 9 写回。两个请求都读到 10 时，它们可能都写回 9，结果少扣了一件。UPDATE 本身会加锁，但锁只能串行化两次写入，无法自动理解应用已经基于过期快照算出了同一个绝对值。

解决方案是让检查与修改在数据库中成为一个原子条件更新，或在读取时使用 FOR UPDATE，或增加版本号实施乐观锁。

21. 首选方案：原子条件更新

UPDATE products
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;

应用检查受影响行数：等于 1 表示扣减成功，等于 0 表示库存不足或记录不存在。数据库在当前版本上完成条件判断和修改，避免把快照读出的旧值带回应用再覆盖。

当业务逻辑可以表达成单条 SQL 时，这通常比“先锁、再读、再写”更简单，锁持有时间也更短。

22. 何时使用 SELECT FOR UPDATE

如果修改依赖多列、多行或无法压缩成一条原子 SQL，可以在事务中先执行锁定读，读取最新状态并锁住需要保护的记录，再完成校验和更新。

START TRANSACTION;

SELECT stock, status
FROM products
WHERE id = 1001
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 1001;

COMMIT;

必须把锁定读和后续更新放在同一个事务内。事务外的 FOR UPDATE，或读取后先调用远程服务再更新，通常不能提供期望的保护，反而会造成长时间持锁。

23. SQLAlchemy 中怎样实现

下面的 Python 代码在一个事务中锁定商品行。数据库锁是否真正生效，仍取决于底层数据库、隔离级别、索引和 SQLAlchemy 实际生成的 SQL。

from sqlalchemy import select
from sqlalchemy.orm import Session

with Session(engine) as session:
    with session.begin():
        product = session.execute(
            select(Product)
            .where(Product.id == 1001)
            .with_for_update()
        ).scalar_one()

        if product.stock <= 0:
            raise OutOfStock()

        product.stock -= 1

能使用原子条件更新时，可以直接判断 rowcount：

from sqlalchemy import update

with Session(engine) as session:
    with session.begin():
        result = session.execute(
            update(Product)
            .where(Product.id == 1001, Product.stock > 0)
            .values(stock=Product.stock - 1)
        )
        if result.rowcount != 1:
            raise OutOfStock()

24. 乐观锁如何补充 MVCC

乐观锁通常给业务表增加 version 字段：读取数据时一并取得版本号，更新时要求版本仍等于旧值，同时把版本号加一。

UPDATE documents
SET content = 'new content',
    version = version + 1
WHERE id = 42
  AND version = 7;

受影响行数为 0 表示期间有人修改过，应用应提示冲突、重新读取或按规则重试。它不是数据库锁的替代品，而是把“我是否基于过期数据更新”变成可检测的业务并发条件。

25. 死锁为什么仍会发生

MVCC 不会消除死锁。事务 A 先锁行 1 再等行 2，事务 B 先锁行 2 再等行 1，就形成循环等待。InnoDB 会检测并回滚其中一个事务，让另一个继续。

工程上应统一加锁顺序，保持事务短小，给过滤条件建立合适索引，避免事务中调用慢速外部服务，并对死锁或可重试的序列化失败做有限次数、带退避的整事务重试。不能只重放最后一条 SQL，因为事务之前的读取和判断也可能已经失效。

26. 长事务为什么会拖累 MVCC

只要较早的 Read View 仍可能需要某个历史版本，InnoDB 就不能把相应的更新 Undo 完全清理。长事务因此会让版本链变长、Undo 空间增长，并增加一致性读取沿链查找和后台 Purge 的压力。

常见诱因包括：事务打开后长时间不提交、分页导出一直占用同一事务、交互式调试忘记结束事务，以及在事务中等待网络或模型响应。监控时应关注长事务、历史列表长度、Undo 表空间和锁等待，而不只是慢 SQL。

28. 常见误区

误区一：MVCC 就是把每一行完整复制很多份。 InnoDB 主要通过当前记录、隐藏字段和 Undo 信息重建逻辑历史版本。

误区二：快照读一定读最新数据。 它读的是对当前 Read View 可见的数据，可能是已经提交但较旧的版本。

误区三：Repeatable Read 中任何查询都只能看到旧值。 普通一致性读与当前读采用不同语义。

误区四：有行锁就只会锁返回的那一行。 InnoDB 锁索引记录和范围，访问路径会影响实际锁范围。

误区五：事务越大越安全。 长事务会延长锁持有时间、保留旧版本并扩大失败重试成本。

29. 面试时怎样回答 MVCC

可以先用 40 秒回答主干：

MVCC 是多版本并发控制。以 InnoDB 为例，聚簇记录包含最后修改事务 ID 和指向 Undo 的回滚指针，更新后可以沿 Undo 形成逻辑版本链。普通一致性读会根据 Read View 判断版本是否可见，不可见就沿版本链找旧版本，所以读写很多时候不用互相阻塞。Read Committed 通常每次一致性读生成新快照，Repeatable Read 通常复用事务内第一次一致性读的快照。MVCC 主要解决读写并发，当前读和写写冲突仍需要记录锁、间隙锁或 Next-Key Lock。

如果面试官继续追问，再展开快照读与当前读、Read View 边界、索引如何影响锁范围，以及长事务为什么阻碍 Purge。
