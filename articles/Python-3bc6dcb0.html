Python 并发：线程、协程、进程与调度模型

核心结论：Python 并发不是“线程还是协程”二选一。大量异步 I/O 优先协程，同步阻塞 SDK 用有界线程池桥接，纯 Python CPU 密集任务使用多进程或独立 Worker；生产后端通常组合使用三者。

本文面向 Python 后端和 AI Agent 平台，重点回答四个问题：Python 为什么需要并发、为什么不能把所有任务都交给线程、协程究竟怎样轻量化，以及抢占式调度和协作式调度有什么本质区别。

1. 并发与并行

并发表示多个任务在同一段时间内持续推进，任务可以只是交替执行；并行表示多个任务在同一时刻由不同 CPU 核心真正执行。只有一个 CPU 核心时也能并发，但不能让两段 CPU 指令真正同时运行。

并发：A 执行 → A 等待 → B 执行 → B 等待 → A 恢复
并行：CPU Core 1 执行 A，同时 CPU Core 2 执行 B

并发主要提高系统吞吐量和响应能力，不一定缩短一个任务本身的计算时间。并行则可能直接缩短可拆分 CPU 计算的总耗时。

2. 后端请求为什么适合并发

一次后端请求通常不是连续占用 CPU，而是在短暂计算和长时间等待之间反复切换。调用数据库、Redis、RPC、对象存储或大模型 API 时，请求的大部分时间可能都在等待网络结果。

请求 A：计算 → 等待 LLM ----------------→ 处理结果
请求 B：       计算 → 等待数据库 --------→ 处理结果
请求 C：              计算 → 等待 Tool --------→ 处理结果

如果串行执行，后续请求只能排队；如果并发执行，A 等待 LLM 时，CPU 可以继续推进 B 和 C。并发的价值是利用等待时间，而不是让远端 LLM 本身变快。

5. 线程是什么

线程是操作系统调度的执行单元。同一进程中的线程共享堆、模块和大部分进程资源，但每条线程拥有自己的原生调用栈、寄存器上下文和线程局部状态。

线程执行阻塞式网络调用时，操作系统可以挂起当前线程并调度其他线程。因此，线程完全能够利用 I/O 等待时间；在同步库较多、并发规模有限的项目里，线程池往往是简单而合理的选择。

6. 为什么不把所有任务都交给线程

阻塞线程等待 I/O 时不会持续占用 CPU，但它仍然占用一条 OS 线程、原生线程栈、内核调度对象以及线程池中的一个工作槽。线程数量增加后，还会增加调度、上下文切换、锁竞争和内存成本。

线程池最多 50 个 Worker
├─ 50 个请求正在等待 LLM
└─ 后续 450 个请求只能在线程池队列中等待

因此，“线程在等待时不使用 CPU”不等于“线程在等待时没有成本”。对于大量 WebSocket、SSE、模型 API 和 Agent Tool 调用，协程可以让少量线程管理大量正在等待的任务。

但这不是说线程不好。同步 SDK 为主、并发量不高、改造异步调用链成本很大时，使用一个有明确上限的线程池通常比强行异步化更稳妥。

7. GIL 限制了什么

在默认启用 GIL 的 CPython 中，同一解释器同一时刻通常只有一个线程执行 Python 代码。这使纯 Python CPU 密集任务很难仅靠增加线程充分利用多个核心。这里的准确边界是“解释器”，不是整个进程：同一进程可以通过多个相互隔离的子解释器形成各自的 GIL。

GIL 并不表示线程没有价值：阻塞 I/O 期间解释器会释放执行机会，部分 C 扩展也会主动释放 GIL。GIL 也不等于业务数据线程安全，读取后修改再写回等复合操作仍然需要锁、队列、事务或原子机制。

从 Python 3.13 开始，CPython 提供可选的 free-threaded 构建；在 Python 3.14 中它仍是可选模式，并非所有第三方扩展都已适配，某些扩展还可能重新启用 GIL。兼容的 free-threaded 构建可以让多个线程在不同核心并行执行 Python 代码，但共享可变状态仍要显式同步。通用后端目前不应假设运行环境已经无 GIL，而应先检查解释器模式、依赖兼容性并用真实负载测试。

8. 协程不是缩小版 OS 线程

“协程是轻量级线程”适合作为第一层直觉，但不够准确。线程由操作系统调度；Python 协程是可以暂停和恢复的函数，通常被包装成 asyncio.Task，由事件循环在用户态调度。

一个 Python Worker 进程
├── 一个事件循环线程
│   └── 一个 Event Loop
│       ├── Task A：等待 LLM
│       ├── Task B：等待数据库
│       ├── Task C：等待 WebSocket
│       └── Task D：当前正在运行
└── 可选线程池工作线程：执行同步阻塞 SDK

同一个事件循环里的 Task 通常不会同时执行 Python 代码。当前 Task 运行到可以暂停的等待点后，事件循环才选择另一个 Task 继续。

9. 协程究竟怎样轻量化

不创建独立原生线程栈。协程暂停时，主要保存执行位置、局部变量、正在等待的 Future 和异常关系。这些信息保存在协程对象及其关联执行帧中，不需要为每个任务创建一条 OS 线程。

切换主要发生在用户态。线程切换需要内核调度并保存、恢复线程上下文；协程通常在 await 处主动交还控制权，事件循环把当前 Task 放入等待集合，再从就绪队列选择下一个 Task。

统一管理大量 Socket。事件循环借助操作系统的就绪或完成通知机制管理大量异步 I/O：Linux 常见 epoll、macOS/BSD 常见 kqueue，Windows 常见 IOCP。前两者侧重通知“哪些资源已经就绪”，IOCP 侧重通知“哪些异步操作已经完成”；共同点是不需要让每个连接分别占用一条阻塞线程。

轻量不等于没有成本。每个 Task、Future、执行帧和局部变量仍然占用内存；如果协程长期持有大型对象，或者无上限地创建 Task，同样会耗尽资源。

10. 事件循环怎样推进协程

Task A 发送 HTTP 请求
  ↓
把 Socket 注册给事件循环
  ↓
await：Task A 暂停，线程继续运行 Task B
  ↓
操作系统通知 Socket 已就绪
  ↓
事件循环把 Task A 放回就绪队列
  ↓
Task A 从 await 后继续

等待期间没有一条专属线程陪着这个请求。事件循环线程可以不断推进其他已经就绪的任务。

13. await 到底意味着什么

async def 只声明这是协程函数，并不会自动产生并发。await 表示等待一个 Awaitable；只有当结果尚未完成时，当前 Task 才会真正暂停并让出执行权。如果被等待对象已经完成，代码可能直接继续。

# 通常是顺序执行
result_a = await request_a()
result_b = await request_b()

# 并发启动
async with asyncio.TaskGroup() as group:
    task_a = group.create_task(request_a())
    task_b = group.create_task(request_b())

result_a = task_a.result()
result_b = task_b.result()

14. asyncio 最小并发示例

import asyncio


async def call_service(name: str, delay: float) -> str:
    await asyncio.sleep(delay)  # 模拟异步网络等待
    return f"{name} 完成"


async def main():
    async with asyncio.TaskGroup() as group:
        task_a = group.create_task(call_service("A", 2))
        task_b = group.create_task(call_service("B", 1))
        task_c = group.create_task(call_service("C", 3))

    print(task_a.result())
    print(task_b.result())
    print(task_c.result())


asyncio.run(main())

三个任务总耗时接近最慢任务的三秒，而不是六秒，因为等待区间发生了重叠。TaskGroup 提供结构化并发语义：作用域结束前会等待子任务结束；当首个子任务因 CancelledError 以外的异常失败时，会请求取消其余子任务并等待它们清理，随后把非取消异常合并为 ExceptionGroup 抛出。取消本身仍是协作式的，子任务执行清理代码时可能延迟退出。

15. 阻塞代码为什么会卡住事件循环

import time


async def bad_task():
    time.sleep(10)  # 同一事件循环线程被阻塞

虽然函数写成了 async def，但 time.sleep()、同步 HTTP SDK、普通阻塞式文件操作和长时间 CPU 计算不会自动变成异步。事件循环线程一旦被占住，其他 Task、定时器和 WebSocket 都无法及时推进。

async def call_old_sdk(argument):
    result = await asyncio.to_thread(
        sync_sdk_call,
        argument,
    )
    return result

asyncio.to_thread() 主要用于让阻塞式 I/O 不阻塞事件循环，但它使用默认 Executor，并不自动提供业务背压：大量调用仍可能在 Executor 队列中堆积。应先用 Semaphore、有界队列等限制提交量，或者自行管理 Executor。取消外层等待也不一定能强制终止已经运行的底层线程，因此还需给同步 SDK 设置自身超时，并保证外部副作用可查询或幂等。

16. CPU 密集任务为什么使用进程

多个进程拥有独立解释器和地址空间，可以在不同 CPU 核心并行执行，并绕开普通 CPython 单进程 GIL 对纯 Python 字节码并行的限制。

from concurrent.futures import ProcessPoolExecutor


def cpu_heavy(n: int) -> int:
    return sum(i * i for i in range(n))


def main():
    numbers = [10_000_000] * 4
    with ProcessPoolExecutor() as pool:
        results = list(pool.map(cpu_heavy, numbers))
    print(results)


if __name__ == "__main__":
    main()

函数、参数和返回值通常需要能够被序列化；进程启动、数据复制和进程间通信也有成本。数据库连接、Socket 和事件循环对象不应直接传给子进程，应在子进程内重新初始化所需资源。

17. concurrent.futures 的作用

concurrent.futures 提供统一的 Executor 和 Future 接口。ThreadPoolExecutor 适合同步阻塞 I/O，ProcessPoolExecutor 适合可序列化的 CPU 计算。Python 3.14 还提供 InterpreterPoolExecutor，让不同子解释器拥有相互隔离的运行时状态和各自的 GIL，但它对共享数据和第三方扩展兼容性有额外要求，基础阶段不必优先使用。

concurrent.futures.Future 和 asyncio.Future 不是同一种对象。前者表示 Executor 中的调用结果，后者服务于事件循环；需要通过 to_thread、run_in_executor 或包装接口在两种模型之间桥接。

18. 并发仍然会产生竞态条件

线程可能在相对不可预测的位置被抢占，所以共享可变状态需要格外谨慎。协程的切换位置更容易观察，但跨越 await 后，另一个 Task 也可能已经修改状态。

balance = account.balance

await call_payment_service()

account.balance = balance - 100

等待支付服务时，其他协程可能已经修改余额。根据资源边界，可以使用 threading.Lock、asyncio.Lock、线程安全队列、数据库事务、乐观锁、唯一约束或消息传递。asyncio.Lock 用于同一事件循环中的 Task，不应拿来同步 OS 线程。

19. 并发控制、超时与取消

协程很轻，但数据库连接池、文件描述符、内存、下游 QPS 和模型配额都不是无限的。无上限地创建 Task 会把排队从应用入口转移到连接池或下游服务，最终表现为超时和雪崩。

import asyncio


llm_limit = asyncio.Semaphore(20)


async def call_llm(prompt):
    async with llm_limit:
        async with asyncio.timeout(30):
            return await llm_client.generate(prompt)

生产系统还要设计背压、重试、取消传播和资源清理。取消本地 Task 不代表远端请求一定停止；支付、发消息、创建云资源等外部副作用仍需幂等键、状态查询和补偿。

20. Agent 平台中的推荐组合

负载均衡器
├── Worker 进程 1
│   └── asyncio Event Loop
│       ├── LLM / 数据库 / WebSocket 协程
│       ├── 有界线程池：同步 Tool SDK
│       └── 提交 CPU / 长任务到外部 Worker
└── Worker 进程 2
    └── asyncio Event Loop
        └── ...

消息队列
└── 独立 Worker / 进程 / 容器
    ├── CPU 密集计算
    ├── 代码执行
    └── 需要重试与 Checkpoint 的长任务

API Worker 快速接收请求和推送事件；异步协程处理大量 LLM、数据库和 WebSocket I/O；有界线程池兼容阻塞 SDK；多进程利用多核并提供故障隔离；消息队列和独立 Worker 承担长任务、重试与削峰。

不可信代码必须单独隔离。如果“代码执行”包含 Agent 生成或用户提交的不可信程序，普通进程、线程或任务队列不是充分的安全边界。应在受限沙箱、容器或虚拟机中执行，并同时限制 CPU、内存、运行时间、文件系统、系统调用和网络访问。

22. 常见误区

误区一：协程就是更小的线程。协程不是 OS 调度实体，而是由事件循环管理的可暂停函数和 Task。

误区二：用了 async def 就不会阻塞。内部同步 I/O 或 CPU 计算仍然会卡住事件循环。

误区三：看到 await 就一定会切换任务。只有 Awaitable 尚未完成时，当前 Task 才会真正悬挂。

误区四：GIL 保证线程安全。GIL 保护的是解释器内部执行条件，不会替你保证业务复合操作正确。

误区五：协程完全不需要锁。跨 await 的共享状态仍可能发生竞态。

误区六：并发越高吞吐越高。超过 CPU、内存、连接池和下游容量后，只会增加排队、超时和失败。

误区七：协程适合 CPU 密集计算。长时间不让出执行权的计算会阻塞整个事件循环。

23. 60 秒面试回答

Python 并发主要使用线程、协程和进程。线程由操作系统抢占式调度，能够处理阻塞式 I/O，但共享内存会产生数据竞争，而且普通 CPython 的 GIL 限制纯 Python CPU 密集任务的多线程并行。协程由事件循环协作式调度，在异步 I/O 的 await 处保存执行状态并主动让出控制权，不需要为每个等待任务创建 OS 线程，因此适合大量 HTTP、数据库、WebSocket 和 LLM 调用。协程如果执行阻塞代码或长时间 CPU 计算，会卡住整个事件循环。生产后端通常使用多个 Worker 进程利用多核，每个 Worker 内用 asyncio 处理 I/O，用有界线程池兼容同步 SDK，再把 CPU 密集和长时间任务交给进程池、消息队列或独立 Worker。

抢占式线程把切换权交给操作系统，协作式协程在等待点主动让出执行权；协程的轻量来自不为每个任务创建 OS 线程，并用事件循环和 I/O 多路复用统一管理等待，而生产 Python 服务应根据 I/O、CPU 和可靠性边界组合使用协程、线程、进程与 Worker。
