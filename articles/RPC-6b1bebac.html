RPC：不同服务之间如何进行同步调用

一句话理解：RPC（Remote Procedure Call，远程过程调用）让一个服务像调用本地函数一样，请求另一个进程或机器上的服务，并等待结果返回。

RPC 是微服务、分布式系统和 AI Agent 平台的基础通信方式。真正需要掌握的不是某个框架的 API，而是同步调用背后的网络、超时、重试、幂等、服务发现、负载均衡和故障治理。

1. 为什么需要 RPC

单体应用中，用户服务、订单服务和支付逻辑位于同一进程，可以直接调用函数。拆成多个服务以后，它们拥有独立的进程、端口、运行环境甚至服务器，普通函数调用无法跨越进程边界。

此时调用方必须完成一整套通信工作：找到目标服务、把参数编码成字节、通过网络发送、等待对方执行、接收响应、解码结果并处理错误。RPC 框架把这些细节封装起来，让开发者面对一个接近函数调用的接口。

2. 什么是“同步调用”

同步描述的是业务依赖关系：调用方发出请求后，需要拿到结果才能继续当前流程。线程是否被阻塞、代码是否使用 async/await，是实现方式层面的问题，不能简单等同于业务上的同步或异步。

  • 同步 RPC：用户服务调用权限服务校验身份，未得到结果前不能继续。
  • 异步消息：订单创建后发送“订单已创建”事件，通知、积分等消费者稍后处理。

关键判断：当前步骤是否必须立即得到下游结果？如果必须，通常使用同步 RPC；如果允许稍后处理，优先考虑消息队列。

4. 一次 RPC 调用到底发生了什么

  1. 构造请求：方法名、参数、请求 ID、认证信息、Trace ID、超时或截止时间。
  2. 序列化：把内存中的对象转换为可传输的字节。
  3. 寻址与连接：根据服务发现和负载均衡结果连接一个实例。
  4. 网络传输：通过 HTTP、HTTP/2 或自定义 TCP 协议发送数据。
  5. 服务端分发：Server Stub 解码请求并路由到实际方法。
  6. 执行业务：服务端完成查询、计算或写入。
  7. 返回响应：结果或错误被序列化并沿网络返回。
  8. 客户端还原：Client Stub 将响应转回业务对象，或抛出可识别的异常。

5. Stub：为什么远程调用看起来像本地函数

Client Stub 是调用方的本地代理，负责隐藏网络细节；Server Stub 负责接收请求、反序列化、调用真实业务函数和返回响应。很多 RPC 框架会根据接口定义文件自动生成两端代码。

这种抽象提高了开发效率，但也容易造成“远程调用和本地调用一样”的错觉。实际上远程调用比本地调用多出网络延迟、部分失败、序列化兼容、跨服务观测等复杂性。

6. 序列化与接口契约

网络只能传输字节，所以请求参数和返回值必须序列化。常见格式包括 JSON、Protocol Buffers、MessagePack 等。

接口契约不仅包括字段名称，还包括字段类型、必填性、错误码和版本兼容规则。演进接口时应优先新增可选字段，避免复用旧字段编号、随意改变含义或删除仍被旧客户端使用的字段。

7. REST 和 gRPC 都能做服务调用

RPC 是一种调用思想，不等于某个具体协议。REST API 也能承担服务间同步调用；gRPC 则提供更典型的 RPC 体验。

面试中不要回答“RPC 与 HTTP 是并列协议”。RPC 可以运行在 HTTP 之上，gRPC 就是典型例子。

8. 最重要的认知：超时不代表服务端没有执行

客户端只知道“在规定时间内没有收到响应”，却无法仅凭超时判断请求处于哪种状态：

  • 请求根本没有到达服务端；
  • 请求已到达，但服务端尚未执行；
  • 服务端正在执行；
  • 服务端已经执行成功，但响应丢失；
  • 服务端执行失败，错误响应也没有及时到达。

分布式系统的核心难点是结果不确定性。因此重试不能单独存在，必须和幂等、超时、错误分类及可观测性一起设计。

9. 超时：任何 RPC 都必须有边界

没有超时的调用可能无限等待，占用线程、连接和内存，最终拖垮整个服务。通常需要区分连接超时、读取超时和整体截止时间。

  • 连接超时：多长时间内无法建立连接就放弃。
  • 读取超时：连接建立后，多长时间没有收到响应就放弃。
  • Deadline：整个请求链允许消耗的绝对时间上限。

超时时间不能凭感觉设置，应参考下游延迟分布、用户体验目标、调用链长度和是否允许重试。

10. 超时预算与 Deadline 传播

假设网关要求 2 秒内返回，服务 A 调用 B，B 再调用 C。A 不能给 B 2 秒、B 又给 C 2 秒，否则总时间会突破用户侧预算。

更合理的做法是传播同一个截止时间。每一层先扣除已消耗时间和自身处理余量，再把剩余预算交给下一层。如果剩余时间已不足，应尽早失败，而不是发起一个注定来不及完成的请求。

11. 重试：只对“可能恢复”的错误使用

适合重试的情况通常包括瞬时网络错误、连接被重置、服务暂时过载或明确的可重试错误码。不适合重试的情况包括参数错误、权限不足、资源不存在和业务规则拒绝。

  • 限制最大重试次数；
  • 使用指数退避，逐步拉长等待时间；
  • 加入随机抖动，避免大量客户端同时重试；
  • 重试必须服从整体 Deadline；
  • 写操作只有具备幂等保护后才能安全自动重试。

12. 幂等：同一请求执行多次，结果保持一致

查询通常天然幂等；创建订单、扣款、发放奖励等写操作通常不是。常见做法是由调用方生成唯一的 Idempotency-Key，服务端将它与处理状态和结果持久化。

  1. 第一次收到幂等键：执行业务并记录结果。
  2. 相同请求再次到达：不重复执行业务，直接返回已记录结果。
  3. 相同幂等键携带不同参数：拒绝请求并记录异常。

只在内存中记录幂等键并不可靠；进程重启或多实例部署时会失效。关键业务应使用具有唯一约束的数据库或可靠共享存储。

13. 服务发现：调用方如何找到服务

生产环境中的服务实例会扩缩容、重启和迁移，IP 地址并不固定。服务发现系统维护“服务名到健康实例列表”的映射。

  1. 服务实例启动后向注册中心登记地址和元数据。
  2. 调用方或网关根据服务名查询可用实例。
  3. 注册中心通过心跳或健康检查剔除异常实例。

常见实现包括 Kubernetes Service/DNS、Consul、etcd、Nacos，以及由服务网格代理完成的发现机制。

14. 负载均衡与健康检查

同一服务通常有多个实例。负载均衡选择具体实例，常见策略包括轮询、随机、最少连接、一致性哈希和基于延迟的选择。

健康检查分为存活检查与就绪检查：进程活着不代表它已准备好接收流量。数据库连接未建立、模型尚未加载、依赖未就绪时，实例应处于“不就绪”状态。

15. 熔断、降级与限流

  • 熔断：下游连续失败达到阈值后，暂时停止真实调用并快速失败；经过冷却期后用少量请求探测恢复情况。
  • 降级：核心依赖不可用时，返回缓存、默认值、简化结果或提示稍后再试。
  • 限流：限制单位时间内的请求量或并发数，保护服务和昂贵资源。

三者目标不同：限流控制入口压力，熔断阻止失败扩散，降级保证系统在异常时仍提供有限能力。

16. 连接池与长连接

每次 RPC 都重新建立 TCP/TLS 连接会产生握手开销。客户端通常使用连接池复用长连接。连接池需要设置最大连接数、空闲超时、连接寿命和等待队列上限。

连接池过小会排队，过大则可能耗尽客户端或服务端的文件描述符和内存。连接池不是越大越好，应结合实例并发能力和延迟目标进行压测。

17. 重试放大与级联故障

假设 A 调用 B、B 调用 C，每层都最多重试 3 次；在最坏情况下，C 可能收到 3 × 3 = 9 次请求。如果链路更长，请求量会指数放大。

下游越慢，上游越重试；重试又让下游更慢，形成正反馈。治理方法包括统一超时预算、只在一层重试、限制次数、指数退避、熔断、并发隔离和负载保护。

18. 错误模型：不要把所有失败都变成 500

调用方需要知道错误是否可重试、是否是自身参数问题、是否需要用户处理。建议至少区分：

  • 业务错误：余额不足、状态不允许、配额用尽；通常不可重试。
  • 客户端错误：参数非法、未认证、无权限；修正请求后再调用。
  • 瞬时基础设施错误：连接重置、服务过载；可能重试。
  • 永久服务错误：接口不存在、版本不兼容；自动重试无意义。
  • 超时与取消：必须单独表达，因为服务端执行状态可能不确定。

错误响应可包含稳定错误码、简短信息、是否可重试和请求 ID，但不要向外泄露堆栈、密钥或内部拓扑。

19. 可观测性：日志、指标与链路追踪

一个请求跨多个服务后，仅查看单个服务日志很难定位问题。RPC 元数据中应传播 Trace ID 和 Span ID，让分布式追踪系统还原完整调用链。

  • 指标：请求量、成功率、错误率、P50/P95/P99 延迟、超时率、重试率。
  • 日志：请求 ID、服务名、方法、错误码、耗时、重试次数；敏感参数要脱敏。
  • Trace：展示每一跳耗时、父子关系和错误位置。

常见经验是关注 RED：Rate（请求速率）、Errors（错误）、Duration（耗时）。

20. Python 示例：使用 FastAPI 与 httpx 完成同步业务调用

下面的“同步”指订单服务必须得到库存结果才能继续；代码使用异步 I/O，是为了等待网络时不阻塞事件循环。

from fastapi import FastAPI, HTTPException
import httpx
import uuid

app = FastAPI()

@app.post("/orders")
async def create_order(sku_id: str, quantity: int):
    request_id = str(uuid.uuid4())
    timeout = httpx.Timeout(connect=0.3, read=1.2, write=0.5, pool=0.2)

    async with httpx.AsyncClient(timeout=timeout) as client:
        try:
            response = await client.post(
                "http://inventory-service/reservations",
                json={"sku_id": sku_id, "quantity": quantity},
                headers={
                    "X-Request-ID": request_id,
                    "Idempotency-Key": request_id,
                },
            )
            response.raise_for_status()
        except httpx.TimeoutException:
            # 此时不能断言库存一定没有被锁定
            raise HTTPException(status_code=504, detail="库存服务响应超时")
        except httpx.HTTPStatusError as exc:
            raise HTTPException(
                status_code=502,
                detail=f"库存服务失败: {exc.response.status_code}",
            )

    reservation = response.json()
    return {"request_id": request_id, "reservation": reservation}

实际项目中不要为每次请求都新建客户端，应在应用生命周期内复用 AsyncClient，从而复用连接池。重试策略也应集中封装，而不是散落在业务代码中。

21. 在 AI Agent 运行平台中如何划分同步与异步

  • 适合同步 RPC：鉴权、租户配置读取、配额校验、短时检索、模型网关调用、用户正在等待的工具操作。
  • 适合消息队列：长时间代码执行、批量文档处理、离线评测、大文件解析、可延后的索引构建。

不要让一个 HTTP/RPC 请求无限等待长任务。可以同步创建任务并返回 task_id，再由队列执行，客户端通过轮询、SSE、WebSocket 或通知获取进度和结果。

22. Agent 平台中的额外注意事项

  • 多租户上下文传播：每次调用显式携带可信的 tenant_id、user_id、权限声明和 Trace ID；下游不能仅相信客户端自由传入的租户字段。
  • 模型调用超时：区分首 Token 延迟、整体生成截止时间和客户端取消。
  • 流式 RPC：生成式模型适合边生成边返回，但仍需处理背压、断线和取消传播。
  • 工具副作用：发邮件、扣费、创建资源等操作必须使用幂等键和审计记录。
  • 资源隔离：按租户或任务限制并发、Token、CPU/GPU 和工具调用次数，避免噪声邻居。

24. 面试回答模板

RPC 是让一个服务调用另一个进程或机器上服务的方法抽象。客户端代理负责序列化、服务发现、负载均衡和网络发送，服务端代理负责反序列化、路由和执行业务，再把结果返回。远程调用与本地调用最大的不同是网络延迟和部分失败：超时并不代表服务端没有执行。因此工程上必须同时设计 Deadline、错误分类、有限重试、幂等、熔断、限流和链路追踪。对于必须立即拿结果的路径使用 RPC；耗时或可延后的工作更适合消息队列。

25. 一句话总结

RPC 解决“服务之间如何像调用函数一样通信”；可靠 RPC 设计解决“网络不可靠、结果不确定时，系统如何仍然可控”。
