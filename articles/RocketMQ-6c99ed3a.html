RocketMQ：异步解耦、削峰填谷与最终一致性

一句话理解：RocketMQ 是分布式消息中间件。生产者把消息交给 Broker 持久化，消费者稍后独立处理。它最常解决三类问题：异步解耦、削峰填谷和跨服务最终一致性。

一、RocketMQ 是什么

假设用户支付成功后，系统还要扣减或确认库存、发放积分、创建物流任务、发送通知。如果支付服务同步调用全部下游，任何一个下游变慢或故障，都可能拖慢甚至阻塞支付主链路。

引入 RocketMQ 后，支付服务先完成最核心的本地事务，再发布一条“订单已支付”事件。库存、积分、物流和通知服务分别订阅并处理，不再要求用户同步等待所有动作完成。

核心组件

同一消费组采用集群消费时，一条消息通常只交给组内一个实例；不同消费组则能分别收到同一条消息。因此，库存、积分、物流和通知一般使用不同消费组。

RocketMQ 通常把消息顺序追加到 CommitLog，再建立面向 Topic 和 MessageQueue 的消费索引。Broker 返回发送成功，只代表消息已按当前配置被接收或持久化，不代表下游业务已经完成。

二、一条消息的完整生命周期

  1. Producer 从 NameServer 获取 Topic 的路由。
  2. Producer 选择 MessageQueue 和对应 Broker，序列化消息并发送。
  3. 消息携带 event_id、业务主键、事件类型、版本和业务数据。
  4. Broker 校验并持久化消息，然后向 Producer 返回发送结果。
  5. Consumer Group 订阅 Topic，消费者拉取或接收消息。
  6. Consumer 执行业务事务，例如发放积分。
  7. 业务事务真正提交后才返回消费成功；失败则进入延迟重试。
  8. 超过最大重试次数仍失败时进入死信队列，等待告警、修复和补偿。

三、为什么引入 RocketMQ

异步与解耦

同步 RPC 链路中，订单服务直接依赖库存、积分、物流和通知：调用延迟会叠加，一个非核心服务故障也可能传播到支付主链路；新增下游还要修改上游。

改为发布领域事件后，支付服务不必知道谁在消费。以后新增风控、数据分析或报表服务，只需新增消费者。不过，校验支付结果、修改订单核心状态等直接决定用户返回结果的操作，通常仍应留在同步主链路中。

削峰填谷

秒杀可能瞬间产生十万次请求，而数据库每秒只能稳定处理一万次。RocketMQ 先承接消息，消费者再按照下游可承受的速率处理，从而保护数据库和第三方服务。

瞬时流量高峰 → RocketMQ 暂存 → 消费者稳定处理 → 保护下游

队列只是把工作延后，并不会凭空增加总处理能力。如果生产速度长期大于消费速度，仍会持续积压，最终必须扩容消费者、优化业务或限制上游流量。

最终一致性

跨服务最危险的是“双写”：订单数据库更新成功，但消息发送失败；或者消息先发送成功，订单事务随后回滚。两边无法被一个普通本地事务原子覆盖。

Transactional Outbox 或 RocketMQ 事务消息，可以把“本地事务成功”与“消息最终可发送”关联起来；消费者通过重试、幂等和补偿，让多个服务最终收敛到一致状态。

最终一致性不等于实时一致。短暂窗口内订单可能已支付但积分尚未到账，系统保证经过重试和补偿后最终一致。

四、商城支付完整案例

订单状态与支付不确定性

PENDING_PAYMENT ──支付成功──▶ PAID ──履约完成──▶ COMPLETED

│

└──超时且确认未支付──▶ CLOSED

支付结果未知 ──主动查询支付平台──▶ PAID / FAILED / 继续等待

“支付接口超时”只说明调用方没有收到明确结果，不等于支付失败。此时不能直接再次扣款，也不能立即关单，应该先用支付单号查询支付平台的真实状态。

支付成功后的推荐流程

  1. 支付平台回调支付服务。
  2. 校验签名、商户号、订单号、金额和支付状态。
  3. 以支付单号或回调事件编号做幂等校验。
  4. 在本地事务中把支付单和订单更新为成功。
  5. 通过 Outbox 或 RocketMQ 事务消息可靠发布 OrderPaid。
  6. 库存、积分、物流和通知服务分别消费并独立重试。

即使通知服务暂时不可用，核心支付结果也不需要回滚。

用户反复点击支付怎么办

  • 每次支付尝试使用唯一幂等键或支付单号。
  • 订单已经成功时直接返回成功，不重复发起扣款。
  • 支付状态未知时优先查单，而不是盲目重试支付。
  • 订单超时关闭前必须再次确认支付状态。
  • 关单后收到迟到的成功回调，要进入对账、恢复订单或自动退款流程。

五、Outbox 与 RocketMQ 事务消息

Transactional Outbox

在同一个数据库事务中，同时更新业务数据并插入待发送事件：

BEGIN

更新订单状态为 PAID

插入 outbox_event(OrderPaid, event_id)

COMMIT

独立投递器扫描 Outbox，把事件发送到 RocketMQ；成功后标记已发送。进程即使崩溃，Outbox 记录仍在，之后可继续投递。也可通过 CDC 监听数据库变更。Outbox 通常是至少一次投递，所以仍可能重复。

RocketMQ 事务消息

  1. Producer 先发送 Half Message，消费者暂时不可见。
  2. Broker 保存 Half Message，并通知 Producer 执行本地事务。
  3. 本地事务成功则 Commit，失败则 Rollback。
  4. Broker 没收到明确结果时，会回查 Producer 的本地事务状态。
  5. 确认 Commit 后，消息才对消费者可见。

事务消息解决的是“生产者本地事务与消息发布”的一致性，不会自动保证消费者数据库事务成功。消费者仍必须重试、幂等和补偿。

再次投递同一条消息

Producer 侧也可能出现：Broker 已保存消息，但成功响应丢失，Producer 重试后形成重复。因此常见工程语义是“至少一次投递 + 业务幂等”，而不是假设消息永远只执行一次。

消费者怎样实现幂等

  • 唯一约束：以 consumer_group + event_id 建数据库唯一索引。
  • 幂等记录表：在同一事务内写入消费记录并修改业务数据。
  • 状态机条件更新：只有处于允许的前置状态才执行转换。
  • 业务唯一键：支付单号、退款单号、优惠券发放编号等。
  • Redis SET NX：可快速挡重复，但资金或核心状态不能只依赖可能过期的 Redis 锁。

event_id 已存在时触发唯一约束冲突，消费者判断为已经处理并返回成功。

重试与死信

  • 网络抖动、临时超时等瞬时错误可以退避重试，并加入随机抖动。
  • 参数错误、商品不存在等永久错误不应无限重试。
  • 消费者必须在业务事务提交后才确认成功。
  • 超过最大次数后进入 Dead Letter Queue。
  • 死信队列不是垃圾桶，应具备告警、查询、修复、重放和人工补偿流程。

七、RocketMQ 常见消息类型

顺序通常只在同一 MessageQueue 或消息组内成立。可用 order_id 作为分片键，让同一订单有序；全局顺序会严重降低并行度。

延时关单消费者不能“到点就关”，必须再次读取订单和支付状态：已支付则不关闭；明确未支付且仍待支付才条件更新为 CLOSED；状态未知则查支付平台或进入对账。

八、RocketMQ、RPC、Redis 与数据库的边界

消息队列不能代替数据库，因为消息不是长期业务事实的主要查询模型；也不能代替所有 RPC，因为部分请求必须立刻得到返回值。Redis Pub/Sub 或 Stream 能覆盖部分轻量消息场景，但不应默认视为专业消息中间件在复杂重试、死信、事务消息、海量积压和治理方面的等价替代。

九、RocketMQ 不能自动解决什么

  • 不能自动保证端到端 Exactly Once，外部数据库和第三方接口仍需业务幂等。
  • 不能把最终一致性变成强一致性，业务要接受短暂不一致窗口。
  • 不能修复错误业务代码和不可重试的业务异常。
  • 不能无限吸收流量，积压仍受磁盘、保留时间和消费能力限制。
  • 不能免费获得全局顺序；顺序越强，并行度通常越低。
  • 不能消除运维成本，需要监控 Broker、磁盘、积压、热点队列、消费延迟和死信。

十、常见面试题

为什么不全部使用 RPC？

RPC 适合必须立即得到结果的操作。积分、通知、物流等后续动作如果都用 RPC，会增加主链路延迟、耦合和故障传播；MQ 可以异步解耦，但代价是最终一致性、重复消费和额外运维。

如何保证消息不丢失？

Producer 检查发送结果并有界重试；本地事务与发布使用 Outbox 或事务消息；Broker 按要求持久化和复制；Consumer 在业务事务提交后才确认成功；全链路监控重试、积压和死信。

如何解决重复消费？

为消息设计唯一 event_id，在消费者数据库中建立唯一约束或幂等记录，且业务修改与幂等记录处于同一事务。

如何保证订单事件有序？

用 order_id 作为分片键，让同一订单进入同一队列或消息组并串行处理，不追求所有订单全局有序。

消息大量积压怎么办？

先定位生产突增、消费者故障还是单条处理变慢；修复瓶颈，在队列数足够时扩容消费者；必要时限流或降级上游；评估磁盘和保留时间，制定安全重放与补偿方案。

事务消息是不是全局分布式事务？

不是。它只协调生产者本地事务与消息发布；消费者仍独立执行，需要幂等、重试和业务补偿。

十一、面试总结

RocketMQ 的核心价值，是用异步消息解耦服务，用消息积压吸收瞬时流量，并配合事务消息或 Outbox 实现跨服务最终一致性。支付场景中，核心链路先确认支付并修改订单，再可靠发布 OrderPaid，由库存、积分、物流和通知分别消费。由于网络结果可能不确定，工程上通常采用至少一次投递，所以消费者必须幂等；多次失败进入死信并触发补偿。RocketMQ 降低了同步链路耦合，但也引入了最终一致性、积压、重复消费和运维治理成本。
