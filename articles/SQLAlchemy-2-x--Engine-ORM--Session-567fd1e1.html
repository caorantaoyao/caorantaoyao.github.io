SQLAlchemy 2.x：从 Engine、ORM 映射到 Session 与异步并发

面向 Python 后端与计算机秋招的研究笔记。资料仅来自 SQLAlchemy 2.0 官方文档与官方项目页面；示例采用 SQLAlchemy 2.x 风格。检索时官方稳定系列为 2.0，文档页面显示当前版本 2.0.51（2026-06-15）。

1. SQLAlchemy 是什么

SQLAlchemy 不是单纯的“把 Python 对象存进数据库”的 ORM。它由两套互相衔接的 API 构成：

  • SQLAlchemy Core：提供 SQL 表达式语言、Engine、Connection、事务、结果集、类型系统和连接池；
  • SQLAlchemy ORM：在 Core 之上增加 Python 类与表的映射、Session、Identity Map、Unit of Work、对象生命周期和关系加载。

SQLAlchemy 2.x 把两者进一步统一：ORM 查询使用 Core 风格的 select()，Core Connection 与 ORM Session 的事务语义也保持一致。因此，Core 与 ORM 不是互斥的两个框架，而是“底层 SQL/连接能力”和“其上的对象工作单元”。

官方来源：SQLAlchemy Unified Tutorial、SQLAlchemy Overview

3. Engine、Connection 与连接池

3.1 Engine 是什么

每个连接数据库的 SQLAlchemy 应用都需要 Engine。它是特定数据库的中心连接源，同时持有 Dialect（数据库/驱动适配）和 Pool（连接池）。create_engine() 通常是惰性的：创建 Engine 时并不会立刻打开真实 DBAPI 连接，第一次调用 connect() 或执行数据库操作时才从池中取连接。

from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg://app:secret@db.example.com/app",
    pool_pre_ping=True,
    echo=False,
)

Engine 和 sessionmaker 都是工厂，通常放在模块级，供多个请求/线程创建各自的 Connection 或 Session；不要为每条 SQL 创建一个新 Engine。

3.2 Connection 是什么

Connection 代表从 Engine 检出的一个连接资源及其事务上下文。推荐通过上下文管理器明确归还连接：

from sqlalchemy import text

with engine.connect() as conn:
    result = conn.execute(text("select id, name from users where id=:id"), {"id": 1})
    row = result.one_or_none()

写操作可以采用两种 2.x 事务风格：

# begin once：代码块成功则提交，异常则回滚
with engine.begin() as conn:
    conn.execute(...)
    conn.execute(...)

# commit as you go：第一次执行时 autobegin，显式结束
with engine.connect() as conn:
    conn.execute(...)
    conn.commit()

退出 engine.connect() 块但没有提交时，未结束事务会被回滚；“关闭连接”通常是把 DBAPI 连接归还池，而非真正断开 TCP。

官方来源：Establishing Connectivity - the Engine、Working with Transactions and the DBAPI、Working with Engines and Connections

4. SQLAlchemy 2.x 的声明式映射

Declarative 是官方所称的主要映射风格。2.x 推荐用 DeclarativeBase、Mapped[T] 和 mapped_column()；DeclarativeBase 取代了旧式 declarative_base() 作为更适合 PEP 484 类型工具的写法。

from __future__ import annotations

from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "user_account"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50), unique=True)
    full_name: Mapped[str | None]

    addresses: Mapped[list[Address]] = relationship(
        back_populates="user",
        cascade="all, delete-orphan",
    )


class Address(Base):
    __tablename__ = "address"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(320))
    user_id: Mapped[int] = mapped_column(ForeignKey("user_account.id"))

    user: Mapped[User] = relationship(back_populates="addresses")

关键点：

  • Mapped[int] 描述 ORM 映射属性；mapped_column() 描述列的额外数据库配置；
  • Mapped[str] 与 Mapped[str | None] 可参与推导列类型和可空性，但约束仍应按数据库设计明确检查；
  • 每个 ORM 映射通常必须有主键，因为 Identity Map 需要用数据库身份识别对象；
  • relationship() 描述对象之间的关联与加载/级联行为，外键列才是数据库层面的引用约束；
  • Base.metadata.create_all(engine) 适合教程、小工具和测试，不应被当成生产数据库迁移系统。

官方来源：Mapping Classes with Declarative、Declarative Mapping Styles、Table Configuration with Declarative

5. Session：ORM 的工作边界

Session 是 ORM 与数据库交互的主接口，也是已加载/关联对象的“持有区”。它会在需要时从绑定的 Engine 取出 Connection 并建立事务，在提交、回滚或关闭后归还连接。

推荐把 sessionmaker 作为长期工厂，把 Session 实例限定在一次明确的逻辑操作中：

from sqlalchemy.orm import sessionmaker

SessionLocal = sessionmaker(engine, expire_on_commit=False)

with SessionLocal.begin() as session:
    session.add(User(name="alice"))
# 正常退出：flush + commit + close；异常退出：rollback + close

Web 应用常见边界是“每个请求一个 Session”：请求开始创建，写请求在业务成功后提交，异常回滚，请求结束关闭。事务边界应由调用层统一掌控，不要让每个仓储函数私自创建和提交 Session，否则跨多个写操作的原子性会被切碎。

官方来源：Session Basics

6. Identity Map 与 Unit of Work

6.1 Identity Map

Identity Map 保证在同一 Session 内，同一个映射类、同一个主键通常对应同一个 Python 对象：

u1 = session.get(User, 1)
u2 = session.get(User, 1)
assert u1 is u2

它不是通用查询缓存：按非主键条件执行 select() 仍会访问数据库，只是在结果回填时复用 Identity Map 中已有身份的对象。Session.get(User, 1) 才会先直接检查 Identity Map。

6.2 Unit of Work

Session 监控映射对象的新增、修改和删除，在 flush 时分析依赖关系并生成 INSERT、UPDATE、DELETE。这个模式叫 Unit of Work。

user = session.get(User, 1)
user.name = "new-name"      # 只修改内存状态
session.flush()              # SQL 已发出，但事务尚未提交
session.commit()             # 提交数据库事务

必须区分：

  • flush()：把内存变更同步为当前事务中的 SQL，仍可回滚；
  • commit()：会先无条件 flush，再提交事务；
  • autoflush：执行某些查询前自动 flush，让查询看见本事务内的待写入状态；它不是自动提交；
  • flush 失败后，即便数据库驱动已经回滚，也必须显式 session.rollback()，才能让 Session 恢复可用状态。

官方来源：What does the Session do?、Flushing、Committing

7. ORM 对象生命周期

映射实例有五个核心状态：

  • Transient（瞬时）：未进入 Session、未持久化，没有数据库身份；
  • Pending（待持久化）：已 add()，等待下一次 flush INSERT；
  • Persistent（持久）：在 Session 内并对应数据库记录；
  • Deleted（待删除）：DELETE 已 flush，但事务还未完成；
  • Detached（游离）：具有数据库身份，但不再关联 Session。

Detached 对象中已经加载且未过期的普通属性仍可读；它不能再触发延迟加载或刷新。可用 inspect(obj) 查看 transient/pending/persistent/deleted/detached。

官方来源：State Management

8. 事务：autobegin、commit、rollback 与 SAVEPOINT

Session 默认使用 autobegin：第一次 add()、execute()、查询或修改持久对象时进入事务状态；这不等同于旧式库级 autocommit。也可以用 Session.begin() 明确框定边界：

with SessionLocal() as session:
    try:
        with session.begin():
            # 一个原子业务操作
            ...
    except Exception:
        # begin 上下文已回滚
        raise

嵌套局部失败可使用 session.begin_nested() 建立 SAVEPOINT，但是否支持及具体行为受数据库影响。SQLAlchemy 2.x 中 commit() / rollback() 作用于最外层事务；SAVEPOINT 句柄需由嵌套事务对象自行提交或回滚。

保持事务短小：不要在事务中等待网络调用、人工输入或耗时计算。Session 生命周期与事务生命周期不是同一个概念；一个 Session 技术上可依次承载多个事务，但一次业务操作一个清晰 Session/事务边界通常最容易推理。

官方来源：Session Basics - Auto Begin、Transactions and Connection Management

9. SQLAlchemy 2.x 的查询方式

2.x 推荐使用 select()，不再以旧式 session.query() 作为主线：

from sqlalchemy import select

stmt = (
    select(User)
    .where(User.name.ilike("a%"))
    .order_by(User.id.desc())
    .limit(20)
)

users = session.scalars(stmt).all()

常见返回方式：

session.execute(select(User.id, User.name)).all()   # Row 元组式结果
session.scalars(select(User)).all()                 # 只取每行第一列，即 User
session.scalar(select(User).where(User.id == 1))    # 单个标量或 None
session.scalars(stmt).one()                         # 必须恰好一个，否则异常
session.scalars(stmt).one_or_none()                 # 0 或 1 个
session.get(User, 1)                                # 按主键，优先 Identity Map

不要用 .first() 误以为自动给 SQL 加 LIMIT 1；2.x 的 Result API 中 first() 本身不会自动修改语句，应在查询上显式 .limit(1)。当 joinedload() 加载一对多/多对多集合造成父行重复时，需要对结果调用 .unique()，官方会在缺少它时抛错。

官方来源：Writing SELECT statements for ORM Mapped Classes、ORM Querying Guide、SQLAlchemy 2.0 Migration - ORM Usage

10. relationship 到底做了什么

relationship() 建立的是 ORM 对象导航和 Unit of Work 依赖，不会代替数据库外键。双向关系推荐用显式 back_populates：

class User(Base):
    # ...
    addresses: Mapped[list[Address]] = relationship(back_populates="user")

class Address(Base):
    # ...
    user_id: Mapped[int] = mapped_column(ForeignKey("user_account.id"))
    user: Mapped[User] = relationship(back_populates="addresses")

类型注解能表达常见基数：集合注解表示 one-to-many；非集合标量可表示 many-to-one 或约定上的 one-to-one。真正的一对一还应配数据库 UNIQUE 约束，防止并发写入破坏唯一性。

级联需要谨慎：

  • 默认 save-update, merge 不是数据库的 ON DELETE；
  • delete-orphan 通常配置在一对多的“一”侧，表示子对象脱离父集合后应删除；
  • 多对多双方都配置 cascade="all, delete" 可能沿整个关系图级联加载并删除；
  • 数据库已有 ON DELETE CASCADE 时，ORM 通常还需匹配 cascade，并根据需要设置 passive_deletes=True，使两套状态管理一致。

官方来源：Basic Relationship Patterns、Cascades

11. 关系加载策略与 N+1

关系加载分为延迟加载、预加载和禁止加载。未另行配置的 relationship() 默认是 lazy="select"：第一次访问属性时额外执行 SELECT。这很方便，也可能产生 N+1。

# 1 条查询取 N 个用户
users = session.scalars(select(User)).all()

# 若 addresses 未预加载，循环最多再发 N 条 SELECT
for user in users:
    print(user.addresses)

常用策略：

策略

行为

典型选择

lazyload / 默认 lazy

访问关系时逐个 SELECT

偶尔访问、简单 many-to-one 且目标已在 Identity Map

selectinload

主查询后用父主键 IN (...) 批量加载

通常是集合关系的首选

joinedload

同一结果集 LEFT OUTER JOIN

常见 many-to-one；集合时注意行膨胀和 .unique()

特定后端/复杂场景；一般不如 select-in 简洁

测试或接口层防止意外 SQL

from sqlalchemy.orm import raiseload, selectinload

stmt = (
    select(User)
    .options(selectinload(User.addresses), raiseload("*"))
)
users = session.scalars(stmt).all()

官方建议中，一对多/多对多集合通常优先 selectinload()；many-to-one 通常可选 joinedload()。选择标准不是“查询条数越少越好”，而是 SQL 次数、SQL 复杂度、返回数据量与数据库限制之间的权衡。

官方来源：Relationship Loading Techniques

12. DetachedInstanceError、过期与 expire_on_commit

12.1 为什么出现 DetachedInstanceError

对象离开 Session 后，如果访问的是未加载关系、deferred 列或已过期属性，ORM 需要查数据库，却没有可用 Session，于是出现类似：

Parent instance <x> is not bound to a Session;
lazy load/deferred load/refresh/etc. operation cannot proceed

常见触发链：查询对象 → 提交使属性过期 → 关闭 Session 使对象 detached → 模板/序列化器再访问属性。

12.2 正确处理

优先方案是：

  1. 在 Session 有效期内，用 selectinload() / joinedload() 加载输出需要的数据；
  2. 在数据访问层转换为 DTO/Pydantic/普通 dict，再离开 Session；
  3. 若确实需要继续操作 detached 对象，显式重新关联或 merge()，理解它返回的是 Session 内的目标实例；
  4. 不要把“让全局 Session 永不关闭”当修复，这会混乱事务边界和连接资源。

12.3 expire_on_commit

同步 Session 默认 expire_on_commit=True：提交后实例属性被标为 expired，下次访问会在新的事务中重新加载，以获得较新的状态。若对象此时已经 detached，则无法自动刷新。

Web 展示层经常设置 expire_on_commit=False，使提交后已加载字段仍可读；代价是对象可能保留提交时的快照，必要时应显式 refresh() 或重新查询。异步 ORM 示例通常也设置 expire_on_commit=False，避免提交后的普通属性访问触发隐式 IO。

官方来源：Error: Parent instance is not bound to a Session、Session Basics - Committing、Asyncio - Preventing Implicit IO

13. 并发、线程与 AsyncSession

Session 是一个可变、有状态、代表单个数据库事务的对象，不是线程安全共享容器。AsyncSession 是同步 Session 的薄代理，也不允许多个 asyncio task 同时共享一个实例。

官方并发模型非常明确：

  • Session per thread；
  • AsyncSession per task。
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

async_engine = create_async_engine(
    "postgresql+asyncpg://app:secret@db.example.com/app",
    pool_pre_ping=True,
)
AsyncSessionLocal = async_sessionmaker(
    async_engine,
    expire_on_commit=False,
)

async def create_user(name: str) -> None:
    async with AsyncSessionLocal.begin() as session:
        session.add(User(name=name))

在 asyncio.gather() 中，每个子任务内部都要各自创建 AsyncSession。异步模式还要避免普通属性访问产生隐式 IO：应提前 eager load、用 AsyncAttrs.awaitable_attrs 显式等待，或配置 lazy="raise"；官方通常建议 AsyncSession 使用 expire_on_commit=False。

异步驱动不是让一个事务并行执行多条命令。一个数据库连接/事务本身有顺序状态；真正并发意味着多个任务拥有各自的 Session、Connection 与事务。

官方来源：Is the Session thread-safe?、AsyncSession with Concurrent Tasks、Preventing Implicit IO

14. 连接池：性能资源也是容量边界

大多数同步 create_engine() 默认已集成 QueuePool，通常无需手动“开启连接池”。常用参数是：

engine = create_engine(
    url,
    pool_size=10,       # 常驻池容量
    max_overflow=20,    # 超出 pool_size 的临时连接上限
    pool_timeout=30,    # 等待连接的超时秒数
    pool_recycle=1800,  # 超过年龄后在下次 checkout 时回收
    pool_pre_ping=True, # checkout 时检测失效连接
)

常见误区：

  • 池耗尽不是单纯把池调大就好：先检查 Session/Connection/Result 是否按时关闭、事务是否过长、数据库最大连接数是否匹配；
  • pool_pre_ping 只处理取连接时发现的陈旧连接：不能无损挽救事务执行到一半发生的断线；原事务已丢失，应由应用决定是否重试整个事务；
  • pool_recycle 是连接年龄回收，不是查询超时；
  • fork 后不能共享父进程池里的真实连接：子进程应初始化自己的 Engine/Pool，或在子进程初始化时 engine.dispose(close=False)，确保新建连接池；
  • Engine 可全局，Connection/Session 不可跨并发任务共享。

AsyncEngine 会使用与 asyncio 兼容的池；create_async_engine() 不能搭配普通 QueuePool。SQLite 等方言可能根据数据库形式选择不同池实现，因此不要假设所有后端行为完全相同。

官方来源：Connection Pooling、QueuePool API、Using Connection Pools with Multiprocessing or os.fork()

15. 一套推荐的同步项目骨架

# db.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine(DB_URL, pool_pre_ping=True)
SessionLocal = sessionmaker(engine, expire_on_commit=False)
# service.py
from sqlalchemy import select
from sqlalchemy.orm import selectinload

def get_user_detail(user_id: int) -> dict | None:
    with SessionLocal() as session:
        stmt = (
            select(User)
            .where(User.id == user_id)
            .options(selectinload(User.addresses))
        )
        user = session.scalar(stmt)
        if user is None:
            return None
        return {
            "id": user.id,
            "name": user.name,
            "addresses": [a.email for a in user.addresses],
        }

def rename_user(user_id: int, new_name: str) -> None:
    with SessionLocal.begin() as session:
        user = session.get(User, user_id)
        if user is None:
            raise LookupError("user not found")
        user.name = new_name

这套骨架体现四个边界：Engine/工厂长期存在；Session 按操作创建；事务由外层上下文管理；返回到展示层前完成必要加载或 DTO 转换。

官方来源：Session Basics、Relationship Loading Techniques

16. 高频判断题与纠错

  1. commit() 才会发 INSERT？ 错。查询前 autoflush 或显式 flush() 都可能先发 DML；commit 负责最终提交。
  2. Session 是一级缓存，所以相同条件查询不会访问数据库？ 错。Identity Map 按主键身份复用对象，不缓存任意查询结果。
  3. 关闭 Session 后对象完全不能读？ 错。已加载且未过期属性通常还能读，不能的是需要数据库 IO 的属性。
  4. relationship() 自动建立数据库外键？ 错。ForeignKey/DDL 才建立数据库约束，relationship 管对象关系。
  5. 异步 Session 可以被 gather 中的任务共享？ 错。必须 AsyncSession per task。
  6. N+1 的唯一解是 JOIN？ 错。集合通常优先 selectinload()；joinedload() 还可能造成行膨胀。
  7. expire_on_commit=False 会关闭事务一致性？ 不准确。它只阻止提交后自动过期；对象可能变旧，数据库事务隔离仍由数据库控制。
  8. 连接池越大吞吐越高？ 错。数据库容量、事务耗时、锁竞争和应用并发共同决定最佳值。
  9. Engine 每请求创建更安全？ 错。Engine 是连接池和连接工厂，通常长期复用；每请求创建的是 Session。
  10. flush 失败后捕获异常即可继续用 Session？ 错。必须 rollback 或关闭丢弃 Session。

17. 面试回答主线

如果被问“SQLAlchemy ORM 是怎么工作的”，可以按这条链路回答：

  1. Engine 封装数据库 Dialect 与连接池，提供连接资源；
  2. Declarative Mapping 用 Mapper 把 Python 类属性映射到 Table/Column；
  3. Session 表示一次对象级数据库会话和逻辑事务；
  4. Identity Map 保证同一 Session 内同一数据库身份只有一个对象实例；
  5. Unit of Work 追踪 new/dirty/deleted，在 flush 时按依赖生成 DML；
  6. select() 生成 SQL 表达式，Session 执行后把行装配成对象；
  7. relationship() 提供对象导航，但加载策略决定是否出现额外 SQL；
  8. 提交会先 flush，默认再使对象过期；关闭会释放事务/连接资源并使对象 detached；
  9. 并发遵循 Session per thread、AsyncSession per task。

这条主线把“连接 → 映射 → 查询 → 对象状态 → 写入 → 事务 → 资源释放”串成一个完整系统，而不是只背 API。
