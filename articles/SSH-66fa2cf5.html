SSH：从握手、认证到隧道与文件传输

面向计算机秋招的 SSH 机制笔记，仅采用 IETF SSH 标准与 OpenSSH/OpenBSD 官方手册作为资料来源。

1. SSH 到底解决什么问题

SSH（Secure Shell）不是“一个远程终端命令”，而是一套在不可信网络上提供安全远程登录及其他网络服务的协议族。它的目标至少包含三件事：

  1. 服务器身份认证：客户端确认连接的是目标服务器，而不是中间人；
  2. 机密性与完整性：传输内容不可被旁观者读取，也不能被无声篡改；
  3. 用户身份认证：服务器确认当前客户端用户是否有权登录。

RFC 4251 把 SSH 分成三个叠加的主要协议：RFC 4251 §1

应用：Shell / Exec / SFTP / TCP 转发 / X11
                 │
Connection Protocol（连接协议，RFC 4254）
  └─ 把一条加密连接复用成多个逻辑 Channel
                 │
User Authentication Protocol（用户认证协议，RFC 4252）
  └─ 认证客户端用户：publickey/password/keyboard-interactive 等
                 │
Transport Layer Protocol（传输层协议，RFC 4253）
  └─ 密钥交换、服务器认证、加密、完整性、可选压缩
                 │
       通常运行在 TCP 之上（默认端口 22）

这里的“Transport Layer”是 SSH 协议栈自己的传输层，不等同于 OSI/TCP/IP 分层中的传输层。它通常运行在 TCP 这样的可靠字节流之上。

2. 建立 SSH 连接：握手和密钥交换

2.1 总体顺序

一次典型连接可以概括为：

算法不是由某一端单方面强制决定。双方在 SSH_MSG_KEXINIT 中分别给出 KEX、服务器主机密钥、双向加密、双向 MAC 和压缩算法列表；例如加密算法按“客户端优先列表中，第一个也被服务器支持的算法”选出，没有共同算法就断开连接。RFC 4253 §7.1

2.2 密钥交换做了什么

以 RFC 4253 中的 Diffie–Hellman 流程为例：客户端发送临时交换值 e，服务器返回主机公钥 K_S、临时交换值 f，以及服务器用主机私钥对交换哈希 H 的签名。H 覆盖客户端/服务器版本字符串、双方 KEXINIT、服务器主机公钥、交换值以及共享秘密，因此把算法协商、临时密钥和服务器长期身份绑定在一起。RFC 4253 §8

密钥交换输出：

  • 共享秘密 K；
  • 交换哈希 H；
  • 由二者派生出的加密密钥、完整性密钥和 IV；
  • 第一次交换的 H 同时成为整个连接不再改变的 session identifier，后续用户公钥认证签名也会包含它，从而把认证证明绑定到当前连接。RFC 4253 §7.2

SSH 可以在现有加密连接中重新进行 KEX（rekey），但会话标识保持不变。RFC 4253 §9

2.3 主机密钥不等于会话加密密钥

这是常见误区：服务器主机私钥通常不直接加密整段会话数据。它的核心用途是对密钥交换内容签名，证明服务器身份；会话数据由密钥交换产生的临时对称密钥加密。主机长期密钥与临时会话密钥分工，才让身份认证和高效传输同时成立。

3. 主机认证：known_hosts 信任服务器

服务器的主机公钥用于让客户端确认“我连接的是谁”。RFC 4251 给出两种信任模型：

  • 客户端维护“主机名 → 主机公钥”的本地数据库；
  • 由受信任 CA 为主机密钥签发证书，客户端只需信任 CA 根公钥。

首次连接时如果不验证主机密钥，连接仍能抵抗被动窃听，却容易遭受主动中间人攻击。RFC 4251 §4.1

OpenSSH 的本地数据库就是：

用户级：~/.ssh/known_hosts
系统级：/etc/ssh/ssh_known_hosts

known_hosts 的每一行通常包含：可选 marker、主机名、密钥类型、Base64 公钥和可选注释；@cert-authority 表示主机 CA，@revoked 表示已撤销密钥。OpenBSD sshd(8)：SSH_KNOWN_HOSTS FILE FORMAT

4. 用户认证：authorized_keys 信任用户

主机认证完成后，用户认证协议在加密传输层之上运行。RFC 4252

4.1 公钥认证并不传私钥

客户端先声明用户名、服务、算法和公钥；正式认证时，用对应私钥对包含 session identifier 和整个认证请求的数据签名。服务器执行两个检查：

  1. 这把公钥是否被允许登录该账户；
  2. 签名是否正确，即客户端是否真正持有私钥。

私钥不会发送到服务器。RFC 4252 §7

OpenSSH 通常从目标账户的以下文件判断哪些公钥被授权：

~/.ssh/authorized_keys

每行格式是：

[options] keytype base64-key [comment]

known_hosts 与 authorized_keys 不可混淆：

4.2 密码认证的准确含义

SSH 密码认证报文中包含明文密码字段，但整个 SSH 报文已被传输层加密；因此不是“先在客户端把密码做哈希再发送”。服务端最终仍会得到密码用于本地验证。RFC 4252 明确要求：如果底层 SSH 传输不提供机密性，就应禁用密码认证。RFC 4252 §8

密码、keyboard-interactive、公钥是不同认证方法。OpenSSH 的 AuthenticationMethods 可要求多步认证，例如 publickey,keyboard-interactive 表示两种方法都必须成功，而不是二选一。OpenBSD sshd_config(5)：AuthenticationMethods

5. Channel：为什么一条 SSH 连接能同时做很多事

完成认证后，Connection Protocol 把单条加密隧道复用成多个逻辑 Channel。终端会话、命令执行、转发连接等都是 Channel；双方都可以发起，Channel 有各自编号、流量窗口和最大包大小。RFC 4254 §5

常见 Channel/请求包括：

  • session：远程 shell、执行单个命令、启动 subsystem；
  • pty-req：在 session 中申请伪终端；
  • shell：启动交互式 shell；
  • exec：执行命令；
  • subsystem：启动预定义子系统，例如 SFTP；
  • direct-tcpip / forwarded-tcpip：TCP 端口转发。

所以 ssh user@host、ssh user@host command、SFTP、端口转发并不是几套完全独立的加密连接；它们都可以构建在同一个 SSH Connection Protocol 和 Channel 抽象之上。Channel 有独立流控，EOF 只表示一个方向不再发送，双向关闭需要双方交换 SSH_MSG_CHANNEL_CLOSE。RFC 4254 §5.2–5.3

6. 三种端口转发

6.1 本地转发 -L

ssh -L 127.0.0.1:15432:db.internal:5432 user@bastion

含义：SSH 客户端在本机监听 127.0.0.1:15432；每个进入该端口的连接通过 SSH Channel 到远端，并由远端一侧连接 db.internal:5432。OpenBSD ssh(1)：-L

典型场景：本机通过堡垒机访问内网数据库。

6.2 远程转发 -R

ssh -R 127.0.0.1:18080:127.0.0.1:8080 user@server

含义：在远端服务器监听 127.0.0.1:18080；连接经 SSH 回到客户端，由客户端一侧访问 127.0.0.1:8080。OpenBSD ssh(1)：-R

远程监听默认通常只绑定回环地址；绑定外部接口还受服务端 GatewayPorts 控制。把监听地址设为 0.0.0.0 或 * 可能把原本本地的服务暴露给整个网络。

6.3 动态转发 -D

ssh -D 127.0.0.1:1080 user@bastion

客户端在本机提供 SOCKS4/5 代理，应用把目的地址交给 SOCKS；SSH 远端再连接实际目的地址。OpenBSD ssh_config(5)：DynamicForward

6.4 转发本质与边界

端口转发不是 VPN 的同义词：通常它只代理选定 TCP 连接；-D 是 SOCKS 代理，不会自动接管所有系统流量。转发还可能绕过网络边界，因此服务端应按需要使用 AllowTcpForwarding、PermitOpen、PermitListen、DisableForwarding，单把 key 还可用 authorized_keys 选项收紧。OpenBSD sshd_config(5)

7. ssh-agent：保管私钥操作能力，而不是传送私钥

ssh-agent 是保存私钥身份并代为执行签名的本地进程。客户端通过 SSH_AUTH_SOCK 指向的 Unix-domain socket 调用它；ssh-add 用于加入、列出或删除身份。OpenBSD ssh-agent(1)、OpenBSD ssh-add(1)

实用命令：

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
ssh-add -l                 # 列出指纹
ssh-add -t 1h -c ~/.ssh/id_ed25519  # 一小时有效，每次使用需确认
ssh-add -D                 # 清空 Agent

Agent 转发 ssh -A 不会把私钥文件复制到跳板机，但会把“请求本地 Agent 签名”的能力转发过去。能访问远端转发 socket 的攻击者虽然不能直接导出密钥材料，却可能利用已加载身份发起认证。因此 OpenSSH 官方明确要求谨慎使用 Agent 转发，并指出 ProxyJump 往往是更安全的替代方案。OpenBSD ssh(1)：-A

降低风险的方法包括：默认不启用 ForwardAgent；为 key 设置生命周期 ssh-add -t、逐次确认 -c，或使用目的地主机约束 ssh-add -h；在可能时使用 ProxyJump 而不是把 Agent 暴露给堡垒机。

8. SFTP 与 SCP

8.1 SFTP

SFTP 是通过加密 SSH transport 运行的文件传输协议/子系统，复用 SSH 的主机认证、用户认证和加密能力；它不是“FTP 加 TLS”，也通常不需要 FTP 的独立控制/数据端口。OpenBSD sftp(1)

sftp user@host
sftp user@host:/remote/path

8.2 SCP

scp 是 OpenSSH 的文件复制命令。当前 OpenSSH 的 scp 默认使用 SFTP 协议传输，同时保留 -O 强制使用旧 SCP protocol 以兼容旧服务器或特定路径展开行为。OpenBSD scp(1)

因此必须区分：

  • scp：命令行工具及其用户体验；
  • SFTP：当前 scp 默认使用的传输协议；
  • legacy SCP protocol：可通过 scp -O 显式启用的旧协议。

不要笼统地说“scp 永远使用旧 SCP 协议”。脚本需要目录同步、删除语义、断点或复杂筛选时，也不能仅凭“都走 SSH”就认为 scp、sftp、rsync 可完全互换。

9. 现代公钥算法：几个容易误解的名字

  • RFC 8332 为 SSH 定义 rsa-sha2-256 和 rsa-sha2-512 签名算法，继续使用已有 RSA key format，但签名哈希改为 SHA-2；这说明“RSA 密钥”与“ssh-rsa（RSA + SHA-1 签名算法名）”不是同一个概念。RFC 8332
  • RFC 8709 定义 SSH 的 ssh-ed25519 与 ssh-ed448 公钥/签名算法。RFC 8709
  • 实际客户端/服务端支持与默认算法应使用本机 ssh -Q key、ssh -Q key-sig、ssh -Q kex、ssh -Q cipher 查询，不应把某个版本的默认列表当成永恒标准。OpenBSD ssh(1)

新生成的一般软件密钥可优先考虑 Ed25519；已有 RSA 密钥在双方支持时可使用 RSA-SHA2 签名。兼容旧系统时应针对目标版本评估，而不是为了“能连上”全局重新启用弱旧算法。

10. 实用配置示例

客户端 ~/.ssh/config：

Host work-bastion
    HostName bastion.example.com
    User caoran
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes
    StrictHostKeyChecking yes
    ForwardAgent no
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host internal-api
    HostName api.internal.example.com
    User deploy
    ProxyJump work-bastion
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes

说明：配置项会按命令行、用户配置、系统配置依次读取，而且对每个参数通常采用“第一个获得的值”；因此更具体的 Host 块通常应放在通配块之前。OpenBSD ssh_config(5)

11. 安全实践清单

客户端

  1. 首次连接通过可信渠道核对主机指纹；自动化部署预置 known_hosts 或主机 CA，不使用 StrictHostKeyChecking no 掩盖问题。
  2. 私钥设置强口令并限制文件权限；ssh-add 会忽略可被其他人访问的 identity 文件。OpenBSD ssh-add(1)
  3. 不把私钥提交到 Git、镜像或服务器；按用途分 key，便于撤销和审计。
  4. 默认关闭 Agent 转发；确需使用时设置生命周期、确认或目的地约束。
  5. 对隧道显式绑定 127.0.0.1，除非确实需要向局域网/公网开放。
  6. 使用 ssh -vvv 排查连接与认证，用 ssh -G host 查看最终生效配置，不靠猜测。

服务端

  1. 优先公钥或硬件安全密钥；确认无密码业务需求后再关闭 PasswordAuthentication，避免配置变更把自己锁在门外。
  2. 限制 root 直接登录；OpenSSH 当前 PermitRootLogin 默认语义可配置为 prohibit-password、forced-commands-only 或 no。OpenBSD sshd_config(5)：PermitRootLogin
  3. 使用 AllowUsers/AllowGroups、Match 按用户和来源收敛入口；高价值系统可用 AuthenticationMethods 要求多因素。
  4. 限制端口、Agent、X11、TUN 和 remote forwarding；自动化 key 用 restrict,command=... 做最小权限。
  5. 保证 ~/.ssh 和 authorized_keys 不可被其他用户写入；StrictModes 默认会检查相关所有权和权限。OpenBSD sshd(8)
  6. 对暴力尝试和连接耗尽使用系统防火墙、日志审计以及 MaxAuthTries、MaxStartups 等控制；修改前用 sshd -t 检查配置语法。
  7. 不要盲目复制网络上的“最强算法清单”：OpenSSH 默认会演进，硬编码过窄列表容易造成升级或兼容故障；确需合规基线时再显式配置并持续复审。

12. 高频误区纠正

误区

正确理解

“SSH 就是远程 Shell”

Shell 只是 Connection Protocol 上的一种 session；SSH 还承载命令、SFTP、转发等。

“使用密钥登录就不需要验证服务器”

用户公钥认证解决服务器信任用户；known_hosts/主机 CA 才解决客户端信任服务器。

“服务器主机密钥直接加密所有数据”

主机密钥主要签名 KEX 以证明身份；会话数据使用协商派生的对称密钥。

“SSH 密码先哈希后发送”

Password 方法传输密码字段，但整个 SSH 报文由传输层加密。

“公钥认证会把私钥传给服务器”

客户端在本地签名，服务器使用公钥验证；私钥不离开客户端/Agent/硬件。

“首次看到指纹输入 yes 就安全了”

未经可信渠道核验时只能获得后续一致性，首次连接仍可能被 MITM。

“ssh-agent -A 很安全，因为私钥没复制过去”

私钥不被导出，但恶意远端可利用转发的 Agent 请求签名并冒用身份。

“端口转发会自动保护所有网络流量”

-L/-R 只转发指定连接，-D 仅提供 SOCKS；应用必须实际使用它。

“关闭服务端 TCP forwarding 就一定安全”

有 shell 权限的用户可能运行自己的转发器；OpenSSH 手册明确指出，除非同时剥夺 shell，否则单独关闭 forwarding 并不必然提升安全性。OpenBSD sshd_config(5)

“scp 一定使用旧 SCP 协议”

当前 OpenSSH scp 默认使用 SFTP，-O 才强制 legacy SCP protocol。

“ssh-rsa 被弃用等于所有 RSA key 都不能用”

ssh-rsa 特指 SHA-1 签名算法；RFC 8332 的 RSA-SHA2 可继续使用 RSA key。

13. 面试回答主线

可以用下面的 90 秒结构回答“SSH 如何工作”：

  1. SSH 是运行在可靠字节流（通常 TCP）上的三层协议族：Transport、User Authentication、Connection。
  2. Transport 阶段双方协商 KEX、主机密钥、Cipher、MAC 等；KEX 产生共享秘密和会话密钥，服务器用主机私钥签名交换哈希。
  3. 客户端用 known_hosts 或主机 CA 验证服务器，避免 MITM。
  4. 安全通道建立后才进行用户认证；公钥认证是客户端对绑定当前 session 的请求签名，服务器用 authorized_keys 中的公钥验签，私钥不上传。
  5. 认证成功后 Connection Protocol 把一条连接复用成多个有独立流控的 Channel，用于 shell、exec、SFTP 和端口转发。
  6. SSH 安全不仅靠密码算法，还依赖首次主机密钥核验、私钥保护、Agent 转发边界以及服务端最小权限配置。
