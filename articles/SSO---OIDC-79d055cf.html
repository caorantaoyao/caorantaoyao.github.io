SSO 单点登录：原理、OIDC 流程与浏览器会话边界

一句话结论

SSO 让多个业务系统共同信任一个身份提供方。用户在同一浏览器中第一次完成认证后，身份提供方保存自己的登录 Cookie；其他业务系统再次把浏览器重定向到该身份提供方时，它可以复用已有会话并快速返回身份结果。业务系统之间通常不共享 Cookie，每个系统仍建立和管理自己的本地 Session。

前置知识与边界

  • 前置知识：HTTP 重定向、Cookie、Session、JWT、认证与授权的区别。
  • 适用范围：公司内部系统、多个 SaaS 产品、微服务入口、移动端和第三方身份联合。
  • 不解决的问题：SSO 只统一身份认证，不自动决定用户能访问哪些业务资源。
  • 核心边界：OIDC/SAML 确认“用户是谁”，Casbin/RBAC/ABAC 判断“用户能做什么”。

1. SSO 是能力，不是单一协议

SSO（Single Sign-On）描述的是“一次登录，访问多个相互信任系统”的能力和用户体验。它可以由不同协议实现：

2. 核心角色

用户和浏览器

用户通过浏览器访问多个业务系统。浏览器负责保存各个域名下相互隔离的 Cookie，并在重定向过程中传递授权码或 SAML Response。

身份提供方 IdP

身份提供方负责：

  • 展示登录页面并验证密码、扫码、Passkey 或 MFA。
  • 维护统一登录会话和风险状态。
  • 签发身份断言或令牌。
  • 执行账号冻结、认证强度和重新认证策略。

OIDC 中通常称为 OpenID Provider（OP），例如企业统一身份平台、Keycloak、Auth0、Okta 或 Microsoft Entra ID。

业务系统

业务系统依赖 IdP 确认身份。OIDC 中称为 Relying Party（RP），SAML 中称为 Service Provider（SP）。业务系统验证身份结果后，通常建立自己的本地 Session。

3. SSO 为什么能做到“第二次免登录”

假设存在：

sso.example.com       统一身份平台
project.example.com   项目系统
wiki.example.com      知识库

第一次访问项目系统：

随后访问知识库：

访问知识库
→ 知识库发现没有自己的 Session
→ 重定向到同一个 IdP
→ 浏览器自动携带 sso.example.com 的 Cookie
→ IdP 识别已有会话，无需再次输入密码
→ 返回新的授权码
→ 知识库验证身份并创建自己的 Session

关键点是：项目系统和知识库并不读取彼此的 Cookie。它们都把浏览器重定向到 IdP，由 IdP 读取自己域名下的 Cookie。

4. Cookie 与浏览器边界

同一个 Chrome 用户配置中可能存在：

Chrome Cookie 存储
├── sso.example.com 的 IdP Cookie
├── project.example.com 的本地 Session Cookie
└── wiki.example.com 的本地 Session Cookie

换成 Safari 后，Cookie 存储是独立的：

所以，更准确的 SSO 有效范围通常是：

同一浏览器
+ 同一浏览器用户配置
+ 尚未失效的 IdP 会话

以下情况通常需要重新认证：

  • 从 Chrome 换到 Safari 或 Firefox。
  • 换电脑或手机。
  • 打开独立的无痕窗口。
  • 切换 Chrome 用户配置。
  • 清除 Cookie。
  • IdP Cookie 过期或被管理员撤销。
  • 风险策略要求重新认证或补充 MFA。

不同浏览器不能直接共享 Cookie，这是安全隔离边界。少数场景看起来能在新浏览器“自动登录”，通常是操作系统集成认证、Kerberos、客户端证书、Passkey、密码管理器或上游 IdP 会话重新完成了一次认证，而不是读取了原浏览器的 Cookie。

5. OIDC Authorization Code + PKCE 流程

5.1 创建登录事务

业务系统生成：

参数

主要作用

state

把回调绑定到发起登录的浏览器会话，防止登录 CSRF

nonce

把 ID Token 绑定到本次认证请求，防止重放

code_verifier

PKCE 随机秘密，仅由客户端保存

code_challenge

code_verifier 的摘要，发送给 IdP

推荐使用：

code_challenge = BASE64URL(SHA256(code_verifier))
code_challenge_method = S256

5.2 浏览器重定向到授权端点

GET https://sso.example.com/authorize?
    client_id=knowledge-base&
    redirect_uri=https://kb.example.com/callback&
    response_type=code&
    scope=openid%20profile%20email&
    state=random-state&
    nonce=random-nonce&
    code_challenge=...&
    code_challenge_method=S256

scope=openid 表示这是 OIDC 身份认证请求。

5.3 IdP 认证并返回授权码

IdP 检查自己的会话 Cookie：有可接受的会话就继续，否则要求密码、扫码、Passkey 或 MFA。成功后重定向到业务系统注册过的回调地址：

GET https://kb.example.com/callback?code=temporary-code&state=random-state

授权码应短时有效、只能使用一次，并绑定客户端、准确回调地址和 PKCE Challenge。

5.4 后端交换令牌

POST https://sso.example.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=temporary-code
&redirect_uri=https://kb.example.com/callback
&client_id=knowledge-base
&code_verifier=original-random-value

IdP 验证 code_verifier 与最初的 code_challenge 是否匹配，然后返回 ID Token、Access Token，以及按需返回 Refresh Token。

6. 三种令牌的职责

ID Token

回答“刚才完成认证的是谁”，典型 Claims 包括：

{
  "iss": "https://sso.example.com",
  "sub": "user_123456",
  "aud": "knowledge-base",
  "exp": 1784635200,
  "iat": 1784631600,
  "nonce": "random-nonce"
}

业务系统必须验证签名、iss、aud、exp、nonce 和允许的签名算法，不能只做 Base64 解码。

Access Token

回答“客户端能否代表用户调用指定资源服务器”。它应发送给目标 API，不应被当作所有系统通用的身份凭证。

Refresh Token

用于 Access Token 过期后的续期。它生命周期更长、风险更高，应保存在可信后端或安全设备存储中，并支持轮换、撤销和重用检测。

7. 为什么业务系统还需要本地 Session

业务后端验证身份后，通常建立本地 Session，并向浏览器设置：

Set-Cookie: session_id=abc123;
            HttpOnly;
            Secure;
            SameSite=Lax;
            Path=/

这样可以：

  • 独立控制本系统的会话有效期和退出。
  • 在服务端安全保存 OIDC Token。
  • 避免每个页面请求都依赖 IdP。
  • 避免前端 JavaScript 直接接触 Refresh Token。
  • 在用户权限或风险状态变化时立即结束本地会话。

对传统 Python Web 项目，优先考虑 Backend-for-Frontend 模式：浏览器只保存 HttpOnly Session Cookie，OIDC Token 保存在后端。

8. SAML SSO

SAML 2.0 常用于企业系统。SP 发起流程为：

用户访问 SP
→ SP 生成 AuthnRequest
→ 浏览器重定向到 IdP
→ IdP 认证用户
→ IdP 生成签名的 SAML Response
→ 浏览器 POST 到 SP 的 ACS 地址
→ SP 验证 Assertion 并创建本地 Session

SAML Assertion 通常包含 Issuer、Subject、Conditions、Audience、认证声明和用户属性。SP 必须验证 XML 签名、受众、有效期、接收地址、InResponseTo，并防止断言重放。

9. 单点登出为什么困难

一次 SSO 登录可能同时产生：

IdP 登录会话
├── 系统 A 本地 Session
├── 系统 B 本地 Session
├── 系统 C 本地 Session
├── Access Token
└── Refresh Token

删除当前系统 Session 只是本地退出；删除 IdP Cookie 也不保证已经创建的业务系统 Session 立即失效。真正的全局退出可能需要：

  1. 删除 IdP 会话。
  2. 通过 Front-channel 或 Back-channel Logout 通知业务系统。
  3. 删除各系统本地 Session。
  4. 撤销 Refresh Token。
  5. 必要时撤销或等待 Access Token 过期。

产品必须明确“退出当前系统”和“退出所有系统”的不同语义。

10. 账号映射与业务授权

业务系统不要用昵称或可变邮箱作为永久主键，推荐保存：

(issuer, subject) → local_user_id

例如：

issuer

subject

local_user_id

https://sso.example.com

user_123456

10001

首次登录可以执行 JIT Provisioning，但应明确自动注册范围、邮箱验证、默认角色、账号冻结和离职同步策略。

与 Casbin 结合时：

# OIDC 确认用户是谁
current_user_id = session["user_id"]

# Casbin 判断该用户能做什么
allowed = enforcer.enforce(
    current_user_id,
    "tenant-a",
    "/orders/1001",
    "delete",
)

SSO 登录成功不代表用户自动拥有业务权限。

11. 生产安全清单

  • 使用 Authorization Code + PKCE S256，不使用隐式模式传递 Access Token。
  • 回调地址使用预注册的精确匹配，禁止宽泛通配符。
  • 正确校验 state、nonce 和 PKCE 事务绑定。
  • 验证 JWT 签名、iss、aud、exp、nbf、算法和密钥来源。
  • 处理 JWKS 密钥轮换、未知 kid 和合理时钟偏差。
  • 禁止开放重定向；登录后的 next 只能是站内路径或严格白名单。
  • Cookie 设置 HttpOnly、Secure、合适的 SameSite、Domain、Path 与生命周期。
  • 登录成功后轮换 Session ID，写操作仍实施 CSRF 防护。
  • 不在 URL、日志、错误页或前端存储中泄露授权码、Access Token 和 Refresh Token。
  • IdP 或 Token 验证异常时默认拒绝，不绕过认证。
  • 多 IdP 场景按 Issuer 隔离配置，防止混淆攻击。
  • 对高风险操作使用近期认证要求，例如 max_age 或强制 MFA。

12. 常见误区与排查

  1. 认为两个业务系统共享同一个 Cookie：通常共享的是对 IdP 的信任；各系统 Cookie 相互隔离。
  2. 认为换浏览器仍应自动登录：新浏览器没有原 IdP Cookie，通常必须重新认证。
  3. 把 OAuth 当作登录协议：登录身份使用 OIDC；OAuth 主要用于委托访问 API。
  4. 把 Access Token 当 ID Token：两者受众和用途不同。
  5. 只解码 JWT 不验证：任何人都能构造未验证的 Payload。
  6. 使用邮箱作为永久身份主键：优先使用 iss + sub。
  7. 登录成功即拥有所有权限：认证之后仍要执行 Casbin/RBAC/ABAC 授权。
  8. 注销 IdP 就认为所有系统都退出：本地 Session 可能继续有效。
  9. 将 Token 全部放入 localStorage：XSS 可以直接读取这些令牌。
  10. 回调地址使用通配符或开放重定向：可能导致授权码和令牌泄漏。

验证与实践

  • 最小实验：在 Chrome 登录 IdP，依次访问两个 RP；再使用 Safari、无痕窗口和清除 Cookie 后重复观察跳转。
  • 网络观察：记录 /authorize、回调、/token 和本地 Session 建立过程，确认 Token 不出现在日志中。
  • 安全测试：修改 state、复用授权码、篡改 nonce、替换 iss/aud、尝试开放重定向，验证系统均拒绝。
  • 会话测试：分别执行本地退出、IdP 退出和全局退出，记录每个系统的真实状态。
  • 关键指标：登录成功率、P95 登录延迟、MFA 触发率、Token 交换失败率、会话撤销延迟和异常 Issuer 次数。
