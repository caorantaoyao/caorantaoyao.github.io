TCP 连接管理：三次握手、四次挥手与连接状态机

1. TCP 连接管理解决什么问题

TCP 连接管理负责建立双向通信状态、同步双方初始序列号、协商参数，并在通信结束后安全释放两个发送方向。一条连接由源 IP、源端口、目标 IP、目标端口组成的四元组标识，内核还会维护序列号、窗口、缓冲区、重传计时器和拥塞状态。

2. 建立连接前的状态

服务端执行 socket → bind → listen 后进入 LISTEN；客户端执行 connect 后发起握手并进入 SYN_SENT。

3. 第一次握手：客户端发送 SYN

客户端选择初始序列号 x，发送 SYN=1, seq=x，表示希望建立连接，并声明自己的初始序列号。客户端进入 SYN_SENT。

4. 第二次握手：服务端返回 SYN+ACK

服务端收到 SYN 后选择初始序列号 y，返回 SYN=1, ACK=1, seq=y, ack=x+1，随后进入 SYN_RECEIVED。SYN 会占用一个序列号。

5. 第三次握手：客户端返回 ACK

客户端收到 SYN+ACK 后返回 ACK=1, seq=x+1, ack=y+1 并进入 ESTABLISHED。服务端收到最终 ACK 后也进入 ESTABLISHED。

客户端                           服务端
CLOSED                           LISTEN
  ├─ SYN，seq=x ───────────────→ SYN_RECEIVED
  ←──── SYN+ACK，seq=y，ack=x+1 ┤
  ├─ ACK，ack=y+1 ─────────────→
ESTABLISHED                      ESTABLISHED

6. 三次握手确认了什么

  • 客户端能发送、服务端能接收。
  • 服务端能发送、客户端能接收。
  • 服务端知道客户端收到了自己的初始序列号。
  • 同步双方初始序列号。
  • 协商 MSS、窗口扩大、SACK、时间戳等 TCP 选项。

7. 为什么不是两次或四次

两次握手无法让服务端确认客户端已经收到服务端的初始序列号，也更容易受到历史重复 SYN 的影响。三次已经能够同步双方序列号和确认双向收发能力。建立连接时，服务端可以把对客户端 SYN 的 ACK 与自己的 SYN 合并，因此不需要固定四次。

8. listen、connect 与 accept

调用

作用

listen()

把 Socket 变为监听 Socket并初始化连接队列

connect()

客户端发起握手；阻塞模式下通常握手完成后返回

accept()

从内核的已完成连接队列取出连接，返回新的已连接 Socket

三次握手主要由内核完成。应用尚未调用 accept() 时，握手也可能已经完成；监听 Socket 继续接收新连接，而 accept() 返回的连接 Socket 专门服务某个客户端。

9. 半连接队列与全连接队列

概念上，处于 SYN_RECEIVED、尚未完成握手的连接位于半连接相关结构；握手完成但尚未被应用接受的连接进入全连接队列。队列容量耗尽时，新连接可能被丢弃、拒绝或等待重传。具体实现和 backlog 语义依操作系统而异。

10. SYN Flood 与 SYN Cookie

SYN Flood 通过大量发送 SYN 而不完成第三次握手，消耗服务端连接资源。常见防护包括限速、调整队列与超时、DDoS 清洗和 SYN Cookie。SYN Cookie 会先把部分连接信息编码进 SYN+ACK 序列号，收到合法 ACK 后再恢复连接状态。

11. 建立连接后的序列号与 ACK

TCP 按字节编号。若发送 seq=1000、长度 500 字节的数据，接收方连续收到后返回 ack=1500。ACK 表示下一次期望的字节序号，帮助实现可靠传输、累计确认和重传。

12. 第一次挥手：主动方发送 FIN

主动关闭方调用 close()，发送 FIN=1, seq=u，进入 FIN_WAIT_1。FIN 表示本方不会再发送新数据，但仍可以接收另一方向的数据。FIN 会占用一个序列号。

13. 第二次挥手：被动方确认 FIN

被动方返回 ACK, ack=u+1 并进入 CLOSE_WAIT；主动方收到 ACK 后进入 FIN_WAIT_2。此时只关闭了主动方到被动方的发送方向。

14. 第三、四次挥手

被动方应用完成剩余发送并调用 close() 后，发送 FIN，进入 LAST_ACK。主动方返回最终 ACK 并进入 TIME_WAIT；被动方收到 ACK 后进入 CLOSED。

主动关闭方                         被动关闭方
ESTABLISHED                        ESTABLISHED
  ├─ FIN，seq=u ─────────────────→ CLOSE_WAIT
FIN_WAIT_1 ←──────── ACK，ack=u+1 ┤
FIN_WAIT_2                         │
  ←──────────────────── FIN，seq=v ┤ LAST_ACK
  ├─ ACK，ack=v+1 ───────────────→ CLOSED
TIME_WAIT
  ↓ 等待 2MSL
CLOSED

15. 为什么通常是四次挥手

TCP 是全双工的，两个发送方向需要分别关闭。收到 FIN 的一方可能仍有数据未发送，因此先返回 ACK，等应用完成后再发送自己的 FIN。如果收到 FIN 时恰好也已发送完，ACK 和 FIN 可以合并，所以抓包中也可能只有三个报文。

16. 半关闭与 shutdown

shutdown(SHUT_WR) 表示关闭本机发送方向，但仍可接收对方数据；shutdown(SHUT_RD) 表示不再接收；shutdown(SHUT_RDWR) 关闭两个方向。close() 则释放当前文件描述符，底层连接何时真正结束还与引用计数和缓冲数据有关。

17. TIME_WAIT 与 2MSL

主动完成关闭的一方通常进入 TIME_WAIT。它有两个主要目的：若最后 ACK 丢失，可以接收对方重传的 FIN 并再次确认；同时等待旧连接报文在网络中消失，避免干扰相同四元组的新连接。

MSL 是报文段最大生存时间。等待 2MSL 用于覆盖最后 ACK 到达与重传 FIN 返回的最长路径。具体等待时间由操作系统实现决定。

18. TIME_WAIT 与 CLOSE_WAIT 排查

状态

常见含义

主要排查方向

TIME_WAIT

本机频繁主动关闭连接

连接池、Keep-Alive、短连接频率、临时端口

CLOSE_WAIT

对端已发送 FIN，但本机应用尚未关闭 Socket

异常路径、资源泄漏、线程阻塞、finally 清理

TIME_WAIT 不一定是错误；CLOSE_WAIT 长期堆积通常更直接指向应用没有正确释放连接。

19. FIN、RST 与异常断开

FIN 表示有序关闭，此前数据仍应可靠处理；RST 表示立即重置连接，常见于目标端口未监听、连接状态不存在或应用强制终止。网线断开或对端断电时，如果双方都不发送数据，本机可能无法立即发现，需要依靠重传超时、TCP Keepalive 或应用层心跳。

21. Python 操作与 TCP 状态对应

# 服务端
server.bind(("127.0.0.1", 8000))
server.listen(128)                 # LISTEN
connection, address = server.accept()

# 客户端
client.connect(("127.0.0.1", 8000))  # 发起三次握手
client.sendall(b"hello")
client.shutdown(socket.SHUT_WR)       # 关闭发送方向
client.close()

recv() 返回空字节串 b""，通常表示对端已经有序关闭发送方向，当前字节流到达 EOF。

23. 面试回答

TCP 通过三次握手同步双方初始序列号、确认双向收发能力并协商参数。客户端发送 SYN，服务端返回 SYN+ACK，客户端再返回 ACK。阻塞模式下 connect() 通常在握手完成后返回，而 accept() 是从内核已完成连接队列中取出连接。

TCP 关闭通常需要四次挥手，因为两个发送方向要分别关闭。主动方发送 FIN，被动方先 ACK，完成剩余数据发送后再发送 FIN，主动方回复最终 ACK 并进入 TIME_WAIT。TIME_WAIT 用于处理最后 ACK 丢失后的 FIN 重传，并让旧报文消失。大量 TIME_WAIT 常见于频繁主动关闭；大量 CLOSE_WAIT 通常意味着应用未正确关闭 Socket。

24. 一句话总结

三次握手建立双向可信的连接状态，四次挥手分别关闭两个发送方向，TCP 状态机则保证连接在丢包、重传和延迟报文存在时仍能安全建立与释放。
