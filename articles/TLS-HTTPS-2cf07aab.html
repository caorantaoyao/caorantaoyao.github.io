TLS：HTTPS 如何建立可信、加密且防篡改的通信通道

TLS 的核心作用是在不可信的网络中，为客户端和服务器建立一条加密、防篡改，并且能够验证服务器身份的通信通道。HTTPS 可以总体理解为受 TLS 保护的 HTTP：HTTP 规定请求与响应的语义，TLS 负责保护通信过程。

1. 普通 HTTP 存在什么问题

如果使用明文 HTTP，中间网络设备可能读取账号、Cookie和请求正文，也可能修改请求或响应、插入恶意内容，甚至冒充目标服务器。TLS主要解决三个问题。

安全目标

解决的问题

机密性

完整性

防止数据被静默篡改

身份认证

确认对方确实是目标服务器

2. TLS 位于网络分层中的哪里

应用层：HTTP
安全层：TLS
传输层：TCP
网络层：IP
链路层：以太网、Wi-Fi

对于 HTTP/1.1 和 HTTP/2，通常先建立 TCP 连接，再进行 TLS 握手；对于 HTTP/3，TLS 1.3 的安全能力集成在 QUIC 握手中。TLS 不负责 DNS 解析和 IP 路由。

3. TLS 使用的密码学能力

对称加密。双方使用协商出的会话密钥加密大量 HTTP 数据，性能较高。握手完成后的业务数据主要使用对称加密。

非对称密码学。使用公钥和私钥证明服务器拥有证书对应的私钥、验证数字签名，并配合临时密钥交换建立共享秘密。现代 TLS 通常不是用服务器公钥直接加密全部 HTTP 数据。

哈希函数。用于握手完整性验证、密钥派生和数字签名等过程。

数字签名。服务器使用私钥对握手相关信息签名，客户端用证书中的公钥验证，从而确认私钥持有者身份以及内容未被替换。签名主要提供身份和完整性证明，不等于加密。

4. 数字证书是什么

数字证书可以理解为由可信机构签发的服务器电子身份证，通常包含证书绑定的域名、服务器公钥、有效期、颁发者、签名算法及 CA 签名。证书可以公开，必须严格保护的是服务器私钥。

公钥：服务器公钥
有效期：2026-01-01 至 2026-12-31
签发者：某个 CA
CA 签名：……

5. CA 是什么

CA 即证书颁发机构。它验证申请者对域名等标识的控制权，签发包含域名和公钥的证书，并使用 CA 私钥签名。浏览器和操作系统预置受信任的根 CA 证书，因此可以判断服务器证书是否来自可信链路，而不是因为服务器自己宣称可信就相信它。

6. 证书链

服务器证书
→ 中间 CA 证书
→ 根 CA 证书

服务器证书通常由中间 CA 签发，中间 CA 再由更上层 CA 或根 CA 签发。服务器一般发送自己的证书和必要的中间证书；根证书通常已存在于客户端信任库。分层签发可以减少根私钥直接参与日常工作的风险。

7. 客户端怎样验证证书

  • 域名匹配：证书必须覆盖当前访问的域名。
  • 有效期正确：证书不能尚未生效或已经过期。
  • 证书链可信：逐级验证签名，最终连接到本机信任的根 CA。
  • 用途正确：证书应允许用于服务器身份认证。
  • 撤销状态：在相应机制可用时检查证书是否被撤销。
  • 私钥持有证明：服务器对握手信息签名，客户端用证书公钥验证。

8. TLS 1.3 握手的整体流程

  1. 客户端发送 ClientHello，声明支持的版本、算法和密钥交换参数。
  2. 服务器返回 ServerHello，选择版本、算法和自己的密钥参数。
  3. 服务器发送证书链和 CertificateVerify 签名证明。
  4. 客户端验证域名、证书链、有效期、签名和握手内容。
  5. 双方根据密钥交换结果派生会话密钥。
  6. 双方通过 Finished 消息确认握手未被篡改。
  7. 随后使用对称加密传输 HTTP 请求与响应。
ClientHello
→ ServerHello
→ 服务器证书与私钥签名证明
→ 客户端验证证书
→ 双方派生会话密钥
→ Finished
→ 加密 HTTP 通信

9. ClientHello 做什么

ClientHello 告诉服务器客户端支持的 TLS 版本、密码套件、签名算法、密钥交换组、客户端临时公钥以及扩展能力。

SNI。告诉服务器客户端想访问哪个域名。因为一个 IP 可以承载多个 HTTPS 网站，服务器需要据此选择证书和站点配置。

ALPN。协商应用层协议，例如 http/1.1、h2 等。

10. ServerHello 做什么

服务器从客户端提供的选项中选择 TLS 版本、密码套件和密钥交换参数，并返回服务器临时公钥。双方利用临时密钥交换参数独立计算出相同共享秘密，再通过密钥派生函数生成客户端到服务器、服务器到客户端以及握手和应用数据阶段使用的不同密钥。

11. 中间人为什么难以冒充服务器

攻击者即使能拦截通信，也需要证明自己拥有目标域名证书对应的私钥。攻击者通常无法生成通过 CertificateVerify 验证的签名；自行伪造的证书则会因为证书链不受信任、域名不匹配或签名错误而被客户端拒绝。TLS 的安全既依赖加密，也依赖证书信任体系和严格验证。

12. 为什么握手后使用对称加密

非对称密码学计算成本较高，不适合持续加密大量业务数据。TLS 先使用证书、签名和密钥交换完成身份认证及共享秘密建立，再使用高效的对称加密保护 HTTP 数据。

身份认证与密钥交换
→ 建立共享秘密
→ 派生对称会话密钥
→ 加密业务数据

现代 TLS 常使用 AES-GCM 或 ChaCha20-Poly1305 等 AEAD 算法，同时提供加密和完整性认证。

13. TLS 怎样发现数据被篡改

TLS 不只把明文变成密文，还为记录提供认证信息。接收方会验证数据是否来自持有正确会话密钥的一方，以及传输过程中是否发生变化。如果密文被修改，验证通常失败，TLS 会终止连接，而不会把篡改后的数据交给 HTTP 层。

加密解决“看不懂”，完整性认证解决“改不了而不被发现”。

14. 前向保密

现代 TLS 通常使用 ECDHE 等临时密钥交换机制，每次连接生成新的临时密钥。连接结束后临时私钥应被销毁。因此，即使服务器长期私钥以后泄露，攻击者通常也不能仅凭长期私钥解密过去录制的会话，这称为前向保密。服务器长期私钥主要用于证明身份，而不是直接生成每次连接的全部业务密钥。

15. TLS 会话恢复

完整握手需要网络往返和密码学计算。客户端再次访问同一服务时，可以使用会话票据等恢复机制，基于已有安全信息更快地建立新会话密钥。会话恢复并不是简单地永久重复使用上一条连接的全部密钥。

16. TLS 1.3 的 0-RTT

在满足条件的会话恢复中，客户端可以在握手完全结束前发送早期数据，从而降低延迟。但早期数据可能被重放，因此不适合直接用于创建订单、扣款、转账、删除数据等非幂等操作。即使请求可重复，服务端仍应实现相应的防重放策略。

18. TLS 能保护哪些内容

握手完成后，TLS通常保护HTTP方法、URL路径和查询参数、Cookie、Authorization、请求体、响应头与响应体。但IP地址、连接时间、数据量、数据包时序以及某些环境中的域名相关信息仍可能暴露。HTTPS保护通信内容，不代表完全隐藏所有网络行为。

19. HTTPS 不能解决什么

HTTPS不能自动解决服务器被入侵、SQL注入、越权访问、弱密码、恶意网站欺骗、用户设备感染、敏感信息写入日志、前端脚本窃取Token等问题。浏览器锁标志主要表示通信经过加密且证书验证通过，不表示网站业务绝对安全。

20. 双向 TLS

普通 HTTPS 通常只由客户端验证服务器证书；服务器对用户的认证仍通过密码、Session、Token、OAuth 或 API Key。双向 TLS（mTLS）还要求客户端提供证书，常见于企业内部服务、微服务通信、零信任网络、高安全 API 和设备认证。

普通 TLS：客户端验证服务器
mTLS：客户端验证服务器 + 服务器验证客户端

mTLS证明客户端证书所代表的服务、设备或主体身份，但服务端通常仍需执行业务授权。

21. 证书为什么会报警

  • 证书过期或尚未生效；
  • 证书域名不匹配；
  • 证书链不完整；
  • 签发 CA 不受信任；
  • 使用自签名证书；
  • 设备系统时间错误；
  • 中间代理替换证书；
  • 证书可能已经被撤销。

开发环境可以使用自签名证书，但正确做法是把受控的开发 CA 加入测试设备信任库，而不是在生产代码中关闭验证。

22. Python 客户端如何验证 HTTPS

import requests

response = requests.get(
    "https://example.com",
    timeout=5,
)

print(response.status_code)

requests 默认验证服务器证书链是否受信任以及域名是否匹配。生产环境不要使用 verify=False 绕过错误，因为这会破坏服务器身份认证。企业使用私有 CA 时，应显式指定可信 CA 文件：

response = requests.get(
    "https://internal.example.com",
    verify="/path/to/company-ca.pem",
    timeout=5,
)

23. 从输入 HTTPS 地址到收到响应

  1. 浏览器解析 URL，DNS 把域名解析为 IP。
  2. 系统查询路由表，数据通过网关和路由器到达服务器。
  3. HTTP/1.1或HTTP/2先建立 TCP 连接。
  4. 客户端发送 ClientHello，服务器返回所选参数和证书。
  5. 客户端验证证书链、域名、有效期和服务器签名。
  6. 双方通过密钥交换建立共享秘密并派生会话密钥。
  7. 客户端发送加密的 HTTP 请求。
  8. 服务器解密后交给 Web 应用处理。
  9. 服务器生成响应，TLS加密后返回。
  10. 客户端验证并解密响应，再交给浏览器处理。
URL
→ DNS
→ IP 与路由
→ TCP
→ TLS 握手
→ 验证证书
→ 协商会话密钥
→ 加密 HTTP 请求
→ 加密 HTTP 响应

24. 常见误区

  • HTTPS用服务器公钥加密所有网页数据：错误。业务数据主要使用握手后派生的对称密钥。
  • 证书负责加密所有数据：错误。证书主要绑定域名、公钥和身份信息。
  • 有HTTPS就说明网站绝对安全：错误。HTTPS只保护通信链路。
  • TLS只提供加密：错误。它还提供完整性保护和身份认证。
  • 拿到证书就可以直接相信：错误。客户端还要验证域名、有效期、证书链、签名和用途。
  • 关闭证书验证只是少一个警告：错误。这会使中间人攻击更容易成功。

25. 面试回答

TLS位于HTTP与传输层之间，主要提供机密性、完整性和身份认证。握手时，客户端通过ClientHello提供支持的版本、密码套件和临时密钥交换参数；服务器选择参数并发送证书链和私钥签名证明。客户端验证证书域名、有效期、证书链和数字签名，再通过ECDHE等机制与服务器建立共享秘密。双方从共享秘密派生对称会话密钥，之后使用高效的对称加密和完整性认证保护HTTP请求与响应。TLS 1.3简化了握手、移除了旧算法，并默认使用支持前向保密的临时密钥交换。

26. 一句话总结

TLS通过证书和数字签名确认服务器身份，通过密钥交换建立共享秘密，再使用对称加密与完整性认证保护HTTP通信。
