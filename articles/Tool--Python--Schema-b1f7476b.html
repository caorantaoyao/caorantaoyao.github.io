Tool 设计与 Python 实现：Schema、注册表与错误协议

本篇从 Python 工程视角回答一个核心问题：怎样把普通函数变成模型能够正确选择、可靠调用、出现错误后还能恢复的 Agent Tool。总览文档见 。

1. Tool 本质上是一份带执行器的类型契约

普通函数只面向程序员；Tool 同时面向模型与运行时。模型需要理解工具做什么、什么时候用、参数怎样填写，运行时则需要知道如何校验、鉴权、执行和记录结果。因此，一个生产级 Tool 至少包含名称、描述、输入 Schema、输出 Schema、执行器和执行策略。

组成部分

作用

典型问题

name

提供稳定、明确的调用标识

名称是否能直接表达业务动作

告诉模型何时使用以及不能做什么

2. 模型不会直接执行 Python

模型只能生成结构化的 Tool Call，例如选择 get_order_status 并给出 order_id。Agent Runtime 收到调用请求后，先做 Schema 校验和权限判断，再调用真实函数；函数返回的 Tool Result 会重新进入模型上下文。模型读取结果后，才能继续调用其他工具或生成最终答案。

用户请求
  -> 模型读取 Tool 定义
  -> 模型生成 tool_call
  -> Runtime 校验参数与权限
  -> Python Executor 执行
  -> 返回 tool_result
  -> 模型继续决策或结束

3. 一个可运行的 Python Tool

下面使用 Pydantic 定义输入输出。业务身份没有出现在模型参数中，而是由可信运行时上下文注入。

from typing import Literal
from pydantic import BaseModel, Field


class RuntimeContext(BaseModel):
    user_id: str
    tenant_id: str
    request_id: str


class GetOrderInput(BaseModel):
    order_id: str = Field(min_length=1, max_length=64)


class OrderData(BaseModel):
    order_id: str
    status: Literal["created", "paid", "shipped", "closed"]


class ToolResult(BaseModel):
    ok: bool
    data: OrderData | None = None
    error_code: str | None = None
    message: str | None = None
    retryable: bool = False


async def get_order_status(
    ctx: RuntimeContext,
    args: GetOrderInput,
) -> ToolResult:
    order = await order_repo.get(
        tenant_id=ctx.tenant_id,
        order_id=args.order_id,
    )
    if order is None:
        return ToolResult(
            ok=False,
            error_code="ORDER_NOT_FOUND",
            message="订单不存在",
            retryable=False,
        )
    return ToolResult(ok=True, data=OrderData(**order))

这一设计把模型可控参数限制为 order_id。即使模型在 Prompt 中看到另一个租户的 ID，也无法伪造可信的 tenant_id，因为真正查询时使用的是 RuntimeContext。

4. Tool Registry 与统一执行器

真实项目不应到处编写 if tool_name == ...。Tool Registry 负责登记工具元数据，统一执行器负责完成查找、参数校验、鉴权、超时、Trace 和错误归一化。

from dataclasses import dataclass
from typing import Awaitable, Callable, Type
from pydantic import BaseModel, ValidationError


@dataclass
class ToolSpec:
    name: str
    description: str
    input_model: Type[BaseModel]
    handler: Callable[..., Awaitable[ToolResult]]
    risk: str = "read"
    timeout_seconds: float = 10.0


TOOL_REGISTRY: dict[str, ToolSpec] = {}


async def execute_tool(ctx, name: str, raw_args: dict) -> ToolResult:
    spec = TOOL_REGISTRY.get(name)
    if spec is None:
        return ToolResult(ok=False, error_code="TOOL_NOT_FOUND")

    try:
        args = spec.input_model.model_validate(raw_args)
    except ValidationError as exc:
        return ToolResult(
            ok=False,
            error_code="INVALID_ARGUMENTS",
            message=str(exc),
            retryable=False,
        )

    await policy_engine.authorize(ctx, spec, args)
    return await run_with_timeout_and_trace(ctx, spec, args)

框架可以自动把 Python 类型标注和 docstring 转换成 JSON Schema，但自动生成并不等于设计完成。名称、描述、枚举、错误语义和权限边界仍然需要开发者主动定义。

5. 怎样写出模型容易选对的 Tool

职责单一。与其暴露一个既能查又能删的 manage_database，不如拆成 get_user、update_user_email 和 disable_user。工具边界越清楚，模型越容易选择，权限也越容易控制。

描述包含使用边界。描述不仅要说“能做什么”，还要写清“什么时候使用、不会做什么、缺少参数时怎么办”。对于写操作，要明确它会修改外部状态。

参数使用业务类型。优先使用枚举、业务 ID、日期格式和有范围的数字，避免把全部能力压进一个自由文本 command。能用 Literal["low", "medium", "high"] 的地方，就不要让模型随意编写优先级字符串。

返回结构化结果。稳定字段让 Agent、前端、Trace 和评测系统都能可靠消费。大文件或长报告应写入 Artifact Store，Tool Result 只返回摘要、artifact_id 和证据引用。

6. 错误协议决定 Agent 能否自我恢复

错误

retryable

Agent 的合理动作

INVALID_ARGUMENTS

false

根据校验信息修正参数

NOT_FOUND

false

换查询条件或向用户确认

PERMISSION_DENIED

false

停止，不通过换 Prompt 绕过

RATE_LIMITED

true

按服务端提示退避

UPSTREAM_TIMEOUT

true

在预算内有限重试或降级

APPROVAL_REQUIRED

false

暂停运行并请求人工批准

不要把所有异常都转成一段自然语言。机器可读的 error_code、retryable 和 details 能让 Agent Loop 做出确定的下一步判断，也方便统计每种失败的频率。

7. 并行、重试与副作用

多个只读查询彼此独立时可以并行；多个写操作如果修改同一资源，应串行执行或使用版本控制。重试只适用于明确可重试的失败，写操作必须携带幂等键，否则超时后的再次调用可能重复发消息、重复扣款或重复创建订单。

class SendMessageInput(BaseModel):
    chat_id: str
    text: str
    idempotency_key: str


async def send_message(ctx, args):
    previous = await idempotency_store.get(
        tenant_id=ctx.tenant_id,
        key=args.idempotency_key,
    )
    if previous:
        return previous

    result = await message_service.send(args.chat_id, args.text)
    await idempotency_store.save(ctx.tenant_id, args.idempotency_key, result)
    return result

8. Tool 的测试策略

Tool 测试不能只测底层 Python 函数。至少应覆盖 Schema 是否正确、典型用户表达能否选中正确工具、错误参数是否被拒绝、无权限租户能否越权、超时和重试是否受预算控制、相同幂等键是否只产生一次副作用，以及 Tool Result 是否符合约定的输出结构。

  • 单元测试：执行器、参数模型、错误映射和权限策略。
  • 契约测试：JSON Schema 与真实处理函数保持一致。
  • 选择评测：一组用户问题对应预期 Tool 或“不调用 Tool”。
  • 集成测试：真实数据库、HTTP 服务或沙箱中的端到端行为。
  • 回归评测：模型或 Tool 描述调整后，比较选错率和参数错误率。

9. 面试回答

在 Agent 系统中，Tool 不是普通函数的别名，而是模型与执行环境之间的类型化契约。模型只生成工具名和参数，Runtime 负责 Schema 校验、身份注入、鉴权、执行、超时、错误归一化和 Trace。我会用 Pydantic 定义输入输出，用 Registry 管理工具元数据，并让错误返回 error_code 与 retryable，帮助 Agent Loop 决定修参、重试、降级还是停止。对于写操作，还必须加入幂等键和审批，避免恢复或重试产生重复副作用。
