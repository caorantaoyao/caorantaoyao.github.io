Tool Gateway：多租户鉴权、幂等、审批与隔离

Tool Gateway 是 Agent Runtime 与真实业务系统之间的安全执行层。模型可以提出调用请求，但不能绕过 Gateway 直接访问数据库、密钥、宿主机或其他租户资源。总览文档见 。

1. 为什么不能让 Agent 直接调用业务函数

模型输出是不可信输入。它可能传错参数、重复调用、选择过高权限的工具，也可能受 Prompt Injection 影响。如果把模型生成的函数名和参数直接交给数据库或 Shell，等于把概率性决策放在了安全边界上。

Tool Gateway 的任务，是把“模型建议执行什么”转化为“平台允许执行什么”。授权、租户、资源范围、审批结果和密钥都必须来自可信系统，而不是来自模型生成的文字。

2. 推荐架构

用户请求
   -> Agent Runtime
   -> Tool Call
   -> Tool Gateway
        ├─ Schema 校验
        ├─ 身份与租户注入
        ├─ Policy 鉴权
        ├─ 风险分级与审批
        ├─ 限流、预算、超时
        ├─ 幂等与去重
        ├─ Secret Broker
        └─ Trace / Audit
   -> Tool Executor
        ├─ Python 函数
        ├─ 内部 HTTP / RPC
        ├─ MCP Server
        ├─ 数据库
        └─ 隔离容器

Gateway 不负责替模型规划任务；它负责在每一次真实执行前进行确定性检查，并把执行结果归一化后交回 Agent Loop。

3. 可信 Runtime Context

模型参数只能包含业务所需字段。user_id、tenant_id、角色、授权范围和请求链路 ID 应由登录态和服务端会话注入。

from pydantic import BaseModel


class RuntimeContext(BaseModel):
    user_id: str
    tenant_id: str
    roles: set[str]
    scopes: set[str]
    run_id: str
    task_id: str


class DeleteFileInput(BaseModel):
    file_id: str
    reason: str


# 错误设计：把 tenant_id 暴露给模型填写
# 正确设计：通过 ctx.tenant_id 确定资源边界

即使模型把其他租户的 ID 写进 Prompt，Gateway 仍然按当前会话的可信 tenant_id 查询和鉴权。多租户隔离不能依赖“请勿访问其他用户数据”这样的提示词。

4. 服务端鉴权

鉴权至少要回答四个问题：当前主体是谁、它能否调用这个 Tool、能否对目标资源执行这个动作、当前条件是否允许执行。例如，同样拥有 file.delete 权限的用户，也只能删除本租户并且归自己管理的文件。

async def invoke_tool(ctx, tool_call):
    spec = registry.require(tool_call.name)
    args = spec.input_model.model_validate(tool_call.arguments)

    await policy.authorize(
        subject=ctx.user_id,
        tenant=ctx.tenant_id,
        action=spec.action,
        resource=await spec.resolve_resource(args),
    )

    await budget.consume(ctx.run_id, spec.cost)
    await approval.ensure_if_required(ctx, spec, args)

    return await executor.run(
        ctx=ctx,
        spec=spec,
        args=args,
    )

对于 Casbin、OPA 或自研 Policy Engine，模型只提供业务参数；最终授权决策必须由服务端策略引擎完成。

审批应展示具体目标和参数，而不是只问“是否允许 Agent 继续”。用户需要看到将要给谁发消息、删除哪个资源、执行什么命令，以及动作是否可恢复。

6. 幂等：防止同一个动作执行两次

Agent 可能因为网络超时、Worker 重启、Checkpoint 恢复或消息队列重复投递再次调用同一个工具。对写操作，Gateway 应要求稳定的幂等键，并持久化第一次执行的状态与结果。

RECEIVED
  -> RUNNING
  -> SUCCEEDED
  -> 返回首次结果

相同 idempotency_key 再次到达：
  RUNNING   -> 返回处理中
  SUCCEEDED -> 返回已保存结果
  FAILED    -> 根据错误类型决定能否重试

幂等键通常应绑定 tenant_id + tool_name + business_operation_id。不能只放在内存里，否则进程重启后无法识别重复请求。

7. 超时、重试与熔断

每个 Tool 应设置独立超时，整个 Agent Run 还应设置总时间和总成本预算。只读、幂等并且错误明确标记为可重试的调用，可以进行带抖动的指数退避；权限拒绝、参数错误和业务校验失败不应重试。

  • Tool 超时：防止一次外部调用永久占用 Worker。
  • 最大重试次数：防止 Agent 与执行器形成重试风暴。
  • 熔断器：上游持续故障时快速失败，保护平台资源。
  • 并发上限：同时限制系统、租户、用户和 Tool 四个维度。
  • 取消传播：用户取消 Run 后，尽可能取消尚未开始的 Tool。

8. 沙箱、网络与 Secret Broker

普通业务 API 可以在受控 Worker 中执行；Shell、代码运行和文件编辑则应使用隔离进程或短生命周期容器。容器只获得当前任务所需目录、网络目标和资源配额，任务结束后销毁或清理。

密钥不应进入 Prompt、聊天记录或 Tool 参数。Secret Broker 根据可信身份和 Tool 策略，在执行时临时注入短期凭据；Trace 中只记录密钥引用和授权结果，不能记录明文密钥。

9. Tool Result 仍然是不可信输入

网页、邮件和外部 MCP Server 返回的内容可能携带 Prompt Injection，例如要求 Agent 忽略原规则并泄露数据。Gateway 或上层 Runtime 应保留来源标签，限制返回长度，进行必要脱敏，并把外部文本作为数据而不是高优先级指令处理。

一个低权限 Tool 的输出也不能自动获得高权限。后续如果触发发送、删除或执行命令，新的 Tool 调用仍然必须重新鉴权和审批。

10. Trace 与审计

一次调用至少记录 run_id、task_id、tool_call_id、Tool 版本、调用主体、租户、参数摘要、授权结果、审批人、开始结束时间、错误码、幂等键和结果引用。敏感字段应脱敏或仅记录哈希。

Trace 面向研发排障，Audit 面向安全追责。两者可以共享事件源，但访问权限、保留期限和展示字段通常不同。

11. 单服务器 Agent 平台怎样落地

单服务器不需要为每个 Tool 永久运行一个容器。可以复用有界 Worker Pool：数据库查询和普通 HTTP Tool 在 Worker 进程中执行；只有代码、Shell 或不可信插件才申请临时容器。高并发请求先排队，每个租户设置独立并发和成本配额。

FastAPI / WebSocket
  -> Agent Orchestrator
  -> Tool Gateway
  -> Redis Queue + PostgreSQL 状态
  -> 有界 Worker Pool
  -> 按需临时容器
  -> Artifact Store + Trace

12. 面试回答

Tool Gateway 是模型决策层和真实执行层之间的服务端安全边界。模型只能提交工具名和业务参数，用户身份、tenant_id、角色和密钥由 Runtime 注入；Gateway 再完成 Schema 校验、资源级鉴权、预算、审批、幂等、超时和 Trace。写操作使用持久化幂等键，高风险动作在执行前展示具体参数并请求批准，Shell 和不可信代码放入受限容器。这样即使模型选错工具或受到 Prompt Injection，也不能绕过确定性的权限和隔离机制。
