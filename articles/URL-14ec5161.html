一次网络请求如何完成：从 URL 到服务端响应

这是一篇计算机网络主线总览。它不深入每个报文字段，而是回答一个核心问题：当用户输入一个 HTTPS 地址后，浏览器发出的请求如何跨越 DNS、局域网、路由器和传输协议，安全地到达服务器进程，并最终得到 HTTP 响应。

1. 先看完整主线

输入 URL
→ 浏览器解析 URL
→ DNS 获得目标 IP
→ 查询本机路由表
→ 判断目标是否在同一局域网
→ 通过 ARP 找到下一跳 MAC
→ 交给目标主机或默认网关
→ 路由器根据目标 IP 逐跳转发
→ 建立 TCP 或 QUIC 连接
→ TLS 验证证书并协商会话密钥
→ 发送加密的 HTTP 请求
→ 目标端口找到服务端进程
→ 反向代理或 Web 框架处理请求
→ 业务代码访问缓存、数据库或其他服务
→ 生成 HTTP 响应
→ TLS 加密并沿网络返回
→ 浏览器解密、解析和渲染

2. 第一步：浏览器解析 URL

假设用户输入 https://api.example.com:443/users/123?lang=zh。浏览器首先得到协议 HTTPS、域名 api.example.com、端口 443、路径 /users/123 和查询参数 lang=zh。

后续用途

协议 HTTPS

决定使用 HTTP 与 TLS

域名

通过 DNS 获得目标 IP

端口 443

到达主机后找到服务进程

路径与参数

告诉服务器要访问哪个资源

3. 第二步：DNS 把域名转换成 IP

网络层不能直接根据域名路由，因此客户端需要先把域名解析为 IP。浏览器和操作系统会优先检查缓存及 hosts；没有结果时向递归 DNS 查询。递归 DNS 也没有缓存时，再根据根 DNS、顶级域 DNS和权威 DNS提供的信息找到最终记录。

api.example.com
→ 浏览器与系统缓存
→ hosts
→ 递归 DNS
→ 根 DNS
→ 顶级域 DNS
→ 权威 DNS
→ 203.0.113.10

4. 第三步：操作系统查询路由表

得到目标 IP 后，操作系统结合本机 IP、子网掩码和路由表判断数据应该从哪个网络接口发送、下一跳是谁。如果目标位于同一局域网，可以直接发送；否则通常交给默认网关。

路由表存在多条匹配项时一般使用最长前缀匹配，选择范围最具体的路由。如果没有更具体的匹配，就使用默认路由 0.0.0.0/0。

5. 第四步：通过 ARP 找到下一跳

IP 地址负责跨网络定位，但以太网或 Wi-Fi 在当前局域网的一跳传输还需要 MAC 地址。IPv4 中，本机会通过 ARP 找到下一跳的 MAC。

  • 目标在同一局域网：查询目标计算机的 MAC；
  • 目标在其他网络：查询默认网关的 MAC。

访问外网时，本机不需要远程服务器的 MAC，只需要默认网关的 MAC。每经过一个路由器，链路层 MAC 地址通常都会变化，而目标 IP 通常保持不变。

6. 第五步：网关与路由器逐跳转发

默认网关是本机前往其他网络时的默认出口。网关收到数据包后读取目标 IP、查询自己的路由表并选择下一跳。后续路由器重复这一过程，让数据逐渐接近目标网络。

客户端
→ 家用或企业网关
→ 运营商路由器
→ 骨干网路由器
→ 目标机房路由器
→ 目标服务器

每台设备只需决定当前下一跳，不需要由客户端提前规划完整路径。IP 的 TTL 字段可以防止数据包因路由错误而无限循环。

7. NAT 可能在出口处修改地址

客户端经常使用 192.168.x.x 或 10.x.x.x 等私有 IP。出口路由器可能通过 NAT 把内部源 IP 和端口转换成公网 IP 和端口，并保存映射，以便响应到达后再转回正确的内部计算机。

192.168.1.10:52000
→ NAT
→ 公网IP:61000

8. 第六步：建立传输通道

如果使用 HTTP/1.1 或 HTTP/2，客户端通常先与服务器建立 TCP 连接。TCP 通过三次握手建立双方状态，并使用序列号、ACK、重传和排序等机制提供可靠字节流。

如果使用 HTTP/3，则使用运行在 UDP 之上的 QUIC。UDP 本身面向数据报且不保证可靠性，QUIC在其上实现可靠传输、拥塞控制、多路复用和TLS 1.3安全能力。

9. 第七步：TLS 建立安全通道

对于 HTTPS，建立底层传输后还需要 TLS 握手。客户端发送 ClientHello，服务器选择参数并提供证书链和私钥签名证明。客户端验证域名、有效期、证书链和签名，双方再通过 ECDHE 等机制建立共享秘密并派生会话密钥。

ClientHello
→ ServerHello
→ 服务器证书与签名证明
→ 客户端验证服务器身份
→ 密钥交换
→ 派生对称会话密钥
→ 加密 HTTP 通信

TLS提供机密性、完整性和身份认证。业务数据主要使用高效的对称会话密钥加密，而不是一直使用服务器公钥。

10. 第八步：客户端发送 HTTP 请求

安全通道建立后，客户端按照 HTTP 语义发送方法、路径、Header 和可选请求体。例如：

GET /users/123?lang=zh HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer token
Cookie: session_id=abc123

HTTP 描述“想做什么”和“怎样返回结果”，底层 TCP或QUIC、TLS和IP负责把消息安全送达。

11. 第九步：目标端口找到服务端进程

数据包到达目标计算机后，IP层确认目标地址属于本机，传输层再根据协议和目标端口找到对应 Socket。IP负责找到计算机，端口负责找到进程。

目标 IP：找到服务器
目标端口 443：找到监听该端口的 Socket
Socket：把数据交给对应进程

12. 第十步：服务器内部处理请求

请求通常不会直接进入最终业务函数，而可能依次经过：

网卡与操作系统协议栈
→ 负载均衡器
→ 反向代理
→ Web服务器或应用服务器
→ Python Web框架
→ 中间件
→ 路由函数
→ 业务逻辑
→ Redis、数据库或其他服务

例如 FastAPI 根据 HTTP 方法和路径匹配 Python 函数，解析参数和认证信息，再调用业务代码。业务代码可能查询 Redis 缓存、数据库或通过 RPC 调用其他服务。

13. 第十一步：服务器生成并返回响应

业务处理完成后，服务器生成状态码、响应头和响应体。例如：

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{"id":123,"name":"Alice"}

TLS加密响应，TCP或QUIC负责传输，IP和路由器逐跳把数据送回客户端。客户端收到数据后进行完整性验证和解密，再把HTTP响应交给浏览器或调用程序。

14. 浏览器如何处理响应

如果响应是 JSON，前端代码可能解析后更新页面；如果是 HTML，浏览器会解析DOM，并继续请求CSS、JavaScript、图片和字体。因此打开一个页面通常不只发生一次网络请求。

HTML响应
→ 解析HTML
→ 请求CSS
→ 请求JavaScript
→ 请求图片和字体
→ 执行脚本
→ 调用后端API
→ 渲染页面

因此，真实请求不一定每次都完整重复所有步骤。例如已有DNS缓存和可复用HTTPS连接时，客户端可以跳过部分建连过程。

18. 面试回答

浏览器输入URL后，首先解析协议、域名、端口和路径，通过DNS缓存或递归DNS获得目标IP。操作系统根据目标IP查询路由表，判断是直接发送还是交给默认网关，并通过ARP获得下一跳MAC。数据经过多个路由器按目标IP逐跳转发。HTTP/1.1或HTTP/2通常先建立TCP连接，HTTPS随后进行TLS握手，客户端验证服务器证书，双方通过密钥交换派生会话密钥。安全通道建立后，客户端发送加密的HTTP请求。数据到达目标计算机后，操作系统根据端口找到Socket，反向代理或Web框架再把请求交给业务代码。服务器处理完成后生成HTTP响应，由TLS加密，再沿网络返回客户端，浏览器解密、解析并渲染结果。

19. 一句话总结

DNS负责把名字变成IP，路由负责找到计算机，端口负责找到进程，TCP或QUIC负责传输，TLS负责保护通信，HTTP负责表达请求与响应，服务端业务代码负责真正完成工作。
