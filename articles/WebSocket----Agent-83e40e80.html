WebSocket 长连接：从握手、心跳到 Agent 实时通信

1. WebSocket 长连接是什么

WebSocket 是一种在单个 TCP 连接上进行双向、全双工通信的应用层协议。连接建立后，客户端和服务端都可以主动发送消息，不必像普通 HTTP 那样始终由客户端先发起一次请求。

它适合聊天、实时通知、协同编辑、在线游戏，以及 AI Agent 的流式输出、工具进度、审批请求和运行状态推送。地址通常是 ws://；生产环境应使用经过 TLS 加密的 wss://。

长连接不是“连接永远不关闭”，而是连接建立后被持续复用，直到一方主动关闭、网络中断或中间设备超时。

2. 什么叫长连接

短连接通常完成一次或少量请求后就断开；长连接会在一段较长时间内保持可用。保持连接能省去频繁建立 TCP、TLS 和应用层会话的成本，也能让服务端及时向客户端推送事件。

但长连接会长期占用文件描述符、内存和连接状态，因此服务器必须管理连接上限、空闲超时、心跳、背压和异常清理。

3. HTTP Upgrade 握手

WebSocket 并不是一开始就直接发送 WebSocket 帧。客户端先发起 HTTP/1.1 请求，并声明希望升级协议：

GET /ws/runs/run_123 HTTP/1.1
Host: agent.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务端接受后返回 101 Switching Protocols。从这一刻开始，同一条底层连接不再传输普通 HTTP 请求和响应，而是传输 WebSocket Frame。

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

因此，“WebSocket 完全不是 HTTP”并不严谨：它使用 HTTP 完成初始握手，升级成功后才进入独立的 WebSocket 通信阶段。

4. 全双工与 Frame

全双工意味着同一时刻客户端和服务端都可以发送数据。协议以 Frame 为基本传输单位，常见类型包括 Text、Binary、Ping、Pong 和 Close。

  • Text：通常承载 JSON 事件。
  • Binary：适合二进制数据，但不应无节制传输大文件。
  • Ping/Pong：检测连接活性，并帮助维持链路。
  • Close：有序结束连接，可携带关闭码与原因。

一次应用消息可能由多个 Frame 组成，所以应用层不要假设一次底层读取就一定得到一条完整业务消息。

5. 连接生命周期

浏览器 WebSocket 通常经历四个状态：CONNECTING、OPEN、CLOSING、CLOSED。服务端还要处理认证失败、客户端刷新页面、网络切换、进程重启和代理主动断开等情况。

  1. 建立连接并完成 Upgrade。
  2. 认证用户，校验租户和资源权限。
  3. 登记连接与订阅关系。
  4. 双向收发事件，并持续做活性检测。
  5. 主动或异常断开，清理连接、订阅和临时状态。

6. 心跳与 Ping/Pong

TCP 连接存在不代表对端应用仍然健康。RFC 6455 定义了 Ping 和 Pong 控制帧：收到 Ping 的一方应尽快返回 Pong。心跳可用于检测失联，并防止负载均衡器或代理因连接长期无流量而触发空闲超时。

工程上需要统一三个时间参数：心跳间隔、Pong 等待时间和中间设备空闲超时。例如每 20～30 秒发一次心跳，连续若干次未收到响应则断开并重连；具体数值应以基础设施配置和业务容忍度为准。

不要仅在应用层发送字符串 "ping" 就宣称实现了协议级 Ping。浏览器 JavaScript 通常不能直接构造 Ping 控制帧，因此也可设计业务层心跳消息，但客户端与服务端必须明确约定。

8. Python FastAPI 示例

下面示例展示连接建立后的关键顺序：先解析身份，再检查租户与运行权限，最后接受连接并处理消息。真实项目不应仅依赖 URL 中的 run_id 判断权限。

from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

async def authenticate(websocket: WebSocket):
    token = websocket.cookies.get("access_token")
    if not token:
        await websocket.close(code=4401)
        return None
    return await verify_token(token)

@app.websocket("/ws/runs/{run_id}")
async def run_socket(websocket: WebSocket, run_id: str):
    user = await authenticate(websocket)
    if user is None:
        return

    if not await can_access_run(user.id, user.tenant_id, run_id):
        await websocket.close(code=4403)
        return

    await websocket.accept()
    await connection_manager.connect(run_id, user.id, websocket)

    try:
        while True:
            message = await websocket.receive_json()
            message_type = message.get("type")

            if message_type == "run.cancel":
                await cancel_run(run_id, user.id)
            elif message_type == "approval.respond":
                await handle_approval(run_id, user.id, message)
            else:
                await websocket.send_json({
                    "type": "error",
                    "code": "unsupported_message"
                })
    except WebSocketDisconnect:
        await connection_manager.disconnect(run_id, user.id, websocket)

示例中的 4401、4403 是应用自定义关闭码，用于表达未认证和无权限；团队需要统一约定并在客户端解释。

9. Agent 平台事件协议

不要只发送随意拼接的字符串。建议定义稳定的事件信封，让前端、网关和执行器围绕同一协议协作：

{
  "event_id": "evt_01J...",
  "sequence": 128,
  "type": "tool.completed",
  "run_id": "run_123",
  "tenant_id": "tenant_7",
  "timestamp": "2026-08-05T10:30:00Z",
  "payload": {
    "tool_call_id": "call_9",
    "tool_name": "search",
    "status": "succeeded"
  }
}

常见事件包括 run.started、token.delta、tool.started、tool.completed、approval.requested 和 run.completed。事件名描述已经发生的事实；客户端命令则可使用 run.cancel、approval.respond 这样的祈使语义。

10. WebSocket 不等于消息队列

WebSocket 解决的是客户端与服务端之间的实时双向传输；消息队列解决的是服务之间的异步解耦、缓冲、持久化、消费确认和重试。WebSocket 默认不会替你持久化事件，也不能保证客户端离线后仍能收到历史消息。

在 Agent 平台中，执行器可以把事件写入 Redis Streams、NATS、Kafka 或 RabbitMQ；WebSocket 网关消费事件，再推送给当前在线的浏览器。二者是互补关系。

11. 断线重连与事件补发

移动网络切换、电脑休眠、服务器发布都会让连接断开。客户端应使用指数退避加随机抖动重连，避免大量客户端同时重连形成惊群。

第 1 次：约 1 秒后重连
第 2 次：约 2 秒后重连
第 3 次：约 4 秒后重连
……设置最大等待时间，并加入随机抖动

若业务不能丢事件，客户端重连时携带 last_sequence。服务端从持久化事件流中补发 sequence > last_sequence 的事件，再切换到实时推送。若历史已过期，则返回快照并从新的序号继续。

12. 可靠性、顺序与幂等

单条 WebSocket 连接上的帧具有顺序，但业务事件可能来自多个执行器、跨多个实例转发，重连补发也可能产生重复。因此可靠性必须由应用层协议补齐。

  • 使用单调递增的 sequence 检测乱序和缺口。
  • 使用全局唯一 event_id 去重。
  • 客户端命令携带 request_id，服务端按幂等键避免重复取消、重复审批或重复创建任务。
  • 关键状态最终以数据库快照为准，实时事件负责快速更新界面。

13. 多实例扩容

一个 WebSocket 连接只存在于某个网关进程中。Agent 执行器若在另一台机器完成工具调用，不能直接访问该进程内存。因此需要把“执行事件”和“在线连接”分开管理。

Agent Worker → 消息总线 → WebSocket Gateway A → 浏览器 A
                         ↘ WebSocket Gateway B → 浏览器 B

网关维护 user_id/run_id → connection 的本地映射，并在共享系统中登记连接所在实例或订阅相同主题。消息总线将事件送达正确网关，网关再推送到浏览器。负载均衡器可以使用粘性会话降低迁移复杂度，但不能代替共享事件系统。

14. 背压

如果 Agent 产生事件的速度超过客户端消费速度，发送缓冲会不断增长，最终耗尽内存。可以采取以下策略：

  • 为每个连接设置有界队列，超限时关闭或降级。
  • 合并高频的 token.delta，按时间窗口批量发送。
  • 对可丢弃的进度事件做采样；完成、错误、审批等关键事件不得静默丢弃。
  • 限制单消息大小、每秒消息数和并发订阅数。
  • 让客户端报告处理进度，必要时暂停或降低生产速率。

15. 认证与安全

  • 生产环境使用 wss://，避免令牌和业务数据明文传输。
  • 握手阶段验证登录态；连接建立后仍要对每条命令做资源级、租户级授权。
  • 验证浏览器的 Origin，防止跨站 WebSocket 劫持。
  • 尽量使用安全 Cookie、短期一次性票据或子协议传递凭证，避免把长期 Token 放进 URL 和日志。
  • 校验 JSON Schema、消息类型、长度和频率，不信任客户端输入。
  • 连接断开、权限撤销或租户切换时立即清理订阅。

16. 常见错误认识

  • “WebSocket 一定比 HTTP 好”：错误。低频查询和普通 CRUD 使用 HTTP 更简单。
  • “有 WebSocket 就不会丢消息”：错误。离线补发、持久化和确认需要应用层设计。
  • “TCP 保证顺序，所以业务必然有序”：错误。多生产者、多实例和重放会改变业务事件顺序。
  • “连接成功就完成鉴权”：错误。每个命令仍需校验用户、tenant_id、run_id 和操作权限。
  • “WebSocket 可以替代消息队列”：错误。二者解决的问题不同。

17. 面试回答模板

WebSocket 是建立在 TCP 之上的全双工通信协议。它先通过 HTTP Upgrade 握手，服务端返回 101 后，双方在同一长连接上传输 Text、Binary、Ping、Pong 和 Close 帧。相比轮询，它减少了重复请求，并允许服务端主动推送；相比 SSE，它支持双向通信。

在生产系统中，重点不是“连上就行”，而是连接治理：认证授权、心跳和空闲超时、指数退避重连、sequence 补发、event_id 去重、request_id 幂等、背压、限流和多实例消息分发。对于 Agent 平台，我会让 Worker 把运行事件写入消息总线，由 WebSocket Gateway 推送给在线客户端；持久化存储负责断线后的历史补发。
